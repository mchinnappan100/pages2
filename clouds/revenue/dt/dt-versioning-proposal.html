Engineering Proposal

Versioning for Decision Tables & Expression Sets

A zero-manual-intervention approach to validating and deploying DT/ES changes — eliminating the deployment friction caused by active-record locking during validation.

Status: Draft for Review Date: August 2026 Audience: Revenue Cloud Engineering Priority: High

⚠️ Problem Statement

Known Issue

When a Decision Table (DT) or Expression Set (ES) is in Active state, any attempt to validate or re-deploy it requires the record to be deactivated first. This creates a risky manual gap: the entity is briefly inactive in production during the validation window, and any error requires a manual re-activation. Quick-deploy flows are blocked entirely until manual remediation is complete.

Active-Lock Validation Block

Validators reject changes against an active DT/ES, forcing teams to deactivate production records before testing — creating a live outage window.

Manual Re-activation Risk

If validation fails mid-flight, the record stays inactive. Operators must manually re-activate the old version, with no automated rollback.

Deployment Bottleneck

Quick-deploy and CI/CD pipelines stall on DT/ES changes because they cannot proceed without manual deactivation gates being cleared.

💡 Proposed Solution

Core Idea

Introduce a version model for Decision Tables and Expression Sets. Each change creates a new version record in Inactive state. Validation runs against the new version — the active version remains untouched and live. On successful validation, deployment atomically activates the new version and deactivates the old one with no manual steps.

🗂️ Version Data Model

Field Type Description
VersionNumber Integer (auto-increment) Monotonically increasing per parent DT/ES record.
Status Picklist Active · Inactive · Validated · Failed · Deprecated
ParentId Lookup (DT or ES) Reference to the master DT or ES definition record.
DefinitionPayload Long Text / JSON Snapshot of the full rule/expression definition at this version.
ValidatedAt DateTime Timestamp when validation completed successfully.
ActivatedAt DateTime Timestamp when this version was promoted to Active.
DeployedBy Lookup (User) User or automated process that triggered deployment.
PreviousVersionId Lookup (Version) Pointer to the version this one replaced, enabling rollback chain.

  1. Create New Version (Inactive)

    Any edit to a DT or ES creates a new version record in Inactive state. The current active version continues serving production traffic with no interruption.

  2. Run Validation Against New Version

    The validation engine targets the new Inactive version exclusively. Rule conflicts, expression errors, and schema mismatches are surfaced without touching the live record.

  3. Automated Deployment on Success

    On passing validation, the deployment pipeline atomically flips the new version to Active and the previous active version to Deprecated. No manual steps required — compatible with Quick Deploy.

  4. Automatic Rollback on Failure

    If deployment or post-deploy health checks fail, the engine re-activates the previous version via PreviousVersionId without any operator action.

  5. Version History & Audit Trail

    Every version record is retained (with Deprecated status) providing a full audit log of who changed what, when it was validated, and when it went live.

⚙️ API & Platform Design

Version Creation

Triggered automatically by the existing DT/ES save flow. No new UI required. Returns the new VersionId for downstream pipeline reference.

Validation Endpoint

Existing validation APIs accept an optional versionId parameter. When supplied, validation runs against that version record instead of the active one.

Deploy & Activate API

A new activateVersion(versionId) Apex/REST method performs the atomic swap: new → Active, previous → Deprecated, with full transaction rollback on error.

Runtime Resolution

The runtime rule engine always resolves to the record with Status = Active for a given parent, making version selection transparent to callers.

// Pseudocode — deploy flow
VersionRecord newVer = DTVersionService.createVersion(dtId, payload);
ValidationResult result = DTValidationService.validate(newVer.Id);

if (result.isSuccess()) {
    DTVersionService.activateVersion(newVer.Id);  // atomic swap
} else {
    // newVer stays Inactive; active version untouched
    throw new DeployException(result.errors);
}

🛡️ Risks & Mitigations

Concurrent Edit Conflicts
If two engineers create versions from the same parent simultaneously, only the one that completes deployment first becomes Active. The second version is rejected with a conflict error, prompting the author to rebase against the latest Active version. An optimistic locking field (LastActivatedVersionId on the parent) enforces this.
Version Accumulation & Storage
Deprecated versions accumulate over time. A configurable retention policy (default: keep last 10 versions per record) will archive older versions to a cold-storage object. Platform storage impact is bounded.
Runtime Performance
Runtime lookup adds a single indexed filter (Status = Active) to the existing DT/ES query. No additional joins are required. Benchmark target: < 2ms overhead per resolution.
Migration of Existing Records
A one-time migration script will create a Version 1 record (Active) for every existing DT and ES. This is non-destructive — it only inserts new child records and does not modify the parent objects.

✅ Success Criteria

Zero-downtime validation

Active DT/ES version remains untouched during validation of any new version — verified by monitoring active record state throughout the CI pipeline.

No manual deactivation steps

All existing deployment runbooks that contain a "deactivate DT/ES" step are retired. Deployment pipelines pass without operator gates.

Automated rollback coverage

100% of failed deployments trigger automatic rollback to previous Active version, confirmed by post-deploy integration tests.

Full audit trail

Every version creation, validation, activation, and deprecation event is captured in the version history with user, timestamp, and outcome.
