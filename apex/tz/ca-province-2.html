Province-Specific Timezone Hardcoding — Issues & Remediation

Executive Summary

Apex code that adjusts DateTime values using hardcoded hour offsets inside province-code conditions is fragile and can produce incorrect results.

For example, using addHours(-6) for Alberta assumes that the UTC offset is always UTC−6. As of fall 2026 Alberta no longer falls back, so that offset is now correct year-round — but only because legislation happened to align with the hardcoded value. The code remains fragile: any future rule change, or any province where the offset differs, will silently produce wrong results.

The problem is broader than daylight saving time (DST):

  • Canadian provinces and territories do not all follow the same time-zone rules.
  • Some provinces contain multiple time zones.
  • British Columbia introduced permanent UTC−7 time for most of the province in 2026.
  • Alberta enacted legislation in summer 2026 to remain on UTC−6 year-round, effective from the fall 2026 clock change — it will not fall back.
  • A province code does not necessarily identify the time zone of the actual service location.
  • Adjusting a DateTime value to display local time can unintentionally change the represented instant.

Recommended approach: Preserve the original DateTime instant, use time-zone-aware formatting for display, and resolve the time zone from the actual service location wherever possible.

The Pattern

Apex code across the codebase may adjust DateTime values using hardcoded hour offsets inside a province-code condition:

String province =
    orderItems[0].OrderItemRecipient.ServiceStateCode;

if ('AB'.equalsIgnoreCase(province)) {
    dt = dt.addHours(-6);
    Logger.info(
        'SOCR: Adjusted DateTime by -6 hours for province AB'
    );
} else if ('BC'.equalsIgnoreCase(province)) {
    dt = dt.addHours(-7);
    Logger.info(
        'SOCR: Adjusted DateTime by -7 hours for province BC'
    );
} else {
    Logger.info(
        'SOCR: Province ' + province +
        ' found, no adjustment applied'
    );
}

This pattern is superficially readable but has several risks:

  1. The hardcoded offset may be incorrect for the date being processed.
  2. Provinces and territories may contain multiple time zones.
  3. Unhandled province codes silently bypass the adjustment.
  4. The adjustment may change the represented instant rather than simply changing its display.
  5. Government time-zone changes can invalidate assumptions without any obvious failure.

The code must also account for null values and unexpected data formats.

Issues

1. Daylight Saving Time Is Not Uniform Across Canada

Many Canadian regions that observe DST change clocks on the second Sunday in March and the first Sunday in November. However, this is not a universal rule for every province, territory, or locality.

For regions that follow the conventional seasonal schedule, a fixed offset is generally correct during only one of the two periods.

These are regional examples, not universal province-wide rules.

British Columbia: permanent UTC−7 since March 2026

Most of British Columbia adopted permanent UTC−7 time following the March 8, 2026 clock change. Those areas no longer follow the traditional fall-back schedule.

However, some southeastern communities and northeastern British Columbia have different local time-zone practices and may not follow the province-wide permanent-time policy.

Alberta: permanent UTC−6 from fall 2026

Alberta enacted legislation in summer 2026 to stop observing daylight saving time. Effective from the fall 2026 clock change (which Alberta will not make), the province remains at UTC−6 year-round.

This means addHours(-6) for AB is now numerically correct — but it is correct by coincidence, not by design. The IANA identifier America/Edmonton must be updated in the platform's time-zone database before it reflects this change. Until Salesforce ships an IANA tzdata update that includes the Alberta rule, TimeZone.getTimeZone('America/Edmonton') may still apply the old fall-back logic. Verify the platform's tzdata version before relying on it.

Hardcoding −6 is not a safe substitute: a future legislative reversal, or a deployment that processes historical records from before fall 2026, would silently produce wrong results.

Consequently, a single hardcoded offset—or even a single province-to-time-zone mapping—must not be assumed to work for every location in either British Columbia or Alberta without verifying the platform's current time-zone database.

2. Saskatchewan's Time-Zone Rules Require Precision

Most of Saskatchewan observes Central Standard Time (UTC−6) throughout the year and does not change clocks seasonally.

It is therefore incorrect to describe most of Saskatchewan as observing Mountain Standard Time year-round.

The America/Regina identifier is appropriate for most of Saskatchewan. However, Lloydminster and some surrounding areas follow Mountain Time rules.

The time zone must reflect the actual service location, rather than relying exclusively on the province code.

  • Ontario contains both Eastern and Central Time regions.
  • Quebec contains regions that observe Atlantic Time.
  • Nunavut spans multiple time zones.

Yukon uses UTC−7 year-round. Newfoundland Time is a particularly important example because its offset includes 30 minutes. An implementation that assumes every offset is a whole number of hours will fail to represent it correctly.

4. ServiceStateCode Is Not a Time-Zone Field

The field:

ServiceStateCode

may identify a province associated with a service or billing record. It does not necessarily identify the time zone where an appointment or service will take place.

Examples include:

  • Lloydminster: The locality crosses the Alberta–Saskatchewan border, and its local time practices do not align with a simple province-to-zone mapping.
  • Corporate accounts: The billing province may differ from the actual service location.
  • Multiple time zones: Ontario, Quebec and Nunavut contain regions that do not share a single time zone.
  • Data quality: Integrations may provide CA-AB, full province names, lowercase codes, or null values rather than the expected two-letter code.

A province-based mapping may be acceptable when the business explicitly defines a province-level approximation. Otherwise, use a validated service-location-to-time-zone mapping.

5. Government Changes Can Invalidate Hardcoded Assumptions

Governments can change daylight saving time and standard-time rules.

British Columbia's March 2026 and Alberta's fall 2026 permanent-time changes demonstrate why assumptions about clock changes must not be embedded in application logic. In Alberta's case the hardcoded addHours(-6) became numerically correct — but only by coincidence, and with no indication in the code that a law changed.

A hardcoded value may become correct or incorrect following a legislative change, with no compilation error or automatic test failure.

An IANA time-zone identifier delegates the seasonal and historical rules to the platform's time-zone database. However, the platform's database must itself contain the relevant rule updates.

6. Tests Must Not Depend on the Date They Run

Tests that use the current date can conceal seasonal bugs.

For example, a test executed during summer might accept an Alberta offset of UTC−6. The same assumption will be incorrect during standard time.

Tests should use fixed date-time instants and assert the expected local representation for each relevant time zone.

Remediation

Option 1 — Format the Original DateTime for Display

If the requirement is to display a timestamp in the service location's local time, do not modify the original DateTime value.

Apex supports time-zone-aware formatting through DateTime.format(String, String).

String tzId = 'America/Toronto';

String localDisplay = utcDt.format(
    'yyyy-MM-dd HH:mm:ss',
    tzId
);

// Keep utcDt unchanged.
// Use localDisplay for presentation only.

This approach lets the platform apply the applicable time-zone rules when formatting the instant.

Do not do this for display purposes:

utcDt = utcDt.addHours(-5);

That operation changes the represented DateTime instant. It is not equivalent to formatting the original instant in Eastern Time.

Option 2 — Use a Validated Time-Zone Mapping

If the application has a business requirement to map province codes to time zones, centralize the mapping instead of scattering hardcoded offsets across Apex classes.

The following example is a starting point for a province-level approximation. It must be adapted to the application's geographic requirements and verified against the Salesforce runtime's current time-zone rules.

private static final Map<String, String> PROVINCE_TZ =
    new Map<String, String>{
        'AB' => 'America/Edmonton',
        'BC' => 'America/Vancouver',
        'MB' => 'America/Winnipeg',
        'NB' => 'America/Moncton',
        'NL' => 'America/St_Johns',
        'NS' => 'America/Halifax',
        'NT' => 'America/Yellowknife',
        'NU' => 'America/Rankin_Inlet',
        'ON' => 'America/Toronto',
        'PE' => 'America/Halifax',
        'QC' => 'America/Toronto',
        'SK' => 'America/Regina',
        'YT' => 'America/Whitehorse'
    };

public static String formatForProvince(
    Datetime utcDt,
    String province
) {
    if (utcDt == null) {
        throw new TimezoneMappingException(
            'DateTime must not be null'
        );
    }

    String code = province == null
        ? null
        : province.trim().toUpperCase();

    String tzId = code == null
        ? null
        : PROVINCE_TZ.get(code);

    if (tzId == null) {
        throw new TimezoneMappingException(
            'Unsupported province code: ' + province
        );
    }

    return utcDt.format(
        'yyyy-MM-dd HH:mm:ss',
        tzId
    );
}

Define the custom exception in the containing Apex class:

public class TimezoneMappingException extends Exception {}

This example demonstrates centralized mapping, input validation and display formatting. It does not resolve the geographic exceptions described earlier.

For applications that require accurate local time at every service address, prefer a validated location-level mapping rather than using the province code as the final time-zone authority.

Option 3 — Use TimeZone.getOffset() Only When an Offset Is Actually Needed

Apex provides TimeZone.getOffset(DateTime) to obtain the time-zone offset for a specific instant.

For example:

TimeZone tz = TimeZone.getTimeZone(
    'America/Toronto'
);

Integer offsetMs = tz.getOffset(utcDt);
Integer offsetSeconds = offsetMs / 1000;

The returned offset accounts for the time-zone rules available to the Salesforce runtime at that instant.

However, the offset should not normally be added to the original DateTime merely to display local time.

If an integration specifically requires a numeric offset, use the offset as part of that integration's explicitly defined conversion contract. Keep the original instant intact unless a genuine conversion is required.

Option 4 — Handle Unknown Locations Explicitly

Avoid silent fallback logic such as:

else {
    Logger.info(
        'Province found, no adjustment applied'
    );
}

If the location cannot be resolved, either stop processing with a clear application-specific exception or route the record to an explicit error-handling workflow.

For example:

if (tzId == null) {
    Logger.error(
        'No timezone mapping for province: ' +
        province
    );

    // Reject or route the record for remediation.
    // Do not silently assume an offset.
}

The exact error-handling mechanism should follow the application's logging and transaction-management conventions.

Detection

Use the apex-timezone-scan.js scanner with the --check-province option to identify suspicious patterns:

node apex-timezone-scan.js \
  -d ./force-app \
  --web \
  --check-province

Review findings categorized as:

province-timezone-adjustment

Potential indicators include:

  • addHours() calls inside conditionals that compare province codes.
  • equalsIgnoreCase() checks against two-letter Canadian province or territory codes.
  • Logger messages mentioning a province and a numeric hour offset.
  • Hardcoded UTC offsets near service-address or appointment-processing logic.
  • Date-time adjustments in code that later persists or transmits the modified value.

The scanner identifies patterns, not definitive defects. Each finding must be reviewed to establish the intended semantics of the DateTime, whether the offset is correct for the target location and instant, and whether the code is performing a real conversion or merely attempting to format a value.

Testing Strategy

Build deterministic regression tests around fixed instants rather than the current clock.

Required test cases

  1. Standard time: Verify local formatting for a winter instant in a region that observes DST.
  2. Daylight time: Verify local formatting for a summer instant in the same region.
  3. Transition boundaries: Test instants immediately before and after relevant DST transitions.
  4. No-DST regions: Verify Saskatchewan, Yukon, Alberta (from fall 2026), and most of BC — locations that do not change clocks.
  5. Half-hour offsets: Verify Newfoundland Time.
  6. British Columbia and Alberta: Test permanent-time rules and regional exceptions; verify the platform's tzdata reflects the 2026 legislative changes.
  7. Multiple time zones: Verify locations in Ontario, Quebec and Nunavut that use different time zones.
  8. Invalid input: Test null, unknown and malformed province codes.
  9. Instant preservation: Confirm that formatting does not alter the original DateTime value.
  10. Database and integration behavior: Verify that values retain the intended instant when stored, retrieved and transmitted.

Tests for DST transitions should assert the expected local representation using verified time-zone rules for the relevant dates. Also verify that the Salesforce runtime's time-zone database contains the government changes the application expects — specifically the Alberta fall 2026 and BC March 2026 permanent-time rules, as these may not yet be present in the platform's bundled tzdata release.

Final Recommendation

For Apex code, the preferred design is:

  1. Preserve the original DateTime instant.
  2. Resolve the intended time zone from a validated service location or business mapping.
  3. Use time-zone-aware formatting when displaying local time.
  4. Use explicit conversion logic only when a downstream system requires it.
  5. Reject or flag unresolved time-zone mappings.
  6. Test standard time, daylight time, transition boundaries and regional exceptions.
  7. Verify that Salesforce's current time-zone database reflects applicable government changes.

The objective is not simply to replace hardcoded hour values. It is to make the intended time-zone semantics explicit and prevent silent corruption of date-time values.
