sf-rust git hook

Install, remove, and list Salesforce-aware git hooks. Hooks are shell scripts written to .git/hooks/ and invoked automatically by git at key workflow moments — before a commit, before a push, and when a commit message is saved. Each hook calls back into sf-rust to show enriched Salesforce component context exactly when you need it.

Subcommands

SubcommandDescription
hook install [HOOK] [--block] Write hook script(s) to .git/hooks/. Any pre-existing hook that is not sf-rust managed is backed up to <hook>.pre-sf-rust first. Idempotent — re-install at any time to change mode.
hook uninstall [HOOK] Remove managed hook(s). Automatically restores the .pre-sf-rust backup if one exists. Refuses to remove hooks it did not write.
hook list UTF8_FULL table showing each hook: Installed yes/no, Managed (sf-rust / external / —), Blocking (yes / —), and full path.

How it works

Every generated hook script starts with a # managed-by: sf-rust line. This marker is what hook uninstall checks before touching a file — it will never remove a hook that you wrote yourself or that another tool installed. The SF_RUST_HOOK_BLOCK variable inside the script controls blocking mode; re-installing with or without --block is the standard way to toggle it. 

# Structure of every sf-rust managed hook
#!/usr/bin/env bash
# managed-by: sf-rust          ← identity marker (never remove without this)
# sf-rust pre-commit: ...       ← human-readable description
SF_RUST_HOOK_BLOCK=0           # 0 = informational only  |  1 = blocking

# Guard: if sf-rust isn't on PATH, do nothing (CI machines without the binary)
if ! command -v sf-rust &>/dev/null; then
    exit 0
fi
# ... hook body ...
exit 0

Blocking vs non-blocking

ModeHow to installExit code on violationBest for
Non-blocking (default) sf-rust git hook install Always 0 — git proceeds regardless Onboarding, solo projects, teams getting started with the hooks
Blocking sf-rust git hook install --block Non-zero on violations — git operation is aborted Mature teams with enforced commit standards; CI-adjacent local gates
◆

Switching modes is safe. Re-running hook install (with or without --block) overwrites the existing managed hook in place — no backup is taken for a managed-to-managed update, and no git history is affected. Run hook list afterward to confirm the Blocking column.

pre-commit hook

Fires before git opens the commit-message editor. Shows a Salesforce component summary of exactly what is staged — the same output as sf-rust git status --staged — so you can see at a glance whether you are committing an ApexClass, a Flow, a PermissionSet, etc. In blocking mode it additionally refuses the commit if any staged file has an unresolved merge conflict.

Script (non-blocking)

#!/usr/bin/env bash
# managed-by: sf-rust
SF_RUST_HOOK_BLOCK=0

if ! command -v sf-rust &>/dev/null; then exit 0; fi

echo ""
echo "── sf-rust: staged changes ────────────────────────────────"
sf-rust --no-time git status --staged 2>/dev/null || true
echo "────────────────────────────────────────────────────────────"
echo ""
exit 0

pre-push hook

Fires before git sends objects to the remote. Receives the remote name and URL as arguments, and reads local_ref → remote_ref pairs from stdin (one per ref being pushed). For each ref it shows the enriched sf-rust git log of commits that are new to the remote — giving you a last-chance review of what Salesforce metadata is about to land in the shared repo.

Script (non-blocking)

#!/usr/bin/env bash
# managed-by: sf-rust
SF_RUST_HOOK_BLOCK=0

if ! command -v sf-rust &>/dev/null; then exit 0; fi

remote="$1"
url="$2"

while read local_ref local_sha remote_ref remote_sha; do
    if [[ "$remote_sha" == "0000000000000000000000000000000000000000" ]]; then
        range="$local_sha"           # new branch — show all commits
    else
        range="$remote_sha..$local_sha"  # delta since last push
    fi

    count=$(git log --oneline "$range" 2>/dev/null | wc -l | tr -d ' ')
    [[ "$count" -eq 0 ]] && continue

    echo ""
    echo "── sf-rust: pushing $count commit(s) to $remote ($remote_ref) ──"
    sf-rust --no-time git log --since="1 month ago" 2>/dev/null | head -60 || true
    echo ""
done
exit 0

commit-msg hook

Receives the path to the commit-message file as $1. Strips comment lines (lines beginning with #) and checks that the remaining body is non-empty. In blocking mode it additionally warns when the subject line exceeds 72 characters, and fails when a multi-paragraph message is missing the required blank line between subject and body — the Git convention that makes git log --oneline and email patches work correctly.

Script (blocking mode shown)

#!/usr/bin/env bash
# managed-by: sf-rust
SF_RUST_HOOK_BLOCK=1

MSG_FILE="$1"

# Strip comment lines, collapse blank-only lines
BODY=$(grep -v '^#' "$MSG_FILE" | sed '/^$/d')

if [[ -z "$BODY" ]]; then
    echo "ERROR: commit message is empty." >&2
    exit 1
fi

SUBJECT=$(echo "$BODY" | head -1)
LEN=${#SUBJECT}

if [[ "$SF_RUST_HOOK_BLOCK" == "1" ]]; then
    if [[ $LEN -gt 72 ]]; then
        echo "WARNING: subject is $LEN chars (recommended ≤ 72)." >&2
        # warning only — does not block
    fi
    LINE2=$(echo "$BODY" | sed -n '2p')
    if [[ $(echo "$BODY" | wc -l | tr -d ' ') -gt 1 && -n "$LINE2" ]]; then
        echo "ERROR: missing blank line between subject and body." >&2
        exit 1
    fi
fi
exit 0

Commit message rules (blocking mode)

RuleSeverityCondition
Non-empty messageHard fail (exit 1)Message is blank after stripping comment lines
Subject ≤ 72 charsWarning only (exit 0)Subject line exceeds 72 characters
Blank line after subjectHard fail (exit 1)Body present but no blank line separating it from the subject

Switching blocking mode

Re-install at any time — the script is overwritten in place, no backup is taken for managed-to-managed updates, and hook list immediately reflects the new mode. 

# Start informational, switch to blocking when the team is ready
$ sf-rust git hook install           # non-blocking
$ sf-rust git hook list              # Blocking column is empty

# Team agrees on enforcement — switch to blocking
$ sf-rust git hook install --block   # overwrites in place
$ sf-rust git hook list              # Blocking column shows 'yes'

# Roll back to informational
$ sf-rust git hook install           # overwrites back to non-blocking

CI / automation notes

Every generated hook script begins by checking whether sf-rust is on PATH. If the binary is not found the hook exits 0 silently — so CI runners that don't have sf-rust installed will never be blocked or fail. This makes the hooks safe to install in shared repositories used by both developer machines and CI pipelines. 

# CI pipeline does not need sf-rust — hooks are no-ops
# Developer machine with sf-rust — hooks show enriched output

# To explicitly skip hooks in CI (e.g. automated release commits):
$ git commit --no-verify -m "chore: bump version"  # bypasses all hooks

Troubleshooting

SymptomCauseFix
hook uninstall says "not managed by sf-rust" The hook was written by another tool (Husky, Lefthook, etc.) and lacks the # managed-by: sf-rust marker Install sf-rust hook first (hook install) — it backs up the existing one, then uninstall restores it
Hook fires but sf-rust command not found Shell PATH at hook time differs from interactive PATH (common on macOS with GUI git clients) Add export PATH="$HOME/.local/bin:$PATH" near the top of the hook script, after the managed-by marker
Hook fires but shows no component table No files are staged (git commit --allow-empty or staging area is empty) Expected — sf-rust git status --staged prints "nothing to commit" when the index is clean
pre-commit blocks a commit unexpectedly in blocking mode Staged file has merge conflict markers (<<<<<<<) Resolve the conflict and re-stage the file, or use git commit --no-verify to bypass for a known-good emergency commit
Want to disable hooks temporarily without uninstalling Need to bypass for one operation git commit --no-verify or HUSKY=0 git commit (if Husky co-exists) — both skip all hooks

Diff engines

File diffs are routed by extension to a format-aware engine. Each engine returns normalized content (used by Monaco for clean visual diffs) and a structured change list (used by --stat and terminal output).

ExtensionEngineWhat it does
.xml .field-meta.xml -meta.xmldiff_xml()Structural XML diff — element-level changes, ignoring whitespace and attribute order
.jsondiff_json()Key-level JSON diff — detects added/removed/changed keys recursively
.csvdiff_csv()Row-level CSV diff — added/removed/changed rows, header-aware
all othersdiff_text()Unified line diff — Apex, JS, HTML, YAML, etc.
◆

The normalized content fed to Monaco is the same content that the diff engine compared, so the visual diff always matches the terminal diff — no surprises from byte-order marks, inconsistent line endings, or attribute-ordering noise.
