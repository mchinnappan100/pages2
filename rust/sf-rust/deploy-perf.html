What the numbers mean

DreamHouse LWC — 2.0×
Both tools send identical SOAP deploy requests to the same Salesforce server and poll for the same result. The gap comes entirely from the client side:

  • Startup — sf-rust is a native binary that starts in under 2 ms. sf boots the Node.js runtime, loads the @salesforce/cli plugin chain, and resolves JIT code before the first byte of the zip is written.
  • Zip assembly — sf-rust builds the deploy package in Rust (synchronous, zero-copy where possible). sf delegates to a JavaScript metadata library.
  • Poll loop — sf-rust polls with a direct reqwest async call; sf routes through several middleware layers.

Network round-trips and Salesforce server-side compilation time are shared equally — they form the floor both tools sit on, which is why the speedup is 2× rather than 10×.

Enterprise project — 2.5×
A larger project amplifies the zip-assembly advantage: merging ~400 metadata components into a deployable archive takes measurably longer in the Node.js pipeline, while Rust's synchronous directory walk and XML merge remain constant-cost per file.

Why the DreamHouse deploy is slower than the enterprise deploy for sf-rust
DreamHouse includes folder-based static resources (the Leaflet.js map library) that must be zipped into a nested .resource file inside the outer deploy archive. This double-zipping adds ~5 s of Rust CPU time not present in the enterprise project, yet sf-rust still finishes more than 2× faster than sf.

DX-to-Metadata API conversion — what sf-rust handles

DreamHouse ships in DX source format (decomposed objects, separate field files, Jest test fixtures in the bundle). The SOAP Metadata API requires old-style merged .object files and no tooling artefacts. sf-rust converts automatically:

DX format on disk Deployed as
objects/Broker__c/fields/*.field-meta.xml Merged objects/Broker__c.object
staticresources/leafletjs/ (folder) Zipped staticresources/leafletjs.resource
staticresources/sampleData.json Renamed staticresources/sampleData.resource
lwc/*/__ tests__/** Excluded (not sent to server)
jsconfig.json, .eslintrc, .snap Excluded

The key insight: merged custom-object XML must live at objects/ObjectName.object (old-style path) rather than objects/ObjectName/ObjectName.object-meta.xml; the subdirectory form causes the Metadata API to expect decomposed sub-components it cannot resolve.
