SF CLI vs SF-Rust: Architecture, Safety, and Execution Model

Overview

Both tools authenticate to Salesforce and invoke the same REST/SOAP APIs.
What differs fundamentally is how they execute on your machine.

Node.js Calling C++: The Hidden Unsafe Boundary

The SF CLI is TypeScript, but every I/O operation ultimately crosses into C++.
This boundary is the source of most native crashes in Node.js tooling.

How the crossing works

TypeScript code
    │
    │  require('fsevents')          // .node file = compiled C++ shared library
    ▼
Node.js N-API / node-addon-api
    │
    │  napi_create_string_utf8()    // bridge: JS ↔ C heap
    ▼
C++ addon code
    │
    │  Manual malloc / free         // no safety guarantees
    │  Raw pointer arithmetic
    │  No lifetime tracking
    ▼
OS system calls

Why this is unsafe

Issue C++ (in Node addons) Rust
Buffer overflow Possible — no bounds check Compile error
Use-after-free Possible — manual memory Impossible — borrow checker
Data race Possible — shared mutable state Compile error
Null pointer deref Possible Option<T> — no null
Integer overflow Silent wrap or UB Panics in debug, checked in release
Memory leak Common — GC does not manage C++ heap Dropped deterministically

When a C++ addon crashes inside Node.js, it takes the entire sf process with it —
no stack unwind, no error recovery, just a segfault.

Real example: the N-API call path for a file read

sf deploy metadata               // TypeScript
  → fs.readFileSync(path)        // Node.js built-in
    → uv_fs_read()               // libuv — C
      → read()                   // POSIX syscall — C
        → kernel

Every step from libuv downward is C with no memory safety.
If the path buffer is malformed, behavior is undefined.

Rust's Execution Model: Safety Without a GC

Rust achieves memory safety at compile time through its ownership and borrowing rules.
There is no garbage collector, no reference counting by default, no runtime safety checks.

Ownership in one paragraph

Every value in Rust has exactly one owner.
When the owner goes out of scope, the value is freed — automatically, deterministically.
You can borrow a value (shared &T or exclusive &mut T), but the compiler
statically proves that no borrow outlives its owner and that mutable and
shared borrows never coexist. This eliminates use-after-free, double-free,
and data races at compile time.

// This code does not compile — use-after-free caught at compile time
let s = String::from("hello");
let r = &s;
drop(s);        // error: cannot move `s` because it is borrowed
println!("{r}");

The type system enforces protocol correctness too

// sf-rust: token is NEVER accidentally printed — it lives in StoredCredentials,
// and the Display command explicitly shows "[REDACTED]".
// There is no way to accidentally pass it to a logging function without
// wrapping it in a type that opts in.

TLS: OpenSSL (C) vs rustls (Rust)

SF CLI uses Node.js's built-in TLS which links against OpenSSL — a C library
with a long history of critical CVEs (Heartbleed, POODLE, DROWN).

SF-Rust uses rustls — a TLS implementation written entirely in Rust:

Property OpenSSL (SF CLI) rustls (SF-Rust)
Language C Rust
Memory safety Manual Compile-time guaranteed
Notable CVEs Heartbleed (2014), DROWN (2016), … None to date
Linking Dynamic .dylib / .so Statically compiled in
Distribution Depends on system OpenSSL version Self-contained

No dynamic linking means sf-rust produces a single binary that runs identically
on any macOS machine without worrying about which OpenSSL version is installed.

Startup Time: Why the Gap Is So Large

SF CLI startup sequence (~2 s):
  1. OS loads Node.js binary               ~30 ms
  2. V8 initialises JIT compiler           ~100 ms
  3. Node.js loads ~800 JS/TS modules      ~400 ms
  4. oclif plugin framework initialises    ~200 ms
  5. Plugin manifest scanned               ~300 ms
  6. TypeScript → JS (already compiled,    ~200 ms
     but still parsed by V8)
  7. Your command runs                     ~remaining

SF-Rust startup sequence (~80 ms):
  1. OS loads binary (already machine code)  ~5 ms
  2. Tokio async runtime starts              ~2 ms
  3. Config file parsed (TOML)              ~1 ms
  4. Your command runs                      ~remaining

The difference is structural: Node.js is a VM that interprets a program;
sf-rust is the program — compiled directly to ARM64 / x86-64 machine code.

Async I/O: Node.js Event Loop vs Tokio

Both tools do async I/O (non-blocking HTTP), but via different mechanisms.

Node.js (libuv):                    sf-rust (tokio):
─────────────────────────           ──────────────────────────────
Single-threaded event loop          Multi-threaded work-stealing scheduler
Callbacks → Promises → async/await  Native async/await (zero-cost futures)
libuv handles I/O (C)               epoll/kqueue directly (Rust)
GC pauses can stall the loop        No GC — no pauses

For a CLI that makes a handful of HTTP calls, the difference is negligible.
For bulk operations (data import, parallel deploys) the Tokio model scales
without the GC pause risk.

Dependency Footprint

SF CLI install:
  ~2,500 npm packages
  ~450 MB on disk
  C++ addons compiled at install time (node-gyp)
  Requires: Node.js runtime, npm, python3 (for node-gyp), Xcode CLT

SF-Rust install:
  1 binary (~12 MB stripped)
  0 npm packages
  0 C++ addons
  Requires: nothing at runtime

Fewer dependencies = smaller attack surface, faster CI setup, no install-time compilation.

Credential Storage: Encryption at Rest

Both tools encrypt credentials at rest using AES-256-GCM.

Property SF CLI SF-Rust
Algorithm AES-256-GCM AES-256-GCM
Format ciphertext:iv (hex) nonce:ciphertext (hex)
Key storage OS Keychain (one entry, prompts once per binary rebuild) ~/.sf-rust/.key (chmod 600, never prompts)
Token file ~/.sfdx/<username>.json (one per org) ~/.sf-rust/credentials.json (all orgs)

SF CLI stores the encryption key in the macOS Keychain. This triggers a password
prompt each time a new binary build is detected (ACL tied to the code signature).
SF-Rust stores the key in a 0600 file, avoiding all Keychain interaction.

Error Handling: Exceptions vs Result Types

// SF CLI (TypeScript) — errors are thrown exceptions
try {
  const result = await org.getConnection().query(soql);
} catch (e) {
  // e is `unknown` — could be anything
  // compiler does not guarantee you handled it
}

// SF-Rust — errors are values, handling is enforced by the compiler
let result = client.query(&soql).await?;
// The `?` propagates SfError up the call stack.
// If you forget to handle it, the code does not compile.

Rust's Result<T, E> type makes every fallible operation explicit.
There are no uncaught exceptions, no silent failures.

SF-Rust is not a rewrite for performance alone.
The safety properties are structural: the entire tool — from TLS to credential
storage to async I/O — is written in a language that proves memory and
thread safety before the binary is ever executed.
