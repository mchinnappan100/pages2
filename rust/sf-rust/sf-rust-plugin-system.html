How it works

sf-rust uses a git-style external dispatch model. Before parsing arguments, it looks at the first positional argument. If it is not a built-in subcommand, sf-rust searches every directory in PATH for an executable named sf-rust-<name>. If found, the current process is replaced by the plugin — no subprocess, no wrapper.

Dispatch flow

On macOS and Linux, exec() replaces the sf-rust process — signals propagate correctly and there is zero subprocess overhead. On Windows, sf-rust spawns the plugin and forwards its exit code.

Zero configuration Any executable on your PATH named sf-rust-* is automatically a valid sf-rust subcommand. No registration, no config file, no restart needed.

Clone or download the sample-plugins/ directory from the sf-rust repo.

Run the install script:

bash sample-plugins/install.sh          # → ~/bin
bash sample-plugins/install.sh ~/.local/bin # custom dir

Make sure the target directory is on your PATH:

# Add to ~/.zshrc or ~/.bashrc
export PATH="$HOME/.local/bin:$PATH"

Verify:

sf-rust plugin list

Write a plugin

A plugin is any executable file named sf-rust-<name> placed on your PATH. It can be a shell script, Python, Ruby, Go, a compiled Rust binary — anything.

Shell script (simplest)

#!/usr/bin/env bash
# File: sf-rust-hello
set -euo pipefail

echo "Hello from sf-rust-hello!"
echo "Arguments: $*"

# Call back into sf-rust from inside a plugin:
sf-rust org display "$@"
chmod +x sf-rust-hello
cp sf-rust-hello ~/bin/
sf-rust hello -o dev1

Python script

#!/usr/bin/env python3
# File: sf-rust-my-report
import argparse, json, subprocess, sys

def main():
    p = argparse.ArgumentParser(prog="sf-rust my-report")
    p.add_argument("-o", "--org", required=True)
    args = p.parse_args()

    # Call sf-rust data query and parse JSON
    r = subprocess.run(
        ["sf-rust", "data", "query",
         "-q", "SELECT Name, Industry FROM Account LIMIT 5",
         "-o", args.org, "--json", "--no-time"],
        capture_output=True, text=True
    )
    records = json.loads(r.stdout).get("result", {}).get("records", [])
    for rec in records:
        print(f"{rec['Name']:<40} {rec.get('Industry','')}")

if __name__ == "__main__":
    main()

Rust binary (separate crate)

# Cargo.toml
[package]
name    = "sf-rust-myplugin"
version = "0.1.0"
edition = "2021"

[[bin]]
name = "sf-rust-myplugin"   # binary name = plugin invocation name
path = "src/main.rs"
cargo install --path .   # installs to ~/.cargo/bin/sf-rust-myplugin
sf-rust myplugin --help

Argument passing

sf-rust passes every argument after the subcommand name to your plugin.

User typesPlugin receives
sf-rust hello world world
sf-rust hello -o dev1 --json -o dev1 --json
sf-rust hello (no arguments)
Note on global flags Global sf-rust flags typed before the subcommand name (--json, --verbose, --no-color, --no-time) are not forwarded. Accept these flags directly in your plugin if you need them.

Calling back into sf-rust

Plugins can shell out to sf-rust to use any built-in command:

#!/usr/bin/env bash
# sf-rust-open-limits — open the org limits page in the browser
ORG="${1:?Usage: sf-rust open-limits <alias>}"
URL=$(sf-rust org open -o "$ORG" --url-only 2>/dev/null)
open "$URL/lightning/setup/OrgLimits/home"

Naming conventions

PatternMeaning
sf-rust-<topic> Single command plugin — sf-rust topic
sf-rust-<topic>-<verb> Verb is handled internally by the plugin binary

Avoid names that shadow built-ins (sf-rust-org, sf-rust-data, etc.). Those names are always handled internally and external dispatch is never attempted.

Security

PropertyBehaviour
What is executed Only executables already on your PATH, marked executable by the OS
Auto-download None — sf-rust never downloads or installs anything automatically
Discovery Read-only directory listing; no network requests
Credentials Plugins do not receive credentials; they call sf-rust commands which manage auth
Trust boundary Trust your PATH — if you add a directory to PATH, executables in it can be invoked as plugins
Review plugins before adding their directory to PATH, just as you would for any executable. sf-rust does not sandbox, sign-check, or restrict what a plugin can do.

Git-style external dispatch  ✓ Live

Any sf-rust-* executable on PATH becomes a subcommand. sf-rust plugin list discovers all installed plugins. Works today — no update required.

2

Manifest-based discovery  Planned

Plugins ship a plugin.toml that declares their commands and flags. sf-rust reads this at startup so plugins appear in sf-rust --help with descriptions, and tab-completion works for plugin subcommands. Adds sf-rust plugin install / plugin remove. 

# plugin.toml
name        = "soql-repl"
version     = "1.0.0"
description = "Interactive SOQL REPL backed by sf-rust"

[[commands]]
name        = "soql-repl"
description = "Start an interactive SOQL session"

  [[commands.args]]
  name     = "--org"
  short    = "-o"
  required = true
3 daysLOE
3

Wasm plugin sandbox  Roadmap

Plugins compiled to .wasm (any language targeting wasm32-wasi) run inside a wasmtime sandbox. They call back into sf-rust via a small set of host functions (sf_query, sf_org_info, sf_print). No PATH, no shell, no filesystem access beyond what sf-rust explicitly grants. 

// Rust wasm plugin example
use sf_plugin_sdk::prelude::*;

#[no_mangle]
pub extern "C" fn run() -> i32 {
    let org  = arg(0).unwrap_or("default");
    let json = sf_query(org, "SELECT Id, Name FROM Account LIMIT 5");
    sf_print(&json);
    0
}
cargo build --target wasm32-wasi --release
sf-rust plugin install target/wasm32-wasi/release/sf-rust-myplugin.wasm
sf-rust myplugin
2 weeksLOE

Compatibility guarantee

Phase 1 (external binary) plugins will continue to work unchanged through Phase 2 and 3. The wire protocol — exec + args — is stable. Only new capabilities are added, nothing is removed or renamed.
