Quick-start workflow
# 1. Register environments
sf-rust devops env create -n dev     -o dev1   --branch develop
sf-rust devops env create -n staging -o stage1 --branch main
sf-rust devops env create -n prod    -o prod1  --branch release

# 2. Create a pipeline
sf-rust devops pipeline create --name main --stages dev,staging,prod

# 3. Define gates
sf-rust devops gate add --name coverage-80      --type coverage  --threshold 80
sf-rust devops gate add --name no-soql-in-loop  --type lint      --pattern "for\s*\(.*\).*query" --include cls
sf-rust devops gate add --name manual-prod      --type manual    --prompt "QA signed off? [y/N]"

# 4. Assign gates to pipeline transitions (edit ~/.sf-rust/devops.toml)
#    [pipelines.main.gates]
#    "dev-to-staging" = ["coverage-80", "no-soql-in-loop"]
#    "staging-to-prod" = ["manual-prod"]

# 5. Deploy to dev (single-hop)
sf-rust devops deploy run -e dev -d force-app

# 6. Promote dev → prod through the pipeline (runs gates per hop)
sf-rust devops pipeline run --name main --from dev --to prod -d force-app

# 7. View history + rollback if needed
sf-rust devops history list -e prod --viz
sf-rust devops rollback list -e prod
sf-rust devops rollback run  -e prod --to d-20261112-091500-0Af00005
Gate types
lint live

Walks source files with walkdir, scans each line with a regex pattern. Default mode fails when the pattern is found (violation detection). --must-match flips it: fail when pattern is not found (required pattern enforcement).

manual live

Reads a y/n answer from stdin at deploy time. Configure a custom prompt with --prompt. Ideal for prod sign-off gates that require human confirmation.

apex-tests advisory

Triggers all Apex tests in the target org. Advisory pass in the current release — run sf-rust apex test run manually while the org-API integration is finalized.

coverage advisory

Verifies code coverage is at or above --threshold (1–100%). Advisory pass in the current release — full support arrives with the apex-test API integration.

Rollback strategy

Every successful deploy records its git SHA in ~/.sf-rust/deploy-history.ndjson. Rollback uses git worktree add --detach <tmp> <sha> to check out that exact state and re-deploy it. The worktree is always cleaned up, even on failure. 

# List candidates
sf-rust devops rollback list -e prod

# Dry run first
sf-rust devops rollback run \
  -e prod --to d-20261109-... \
  --dry-run

# Validate before deploying
sf-rust devops rollback run \
  -e prod --to d-20261109-... \
  --check-only

Rollback guards

  • Record must exist in history
  • Record must belong to the target --env
  • Must have a recorded git SHA
  • Must be a non-check-only deploy
  • Must have result = "Succeeded"
devops.toml structure
# ~/.sf-rust/devops.toml

[environments.dev]
org_alias   = "dev1"
branch      = "develop"
last_deploy = "d-20261112-091500-0Af00005"

[pipelines.main]
stages = ["dev", "staging", "prod"]

[pipelines.main.gates]
"dev-to-staging"  = ["coverage-80", "no-soql-in-loop"]
"staging-to-prod" = ["manual-prod"]

[gates.coverage-80]
type      = "coverage"
threshold = 80

[gates.no-soql-in-loop]
type        = "lint"
description = "No SOQL inside loops"
pattern     = "for\\s*\\(.*\\).*query"
include     = "cls"

[gates.manual-prod]
type   = "manual"
prompt = "Has QA signed off on this release? [y/N]"

Managed by sf-rust devops commands. Staged paths are also stored in this file under [staged.<env>]. Deploy history lives in a separate append-only NDJSON file: ~/.sf-rust/deploy-history.ndjson
