sf-rust metadata

Deploy, validate, retrieve, and inspect Salesforce metadata from a single native binary. No Node.js, no npm, no Metadata API SDK required.

SOAP Metadata API Deploy + Validate Retrieve & unpack zip Comfy-table component list No Node.js JSON output

Command overview

All metadata subcommands at a glance. validate was added in v0.2.0 and runs a check-only deploy so you can confirm correctness before touching a production org. list was upgraded to a formatted Unicode table in v0.2.0.

metadata list Table of all deployed components of a given type
metadata describe Enumerate all available metadata types in the org
metadata deploy Package a source directory as zip and deploy via SOAP
metadata validate ✦ Validate-only deploy — no changes committed to org
metadata retrieve Retrieve components and unpack the returned zip
metadata delete Build a destructive-changes manifest and deploy it

✦ New in v0.2.0.

ℹ

Transport: All metadata commands use the SOAP Metadata API (/services/Soap/m/{version}). Deploy and retrieve operations build / unpack a zip file in memory — no sfdx-project.json or scratch-org toolchain required.

metadata list

Retrieve the list of deployed components of a given metadata type and render them as a Unicode table (Name · Type · Last Modified · Created · ID). Upgraded to comfy_table in v0.2.0; previously plain text output.

FlagShortDescription
--metadata-type <TYPE>-mSalesforce metadata type, e.g. ApexClass, CustomObject, Flow.
--target-org <ALIAS>-oOrg alias or username. Defaults to the configured default org.
--json-jReturn result as JSON array of component objects.

Examples

# List all Apex classes
sf-rust metadata list -m ApexClass -o dev1

# List custom objects
sf-rust metadata list -m CustomObject -o dev1

# List flows as JSON and pipe to jq
sf-rust metadata list -m Flow -o dev1 --json \
  | jq '[.result[] | select(.fullName | startswith("Order"))]'

# Count how many Apex triggers exist
sf-rust metadata list -m ApexTrigger -o dev1 --json \
  | jq 'length'

metadata describe

Call the Metadata API describeMetadata() SOAP operation to retrieve all metadata types available in your org. Use this to discover valid type names for --metadata-type in metadata list and metadata retrieve.

FlagShortDescription
--target-org <ALIAS>-oOrg alias or username. Defaults to the configured default org.
--json-jReturn result as JSON object.

Examples

# Show all metadata types
sf-rust metadata describe -o dev1

# Output as JSON for scripting
sf-rust metadata describe -o dev1 --json

metadata deploy

Package a Salesforce source directory (or an explicit package.xml manifest) as a zip file and deploy it to the target org via the SOAP Metadata API. A progress spinner shows component counts as the deployment runs; the command polls until done or the wait timeout expires.

FlagShortDescription
--source-dir <DIR>-dSource directory containing metadata to deploy. Defaults to current directory (.).
--manifest <FILE>-xPath to package.xml manifest (alternative to -d).
--target-org <ALIAS>-oOrg alias or username. Defaults to the configured default org.
--test-level <LEVEL>Test level: NoTestRun, RunLocalTests, RunAllTestsInOrg, RunSpecifiedTests. Default: NoTestRun.
--tests <CLASS>-tTest class names (repeatable). Required when --test-level RunSpecifiedTests.
--wait <MINUTES>-wPolling timeout in minutes. Default: 33.
--json-jOutput deploy result as JSON.

Examples

# Deploy a force-app directory
sf-rust metadata deploy -d force-app -o dev1

# Deploy with local tests
sf-rust metadata deploy -d force-app -o staging \
  --test-level RunLocalTests

# Deploy with specific test classes
sf-rust metadata deploy -d force-app -o staging \
  --test-level RunSpecifiedTests \
  -t AccountServiceTest -t ContactControllerTest

# Deploy and capture result as JSON
sf-rust metadata deploy -d force-app -o dev1 --json

# Deploy from a package.xml manifest
sf-rust metadata deploy -x manifest/package.xml -o dev1

# Increase wait to 60 minutes for large deployments
sf-rust metadata deploy -d force-app -o prod \
  --test-level RunLocalTests --wait 60

⚠

Production deployments require at least 75% code coverage (Salesforce platform rule). Use --test-level RunLocalTests or RunAllTestsInOrg for production. Run metadata validate first to catch failures before they affect the org.

metadata validate NEW in v0.2.0

Run a check-only deploy (checkOnly=true in the SOAP envelope) to validate that your source directory would deploy successfully — without committing any changes to the org. Identical flags to metadata deploy; internally delegates to the same deploy path with check_only: true.

Use this as a CI gate: validate on every pull request, deploy only on merge to main. A --test-level RunLocalTests validate run on a sandbox gives you full pre-flight coverage before touching production.

FlagShortDescription
--source-dir <DIR>-dSource directory to validate. Defaults to ..
--manifest <FILE>-xPath to package.xml manifest.
--target-org <ALIAS>-oOrg alias or username. Defaults to the configured default org.
--test-level <LEVEL>Test level for the validation run. Defaults to NoTestRun.
--tests <CLASS>-tTest classes when using RunSpecifiedTests.
--wait <MINUTES>-wPolling timeout in minutes. Default: 33.
--json-jOutput validation result as JSON.

Examples

# Validate a source directory (no changes deployed)
sf-rust metadata validate -d force-app -o dev1

# Validate with local tests — typical CI gate
sf-rust metadata validate -d force-app -o staging \
  --test-level RunLocalTests

# Validate against production before deploying
sf-rust metadata validate -d force-app -o prod \
  --test-level RunLocalTests --wait 60

# Validate and exit non-zero on failure (for CI pipelines)
sf-rust metadata validate -d force-app -o dev1 --json \
  | jq '.result.success'

Validate vs Deploy

metadata validate → checkOnly=true → no org state changes, returns deploy ID metadata deploy → checkOnly=false → commits changes on success
💡

CI/CD pattern: Use metadata validate --test-level RunLocalTests on PRs and metadata deploy --test-level RunLocalTests on merge to main. A passing validate guarantees the deploy will succeed (same code path, same test run).

metadata retrieve

Retrieve one or more metadata components from the org and unpack the returned zip into a local directory. Accepts either a list of Type:Name pairs via -m or an explicit package.xml manifest via -x.

FlagShortDescription
--metadata <Type:Name>-mComponent to retrieve (repeatable). Format: ApexClass:AccountService.
--manifest <FILE>-xPath to package.xml manifest (alternative to -m).
--target-dir <DIR>-dOutput directory. Default: ./retrieve_output.
--api-version <VER>-aOverride API version (e.g. 62.0). Defaults to org's max version.
--target-org <ALIAS>-oOrg alias or username.
--json-jOutput result as JSON.

Examples

# Retrieve a single Apex class
sf-rust metadata retrieve -m ApexClass:AccountService -o dev1

# Retrieve multiple components into a custom directory
sf-rust metadata retrieve \
  -m ApexClass:AccountService \
  -m ApexClass:ContactController \
  -m CustomObject:Order__c \
  -d ./retrieved-metadata -o dev1

# Retrieve using an existing package.xml
sf-rust metadata retrieve -x manifest/package.xml \
  -d ./force-app -o dev1

# Retrieve with explicit API version
sf-rust metadata retrieve -m Flow:Order_Approval -o dev1 -a 62.0
ℹ

How it works: sf-rust builds a package.xml from your -m flags, POSTs a SOAP retrieve() call, polls checkRetrieveStatus() every 5 seconds, then base64-decodes and unzips the returned payload into --target-dir. No temporary files on disk during the transfer.

metadata delete

Delete metadata components from the org by deploying a destructiveChanges.xml manifest (Salesforce's mechanism for removing metadata via the Metadata API). This command builds the manifest from the -m component list and deploys it.

FlagShortDescription
--metadata <Type:Name>-mComponent to delete (repeatable). Format: ApexClass:OldUtils.
--target-org <ALIAS>-oOrg alias or username.
--json-jOutput result as JSON.

Examples

# Delete an obsolete Apex class
sf-rust metadata delete -m ApexClass:OldUtils -o dev1

# Delete multiple components in one operation
sf-rust metadata delete \
  -m ApexClass:LegacyHelper \
  -m ApexTrigger:ObsoleteTrigger \
  -o dev1
⚠

Destructive changes are permanent. Deleted metadata cannot be recovered from the Metadata API. Use metadata retrieve to back up components before deleting them. Always test on a sandbox first.

Quick examples

Common workflows across the entire metadata command suite.

Full deploy pipeline

# 1. Validate on staging with tests
sf-rust metadata validate -d force-app -o staging \
  --test-level RunLocalTests

# 2. If validate passes, deploy to production
sf-rust metadata deploy -d force-app -o prod \
  --test-level RunLocalTests

Discover and inspect

# See all metadata types supported by your org
sf-rust metadata describe -o dev1

# List all Permission Sets as a table
sf-rust metadata list -m PermissionSet -o dev1

# Extract Permission Set names as a text list
sf-rust metadata list -m PermissionSet -o dev1 --json \
  | jq -r '.result[].fullName'

# Count LWC bundles
sf-rust metadata list -m LightningComponentBundle -o dev1 --json \
  | jq 'length'

Targeted retrieve and diff

# Retrieve one class to review changes
sf-rust metadata retrieve \
  -m ApexClass:AccountService \
  -d /tmp/before -o prod

# Diff against local working copy
diff /tmp/before/classes/AccountService.cls \
     force-app/main/default/classes/AccountService.cls
