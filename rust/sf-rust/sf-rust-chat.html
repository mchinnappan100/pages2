sf-rust chat opens a direct TCP connection between two machines. Phase 2 added a ratatui split-screen TUI and AES-256-GCM encryption. Phase 3 makes the server a multi-party hub — it accepts up to --max-peers N simultaneous connections and fan-outs every message to all connected peers.

🖥️
chat serve v2
Binds a TCP port, waits for one peer. Full TUI on connection. Add --secret to encrypt.
🔌
chat connect v2
Connects to the serving machine. TUI starts immediately. Add --secret with the same passphrase.
🔒
AES-256-GCM Phase 2
Pass --secret passphrase on all sides. Key = SHA-256(passphrase). Each message encrypted with a fresh nonce. Server relays the raw encrypted wire line — no re-encryption.
👥
Multi-party Phase 3
Server accepts up to --max-peers N (default 8) simultaneous TCP connections. Every incoming message is fanned-out to all other peers. Server itself participates as a peer — types in the TUI, messages broadcast to all.

Split-screen TUI Phase 2

Phase 2 replaces the raw terminal with a ratatui split-screen. Incoming messages no longer interrupt your typing.

How to use

Plain (no encryption)

# Machine A — listen sf-rust chat serve sf-rust chat serve --port 9000 --name mohan-mbp # Machine B — connect sf-rust chat connect 192.168.1.5:7878 sf-rust chat connect 192.168.1.5:7878 --name sarojan-mini

Encrypted (AES-256-GCM) Phase 2

# both sides must pass the same --secret passphrase # Machine A sf-rust chat serve --secret "my-team-secret" # Machine B sf-rust chat connect 192.168.1.5:7878 --secret "my-team-secret"
The TUI shows [AES-256-GCM] in the title bar when encryption is active. If the passphrases don't match, a decryption-failed warning appears in the message pane.

Multi-party chat Phase 3

The server now acts as a hub. All peers connect to the same chat serve instance. Every message from any peer is fan-outed to all others — including the server operator. The server's title bar shows peers: N/max live.

# Machine A — start the hub (server + participant) sf-rust chat serve --max-peers 4 --name mohan-hub # Machine B — connect sf-rust chat connect 192.168.1.5:7878 --name alice # Machine C — connect sf-rust chat connect 192.168.1.5:7878 --name bob # All three can now chat together # Server title bar: "peers: 2/4"
The server operator types in their own TUI just like any other peer. Their messages are broadcast to all connected clients. When a peer joins or leaves, a system message appears in the server's TUI.
Peer limit: attempting to connect beyond --max-peers shows a "Rejected" system message on the server and the client's connection is dropped immediately. The default limit is 8.

Multi-party with encryption

# Server and ALL clients must pass the same --secret sf-rust chat serve --max-peers 4 --secret "team-pass" sf-rust chat connect 192.168.1.5:7878 --secret "team-pass" sf-rust chat connect 192.168.1.5:7878 --secret "team-pass" # Server relays the raw AES-256-GCM wire line — no re-encryption needed

Same machine (testing)

# Terminal 1: sf-rust chat serve --name alice # Terminal 2: sf-rust chat connect 127.0.0.1:7878 --name bob

Encryption

DetailValue
AlgorithmAES-256-GCM (authenticated encryption)
Key derivationSHA-256(passphrase) → 32-byte key
NonceRandom 96-bit, generated fresh per message via OsRng
Wire formathex(nonce):hex(ciphertext)\n (plaintext is the JSON payload)
Mismatch detectionDecryption failure shows a warning in the TUI message pane
No-secret fallbackRaw JSON — V1 wire-compatible
Key derivation is SHA-256, not PBKDF2. This is intentional for V2 speed on a LAN. For a hostile network, use Tailscale/WireGuard VPN in addition to --secret.

sf-rust chat connect 100.64.x.x:7878 --secret "passphrase"

History log

Pass --history on either or both sides. Messages are appended to ~/.sf-rust/chat_history.log:

# log format (one line per message): [2026-11-14 14:32:09] mohan@MacBook-Pro: hello from the MacBook! [2026-11-14 14:32:11] sarojan@mac-mini: hi! can you hear me? # view recent history tail -50 ~/.sf-rust/chat_history.log # search history sf-rust grep "deploying" ~/.sf-rust/chat_history.log
