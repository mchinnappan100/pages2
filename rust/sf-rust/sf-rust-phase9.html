Phase 9 — Advanced Dev Tooling

Seven new commands that close the gap between sf-rust and a full Salesforce developer workbench: interactive coverage heat-maps, cross-org SOQL diff, schema code generation, named environment profiles, regex metadata search, Change Data Capture subscriptions, and enriched SObject describe with record types.

apex coverage --report data describe --record-types data diff data schema-gen env add/list/switch/remove metadata search --pattern notify cdc

1 · apex coverage --report

Fetches Apex code-coverage data from the org and opens a self-contained dark-mode HTML heat-map in the browser. Each class gets a color-coded bar (green ≥ 75 %, yellow 50–74 %, red < 50 %) plus stat cards for total lines, covered lines, and overall coverage percentage. Filter chips let you narrow by threshold, and an inline search finds classes by name.

Usage

sf-rust apex coverage -o <org>
sf-rust apex coverage -o <org> --report           # open HTML heat-map in browser
sf-rust apex coverage -o <org> --report --json     # print JSON + open report
sf-rust apex coverage -o <org> --datatable         # AG-Grid datatable view

Flags

FlagDefaultDescription
-o / --target-orgdefault orgOrg alias or username
--reportoffGenerate and open HTML heat-map
--jsonoffOutput raw JSON records to stdout
--datatableoffOpen AG-Grid datatable view

Sample output — heat-map cards

┌─────────────────────────────────────────────┐ │ Apex Coverage Report · dev1 │ │ 87 classes · overall 74.3 % covered │ │ │ │ ● AccountService 92 % ████████▉ │ │ ● OpportunityHelper 78 % ███████▊ │ │ ▲ LeadProcessor 61 % ██████▏ │ │ ✕ InvoiceGenerator 42 % ████▏ │ └─────────────────────────────────────────────┘
The HTML report is written to /tmp/sf-rust-coverage-{ts}.html and opened automatically with open. Dark mode follows prefers-color-scheme; a manual toggle is persisted in localStorage.

2 · data describe --record-types

Extends data describe with an extra table showing all active and inactive Record Types for the queried SObject — Id, Name, DeveloperName, Active, and Description — fetched via a SOQL query on the RecordType object.

Usage

sf-rust data describe Account -o dev1
sf-rust data describe Account -o dev1 --record-types
sf-rust data describe Opportunity -o dev1 --record-types --datatable

Flags

FlagDefaultDescription
-o / --target-orgdefault orgOrg alias or username
--record-typesoffAppend Record Types table after field list
--datatableoffOpen AG-Grid datatable view
--jsonoffOutput raw describe JSON

3 · data diff

Compares the results of the same SOQL query run against two orgs (or two different queries against the same org). Records are matched by a key field (--key, default Id). The diff output classifies each record as ADDED, REMOVED, or CHANGED, showing only the fields that differ in CHANGED rows.

Usage

# Compare Account records between two orgs
sf-rust data diff \
  -q "SELECT Id, Name, Industry FROM Account ORDER BY Name" \
  --source dev1 --target staging1

# Use Name as the matching key instead of Id
sf-rust data diff \
  -q "SELECT Name, AnnualRevenue, Industry FROM Account ORDER BY Name" \
  --source dev1 --target staging1 --key Name

# Open visual diff in browser
sf-rust data diff \
  -q "SELECT Id, Name, Stage FROM Opportunity" \
  --source dev1 --target staging1 --datatable

Flags

FlagDefaultDescription
-q / --queryrequiredSOQL query to run against both orgs
--source / -srequiredSource org alias
--target / -trequiredTarget org alias
--keyIdField to use as the record identifier for matching
--datatableoffOpen visual diff in browser datatable
--jsonoffOutput diff results as JSON

Sample output

── data diff · dev1 → staging1 ────────────────────────────────────────── Source records: 142 Target records: 139 ADDED (in target only): 3 REMOVED (from source): 6 CHANGED: 12 Identical: 121 ╔════════╤══════════════════════╤═══════════╤══════════════════════╗ ║ Status │ Id │ Field │ dev1 → staging1 ║ ╠════════╪══════════════════════╪═══════════╪══════════════════════╣ ║ ADDED │ 001Xx000003GhNpIAK │ — │ — ║ ║ REMOVED│ 001Xx000003GhNqIAK │ — │ — ║ ║ CHANGED│ 001Xx000003GhNrIAK │ Industry │ Technology → Finance ║ ╚════════╧══════════════════════╧═══════════╧══════════════════════╝
Both orgs must be authenticated. The query runs against each independently, so network latency doubles. Use --key Name for objects where Id differs between orgs (sandbox refreshes re-assign Ids for some record types).

4 · data schema-gen

Calls the Salesforce Describe API for a given SObject and generates a typed schema in your language of choice — Rust structs, TypeScript interfaces, or JSON Schema (Draft 7). The output can be written directly to a file with --out.

Usage

# Print TypeScript interface to stdout
sf-rust data schema-gen Account -o dev1 --lang typescript

# Write Rust struct to a file
sf-rust data schema-gen Opportunity -o dev1 --lang rust --out src/models/opportunity.rs

# Generate JSON Schema Draft 7
sf-rust data schema-gen Contact -o dev1 --lang json-schema --out schemas/contact.json

Flags

FlagDefaultDescription
sobjectrequiredSObject API name (e.g. Account)
-o / --target-orgdefault orgOrg alias or username
--langtypescriptOutput language: rust | typescript | json-schema
--outstdoutWrite output to this file path

TypeScript output sample

export interface Account {
  Id?: string;
  Name: string;
  AnnualRevenue?: number | null;
  Industry?: string | null;
  OwnerId: string;
  // ... all fields from describe
}

Rust output sample

#[derive(Debug, Serialize, Deserialize)]
pub struct Account {
    pub id: Option<String>,
    pub name: String,
    pub annual_revenue: Option<f64>,
    pub industry: Option<String>,
}

5 · env — Named Environment Profiles

Manage named environment profiles stored in ~/.sf-rust/envs.toml. Each profile maps a name (e.g. dev, staging, prod) to a default org alias. env switch updates the active default org in ~/.sf-rust/config.toml so all subsequent commands use that org without needing -o.

Usage

# List all profiles
sf-rust env list

# Add a named profile
sf-rust env add dev --org developer-sandbox
sf-rust env add staging --org staging-sandbox
sf-rust env add prod --org production-org

# Switch the active default org to a profile
sf-rust env switch staging

# Remove a profile
sf-rust env remove dev

Subcommands

SubcommandDescription
listPrint all profiles with org aliases and active indicator
add <name> --org <alias>Create or overwrite a named profile
switch <name>Set profile's org as the default org in config.toml
remove <name>Delete a profile from envs.toml

Sample output — env list

╔═══════════╤══════════════════════╤══════════╗ ║ Profile │ Org │ Active ║ ╠═══════════╪══════════════════════╪══════════╣ ║ dev │ developer-sandbox │ ║ ║ staging │ staging-sandbox │ ● active ║ ║ prod │ production-org │ ║ ╚═══════════╧══════════════════════╧══════════╝
Profiles are stored in ~/.sf-rust/envs.toml. env switch writes the new default to ~/.sf-rust/config.toml — the same file used by all other sf-rust commands to look up the default org.

6 · metadata search --pattern

Uses the Tooling API to fetch Apex class and trigger bodies from the org and applies a regex search line-by-line. Results show the class name, line number, and matched line — similar to grep -n but running directly against org metadata without a local checkout.

Usage

# Search all Apex classes for Database.query calls
sf-rust metadata search --pattern 'Database\.query' -o dev1

# Case-insensitive search across classes and triggers
sf-rust metadata search --pattern 'without sharing' -o dev1 --ignore-case

# Limit to ApexTrigger only
sf-rust metadata search --pattern 'trigger.*Account' -o dev1 --type trigger

# Output as JSON
sf-rust metadata search --pattern 'SOQL_query' -o dev1 --json

Flags

FlagDefaultDescription
--pattern / -prequiredRegex pattern to search for
-o / --target-orgdefault orgOrg alias or username
--typebothclass | trigger | both
--ignore-case / -ioffCase-insensitive matching
--jsonoffOutput matches as JSON array
--datatableoffOpen results in browser datatable

Sample output

Searching 247 ApexClass, 18 ApexTrigger for /Database\.query/ AccountService.cls:42: List<Account> accs = Database.query(soql); LeadProcessor.cls:118: return Database.query(buildQuery()); OpportunityHelper.cls:77: results = Database.query(dynamicSOQL); AccountTrigger.trigger:23: Database.query(q); 4 matches in 247 classes + 18 triggers (1.24s)
This queries the Tooling API endpoint (/services/data/vXX.0/tooling/query). Large orgs with hundreds of classes may take several seconds as the full class bodies must be fetched. The regex engine is Rust's regex crate — PCRE backreferences are not supported.

7 · notify cdc

Subscribes to Salesforce Change Data Capture (CDC) events for any standard or custom SObject using the CometD long-polling protocol. Each change event (create, update, delete, undelete) is printed as pretty-printed JSON as it arrives. Use --count N to capture a fixed number of events and exit.

Usage

# Subscribe to Account CDC events (Ctrl-C to stop)
sf-rust notify cdc Account -o dev1

# Stop after 5 events
sf-rust notify cdc Contact -o dev1 --count 5

# Replay from all retained events
sf-rust notify cdc Opportunity -o dev1 --replay-id -2

# Custom SObject
sf-rust notify cdc My_Object__c -o dev1

Flags

FlagDefaultDescription
sobjectrequiredSObject API name (e.g. Account, Contact, My_Object__c)
-o / --target-orgdefault orgOrg alias or username
--replay-id-1-1 = new events only; -2 = all retained events
--count0 (unlimited)Stop after N events (0 = run until Ctrl-C)

CDC channel naming

The CometD channel is /data/{SObject}ChangeEvent. For standard objects use the API name directly: Account → /data/AccountChangeEvent. For custom objects include the __c suffix: My_Object__c → /data/My_Object__cChangeEvent.

Sample event output
