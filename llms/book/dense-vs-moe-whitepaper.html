Overview

Large Language Models (LLMs) have transformed natural language processing over the past decade. As these models scale from billions to trillions of parameters, the question of how to activate and utilise those parameters efficiently becomes critical — both for cost and sustainability.

Two fundamentally different philosophies have emerged:

📦

Dense Models

Every parameter is activated for every token. Maximum knowledge, maximum compute.

⚡

MoE / Sparse Models

Only the relevant subset of parameters ("experts") activates per token. Efficient and scalable.

📚 The Backpack Analogy

The best way to understand the difference is through a simple school-day analogy:

Dense Model

Like a student who carries every single book in their backpack every day — Math, Science, History, Art, PE — regardless of what classes are scheduled. The backpack is heavy, access is slow, but everything is always available.

MoE / Sparse Model

Like a student who checks the day's timetable each morning and only packs the books they need — Math and Science on Monday, History and Art on Tuesday. The backpack is light, fast, and efficient.

Dense Models — Deep Dive

In a dense Transformer, every forward pass activates all parameters. A 70B dense model like LLaMA-3 processes every token through all 70 billion weights. This gives highly coherent, predictable behaviour but at significant compute cost.

Dense Transformer — Forward Pass

Examples

  • GPT-4 (estimated)
  • LLaMA 3 70B/405B
  • Mistral 7B
  • Falcon 180B

Strengths

  • Simple architecture
  • Stable training
  • Predictable latency
  • Easy to fine-tune

Weaknesses

  • High compute per token
  • Expensive to scale
  • Memory bandwidth bound
  • Energy intensive

Mixture of Experts (MoE)

MoE replaces the monolithic Feed-Forward Network (FFN) inside each Transformer layer with a set of N expert sub-networks. A lightweight router (gating network) reads each token and dynamically selects only the top-K experts to process it — typically K=1 or K=2 out of 8–64 experts.

The result: a model with many more total parameters than an equivalent dense model, but the same (or fewer) active parameters per token.

MoE Layer — Expert Routing

Key insight: Mixtral 8×7B has ~47B total parameters but only ~13B active per token — delivering near-70B quality at 13B inference cost.

Examples

  • Mixtral 8×7B / 8×22B
  • Gemini 1.5 Pro (MoE)
  • DeepSeek-V2/V3
  • Switch Transformer

Strengths

  • High capacity, low FLOPs
  • Specialised experts
  • Scales to trillions
  • Efficient inference

Challenges

  • Load balancing experts
  • Complex training
  • High memory footprint
  • Expert collapse risk

Sparse Models — Beyond MoE

Sparsity is a broader concept. While MoE applies sparsity at the expert level, other forms of sparsity operate at the attention, weight, or activation level:

Sparse Attention

Instead of every token attending to every other token (O(n²)), sparse attention restricts each token to a local window or learned pattern. Used in Longformer, BigBird, Flash-Attn variants.

Weight Pruning / Sparsity

After training, weights below a threshold are zeroed out. The resulting sparse weight matrices can be stored and multiplied more efficiently using hardware-aware sparse kernels (e.g., NVIDIA cuSPARSE).

Activation Sparsity

ReLU naturally produces zero activations; models can be trained to have high activation sparsity (70–95%), enabling conditional compute skipping. Relevant in models like Mamba and state-space alternatives.

Structured Sparsity

Removes entire blocks, heads, or layers rather than individual weights. More hardware-friendly than unstructured pruning. Used extensively in mobile and edge deployments.

Trade-offs in Practice

Decision Flow — Which Architecture?

Memory vs Compute Trade-off

MoE models require all experts to be loaded into memory (or distributed across GPUs) even though only K are active per token. A Mixtral 8×7B needs ~90GB of GPU memory, compared to ~35GB for a comparable dense 20B model.

Load Balancing

Without regularisation, all tokens gravitate toward the same popular experts — known as expert collapse. Auxiliary load-balancing losses (e.g., Switch Transformer's auxiliary loss) force even distribution across experts during training.

When to Use Each

📦

Dense Models

  • Single-GPU deployments
  • Fine-tuning for custom domains
  • Low-latency, predictable serving
  • Research / experimentation
  • Edge & mobile (small dense)
⚡

MoE Models

  • Multi-GPU / cluster serving
  • High-throughput inference
  • General-purpose frontier models
  • When quality > memory cost
  • Long-context applications
✂️

Sparse/Pruned

  • Post-training compression
  • Model distillation pipelines
  • Hardware-constrained devices
  • Quantisation + sparsity combos
  • Inference optimisation

Future Outlook

The field is rapidly converging on hybrid architectures — models that combine dense self-attention layers with MoE feed-forward layers, or that use structured sparsity at the hardware level.

Trend: Fine-grained MoE

DeepSeek-V3 uses 256 fine-grained experts per layer, selecting top-8. This dramatically increases routing granularity and specialisation without proportionally increasing compute.

Trend: Hardware-native Sparsity

NVIDIA H100 / H200 supports 2:4 structured sparsity natively in Tensor Cores — 2 non-zero values in every 4. This doubles throughput with zero software overhead.

Trend: Sparse + Quantised

Combining 4-bit quantisation with 50–70% weight sparsity is becoming standard practice for edge deployment, yielding 8–16× model size reduction with minimal quality loss.

Trend: Conditional Compute

Next-generation architectures (e.g., state-space models, Mamba, Griffin) offer sub-quadratic attention alternatives that are inherently sparse in their recurrent computation.
