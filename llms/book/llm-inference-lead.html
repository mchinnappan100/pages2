Role Guide

LLM Inference Lead

The LLM Inference Lead owns the end-to-end serving of language models in production — from the moment a request arrives to the moment the last token reaches the user. This role sits at the intersection of ML engineering, systems engineering, and platform reliability.

📅

Daily

Monitor health, triage alerts, keep SLOs green, unblock the on-call rotation.

🗓

Weekly

Review KPIs, ship optimisations, drive capacity planning, sync with ML & platform teams.

📆

Monthly

Architecture reviews, cost audits, model upgrades, roadmap alignment, post-mortems.

🥖 The Bakery Analogy

The easiest way to explain the difference between Training and Inference is through a bakery:

🔥 Training = Running the Bakery

Mixing ingredients (data), running the oven (GPUs) for a long time, perfecting the recipe (architecture). Happens once (or rarely). Produces the model weights — the baked loaves stored on disk.

🚐 Inference = Delivering Fresh Bread

Loading the pre-baked loaves (weights) into a delivery van (inference server) and driving them to customers (users) on demand — fresh, fast, and reliably, thousands of times per day.

📅 Daily Work

What the Inference Lead does every working day.

Daily Routine Flow

Morning (First Hour)

  • ▸ Review Grafana / Datadog inference dashboards
  • ▸ Check overnight alerts — TTFT spikes, error rates, GPU OOM
  • ▸ Skim on-call handoff notes
  • ▸ Check queue depth and pending request backlog

Core Hours

  • ▸ Investigate latency regressions or throughput drops
  • ▸ Tune batching configs, KV-cache, or memory settings
  • ▸ Review PRs for inference stack changes
  • ▸ Coordinate with SRE on GPU health & provisioning

Afternoon

  • ▸ Benchmark experiments (e.g. vLLM vs TensorRT-LLM)
  • ▸ Unblock team members — PR reviews, architecture questions
  • ▸ Update runbooks for new failure modes found

End of Day

  • ▸ Write on-call handoff summary
  • ▸ Log daily SLO status (p50/p99 TTFT, throughput, error %)
  • ▸ Flag capacity risks for tomorrow

🗓 Weekly Work

Recurring weekly rituals and deliverables.

Weekly Cadence

Capacity Planning

  • Forecast next week's request volume
  • Check GPU reservation vs utilisation gap
  • Trigger autoscaling rule adjustments
  • Coordinate spot vs on-demand GPU strategy

Performance Optimisation

  • Ship one perf improvement per week
  • Tune batch size, concurrency, KV cache
  • Evaluate speculative decoding configs
  • Profile CUDA kernels on regression

📆 Monthly Work

Strategic and architectural work done on a monthly cadence.

🏗

Architecture Review

Evaluate new serving frameworks (vLLM, TRT-LLM, Triton, SGLang). Assess whether to migrate or integrate. Produce ADR (Architecture Decision Record).

💰

Cost Audit

Break down GPU cost per 1M tokens served. Identify top 3 cost drivers. Set reduction target for next quarter. Present to engineering and finance leadership.

🔁

Model Upgrade Cycle

Evaluate new model checkpoints or quantised versions. Shadow traffic testing. Staged rollout (1% → 10% → 100%). Rollback plan documented.

📝

Post-Mortem & Roadmap

Consolidate all incidents into a trends report. Update the inference roadmap. Align with product on upcoming traffic growth expectations.

🧪

Hardware Evaluation

Benchmark new GPU SKUs (H200, B200, MI300X) for cost/perf. Engage cloud vendor reps for reserved instance pricing. Write buy vs rent recommendation.

📣

Stakeholder Report

Monthly inference health digest to CTO / VPs: availability %, latency trend, cost efficiency, upcoming risks, and mitigation plans.

⏱ First Token — TTFT & Beyond

TTFT (Time to First Token) is the most user-perceived latency metric. It measures the wall-clock time from request receipt to when the first output token starts streaming.

Request Lifecycle — The Full Journey

TTFT Killers

  • Long prompt → slow prefill
  • Request queuing (GPU busy)
  • KV cache eviction under memory pressure
  • Cold start / model loading delay
  • Network round-trip to load balancer

TTFT Improvers

  • Prefix / system-prompt KV caching
  • Chunked prefill (interleave with decode)
  • FlashAttention-2/3 for long contexts
  • Keep GPU warm — avoid cold starts
  • Edge deployment to reduce network RTT

🚨 On-Call & Incident Response

The Inference Lead sets the standard for on-call excellence. Common incidents and their playbooks:

🔴 GPU OOM (Out of Memory)

  1. Check KV cache utilisation
  2. Reduce max_model_len or batch size
  3. Enable chunked prefill
  4. Restart with lower memory fraction

🟠 TTFT Spike (>2s p99)

  1. Check queue depth — scale out if >100
  2. Look for long-prompt abuse → rate limit
  3. Verify KV cache eviction rate
  4. Check for noisy-neighbour GPU contention

🟡 Throughput Drop (>20%)

  1. Compare batch size distribution vs baseline
  2. Check for model version rollback side effect
  3. Profile CUDA kernels for regression
  4. Verify continuous batching config intact

🔵 GPU Node Failure

  1. Auto-drain triggers via k8s health check
  2. Confirm replacement node comes up
  3. Validate model loaded correctly (checksum)
  4. File cloud vendor hardware ticket
