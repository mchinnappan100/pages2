Chapter 01

Why Custom CUDA in PyTorch?

PyTorch's built-in ops cover most use cases. But for novel architectures, fused kernels, or squeezing the last 30% of GPU utilization out of a model, you need to go lower. This chapter explains exactly where the boundary is and why it matters.

The framework ceiling

Every PyTorch operator dispatches to a pre-written CUDA kernel. These kernels are well-optimized for common shapes and dtypes. But they cannot know your access pattern, your fusion opportunity, or your numeric precision trade-off — you do.

Memory round-trips

Chaining standard ops like x = torch.relu(x + bias) launches two kernels, each reading from and writing to HBM. A single fused kernel does the same work in one pass — cutting HBM traffic in half for elementwise chains.

Novel operations

Research operations — rotary embeddings, custom attention masks, sparse patterns, quantized dot products — often have no PyTorch built-in. Writing them in CUDA gives you correctness, gradient support, and the ability to torch.compile them.

FRAMEWORK LAYER

What PyTorch gives you

  • Tensor abstraction with shape, dtype, device
  • Automatic differentiation (autograd)
  • ~2000 built-in operators (aten)
  • torch.compile + Triton code generation
  • Distributed training primitives

CUDA LAYER (you write this)

What custom kernels add

  • Operation fusion across multiple aten ops
  • Novel numeric patterns not in aten
  • Shared-memory tiling for custom access patterns
  • Warp-level intrinsics and tensor core fragments
  • Zero-copy in-place ops with custom strides
The path from "I wrote a new attention variant" to "it runs at peak hardware utilization" goes through custom CUDA — and PyTorch's extension system makes that path shorter than it used to be.

Chapter 02

Environment & Project Setup

A working CUDA/PyTorch development environment requires matching the CUDA toolkit version to the PyTorch build, configuring the C++ compiler, and choosing between JIT loading and ahead-of-time compilation. Getting this right once saves hours of pain later.

CUDA Toolkit

Install the CUDA Toolkit version that matches your PyTorch build (torch.version.cuda). Mismatches cause silent runtime failures. Use nvcc --version to confirm the active compiler.

PyTorch C++ headers

Installing PyTorch via pip or conda includes the C++ headers under torch.utils.cpp_extension.include_paths(). No separate libtorch download is needed for extensions.

JIT vs AOT build

JIT (load()) compiles at first import — convenient for development. AOT (setup.py) builds a wheel — required for production and conda packaging.

Compiler flags

Pass -O3 --use_fast_math to nvcc for production. Use -G for device-side debugging. -arch=sm_80 (or -gencode) must match your target GPU compute capability.

CMake alternative

For large projects, CMake with find_package(Torch REQUIRED) gives finer control over targets, linking, and multi-file compilation than CppExtension.

Version pinning

Pin torch==X.Y.Z+cuNNN in requirements. PyTorch's ABI changes between minor versions — an extension compiled against 2.3 will crash when loaded under 2.4.

PYTHON — JIT EXTENSION LOAD (DEVELOPMENT)

from torch.utils.cpp_extension import load

my_ext = load(
    name="my_ext",
    sources=["my_op.cpp", "my_op_kernel.cu"],
    extra_cuda_cflags=["-O3", "--use_fast_math"],
    verbose=True,   # print nvcc command for debugging
)

# First call compiles and caches under ~/.cache/torch_extensions/
# Subsequent imports reuse the cached .so unless sources change
result = my_ext.my_forward(x, y)

PYTHON — setup.py (AHEAD-OF-TIME / WHEEL BUILD)

from setuptools import setup
from torch.utils.cpp_extension import BuildExtension, CUDAExtension

setup(
    name="my_ext",
    ext_modules=[
        CUDAExtension(
            name="my_ext",
            sources=["my_op.cpp", "my_op_kernel.cu"],
            extra_compile_args={
                "cxx":  ["-O3"],
                "nvcc": ["-O3", "--use_fast_math",
                          "-gencode=arch=compute_80,code=sm_80"],
            },
        )
    ],
    cmdclass={"build_ext": BuildExtension},
)
# pip install -e .   →  builds and installs in editable mode

Chapter 03

Your First CUDA Kernel

A CUDA kernel is a C++ function decorated with __global__ that runs on the GPU. In PyTorch extensions, kernels receive raw pointers extracted from torch::Tensor objects. This chapter walks through a complete element-wise example end to end.

The minimal PyTorch CUDA extension has three files: a .cu file containing the CUDA kernel and a thin C++ launcher, a .cpp file exposing the launcher to Python via pybind11 (or TORCH_LIBRARY), and a Python file that loads the extension and wraps it in a Tensor-friendly API.

The key bridge is tensor.data_ptr<float>() — it extracts the raw device pointer from a PyTorch tensor, which you then pass to the kernel. Responsibility for correct shape and contiguity lies with you.

CUDA C++ — relu_kernel.cu

// relu_kernel.cu
#include <cuda_runtime.h>
#include <torch/extension.h>

// One thread per element. Each thread reads, applies ReLU, writes.
__global__ void relu_kernel(const float* __restrict__ x,
                             float* __restrict__ out,
                             int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N) {
        out[i] = x[i] > 0.f ? x[i] : 0.f;
    }
}

// C++ launcher: called from Python via pybind11
torch::Tensor relu_cuda(torch::Tensor x) {
    TORCH_CHECK(x.is_cuda(),   "x must be a CUDA tensor");
    TORCH_CHECK(x.is_contiguous(), "x must be contiguous");

    auto out = torch::empty_like(x);
    int N = x.numel();
    const int threads = 256;
    const int blocks  = (N + threads - 1) / threads;

    relu_kernel<<<blocks, threads>>>(
        x.data_ptr<float>(),
        out.data_ptr<float>(),
        N
    );
    // Errors surface on next synchronization point
    return out;
}

C++ — relu_op.cpp (pybind11 binding)

// relu_op.cpp
#include <torch/extension.h>

torch::Tensor relu_cuda(torch::Tensor x);  // declared in .cu

PYBIND11_MODULE(TORCH_EXTENSION_NAME, m) {
    m.def("relu", &relu_cuda, "Custom ReLU (CUDA)");
}

PYTHON — usage

import torch
from torch.utils.cpp_extension import load

ext = load(name="relu_ext", sources=["relu_op.cpp", "relu_kernel.cu"])

x = torch.randn(1_000_000, device="cuda")
out = ext.relu(x)

# Verify against PyTorch reference
assert torch.allclose(out, torch.relu(x)), "Mismatch!"
print("Custom ReLU matches reference.")
Always verify your kernel against a PyTorch reference before benchmarking. A kernel that is fast but wrong is worse than slow and correct.

Chapter 04

Memory & Data Layout

PyTorch tensors carry a stride alongside their shape. A kernel that ignores strides and reads memory sequentially will silently produce wrong results for transposed or sliced tensors. This chapter covers the memory model and three critical optimization patterns.

ConceptWhat it meansWhy it matters
Contiguous tensorElements stored in row-major C order with no gapsdata_ptr gives a clean pointer; kernels can use i directly as the memory offset
Non-contiguous tensorResult of transpose, slice, expand — strides may be non-unit or zeroMust either .contiguous() first or index by stride in the kernel
Memory coalescingAdjacent threads access adjacent memory addressesHardware can service 32 accesses in one transaction instead of 32 separate ones
Shared memory tilingThreads cooperatively load a block of data on-chip before computingReuse each byte T times before evicting; reduces HBM traffic by factor T
__restrict__C99 hint: this pointer does not alias any other in the kernelLets the compiler emit better vectorized load/store instructions

CUDA C++ — STRIDE-AWARE KERNEL

// Handle non-contiguous input via PackedTensorAccessor
__global__ void scale_kernel(
    torch::PackedTensorAccessor32<float,2,torch::RestrictPtrTraits> x,
    torch::PackedTensorAccessor32<float,2,torch::RestrictPtrTraits> out,
    float scale
) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < x.size(0) && col < x.size(1)) {
        out[row][col] = x[row][col] * scale;  // accessor handles strides
    }
}

torch::Tensor scale_cuda(torch::Tensor x, float s) {
    auto out = torch::empty_like(x);
    dim3 threads(16, 16);
    dim3 blocks((x.size(1)+15)/16, (x.size(0)+15)/16);
    scale_kernel<<<blocks, threads>>>(
        x.packed_accessor32<float,2,torch::RestrictPtrTraits>(),
        out.packed_accessor32<float,2,torch::RestrictPtrTraits>(),
        s);
    return out;
}

Coalesced access (fast)

Thread 0 reads index 0, thread 1 reads index 1, …, thread 31 reads index 31. The hardware issues a single 128-byte transaction to serve the entire warp. Throughput approaches the theoretical HBM bandwidth limit.

Strided access (slow)

Thread 0 reads index 0, thread 1 reads index 32 (column-major transpose). Each thread's access touches a different cache line. The warp requires 32 separate transactions instead of 1 — 32× the HBM traffic for the same data volume.

PYTHON — CONTIGUITY CHECK PATTERN

def my_op(x: torch.Tensor) -> torch.Tensor:
    # Make contiguous only if necessary (avoids a redundant copy)
    x = x.contiguous() if not x.is_contiguous() else x
    return my_ext.forward(x)

# Transposed input works correctly without changing the kernel
x = torch.randn(512, 768, device="cuda").T   # non-contiguous
out = my_op(x)   # .contiguous() called internally

Chapter 05

Custom C++/CUDA Extensions

Real extensions handle multiple dtypes, check tensor shapes, support batching, and expose a clean Python API. This chapter covers the patterns that make an extension production-worthy: AT_DISPATCH_FLOATING_TYPES, argument validation, and the TORCH_LIBRARY operator registration system.

CUDA C++ — MULTI-DTYPE DISPATCH PATTERN

// AT_DISPATCH_FLOATING_TYPES selects the right scalar_t at runtime
torch::Tensor gelu_cuda(torch::Tensor x) {
    TORCH_CHECK(x.is_cuda());
    TORCH_CHECK(x.scalar_type() == torch::kFloat ||
                x.scalar_type() == torch::kHalf,
                "gelu_cuda: expected float or half tensor");

    auto out = torch::empty_like(x);
    int N = x.numel();

    AT_DISPATCH_FLOATING_TYPES_AND_HALF(x.scalar_type(), "gelu_cuda", [&]() {
        int threads = 256;
        int blocks  = (N + threads - 1) / threads;
        gelu_kernel<<<blocks, threads>>>(
            x.data_ptr<scalar_t>(),
            out.data_ptr<scalar_t>(),
            N);
    });
    return out;
}

CUDA C++ — GELU KERNEL (float & half)

template <typename scalar_t>
__global__ void gelu_kernel(const scalar_t* __restrict__ x,
                             scalar_t* __restrict__ out, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N) {
        float v = static_cast<float>(x[i]);
        // GELU ≈ 0.5·x·(1 + tanh(√(2/π)·(x + 0.044715·x³)))
        const float c = 0.7978845608f;  // sqrt(2/pi)
        float tanh_arg = c * (v + 0.044715f * v * v * v);
        out[i] = static_cast<scalar_t>(0.5f * v * (1.f + tanhf(tanh_arg)));
    }
}

C++ — TORCH_LIBRARY REGISTRATION (modern API)

// Registers op in the aten namespace — works with torch.compile
TORCH_LIBRARY(my_ops, m) {
    m.def("gelu(Tensor x) -> Tensor");
}

TORCH_LIBRARY_IMPL(my_ops, CUDA, m) {
    m.impl("gelu", &gelu_cuda);
}

// Python: torch.ops.my_ops.gelu(x)
AT_DISPATCH_FLOATING_TYPES is the idiomatic way to write a single C++ function that dispatches to typed kernels. Use it from the start — retrofitting dtype support is painful.

Chapter 06

Autograd Integration

A forward CUDA kernel without a backward pass is useful only for inference. PyTorch's torch.autograd.Function lets you attach a custom CUDA backward to any forward, so that .backward() calls your hand-written gradient kernel instead of autodiff.

The forward method receives input tensors, runs your CUDA kernel, saves any tensors needed for the backward, and returns outputs. The backward method receives grad_output (the upstream gradient) and must return a gradient tensor for every input that required a gradient — returning None for non-differentiable inputs.

PYTHON — torch.autograd.Function WRAPPER

import torch

class GeluFunction(torch.autograd.Function):

    @staticmethod
    def forward(ctx, x: torch.Tensor) -> torch.Tensor:
        out = my_ext.gelu_forward(x)   # calls CUDA kernel
        ctx.save_for_backward(x)       # save input for grad computation
        return out

    @staticmethod
    def backward(ctx, grad_out: torch.Tensor) -> torch.Tensor:
        (x,) = ctx.saved_tensors
        grad_x = my_ext.gelu_backward(grad_out, x)  # CUDA backward kernel
        return grad_x  # one grad per forward input

# Convenience wrapper
def fast_gelu(x: torch.Tensor) -> torch.Tensor:
    return GeluFunction.apply(x)

CUDA C++ — GELU BACKWARD KERNEL

template <typename scalar_t>
__global__ void gelu_backward_kernel(
    const scalar_t* __restrict__ grad_out,
    const scalar_t* __restrict__ x,
    scalar_t* __restrict__ grad_x,
    int N)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N) {
        float v  = static_cast<float>(x[i]);
        float go = static_cast<float>(grad_out[i]);
        const float c = 0.7978845608f;
        float tanh_arg = c * (v + 0.044715f * v * v * v);
        float t   = tanhf(tanh_arg);
        float sech2 = 1.f - t * t;
        float dgelu = 0.5f * (1.f + t)
                    + 0.5f * v * sech2 * c * (1.f + 3.f * 0.044715f * v * v);
        grad_x[i] = static_cast<scalar_t>(go * dgelu);
    }
}

Gradient checking

Always run torch.autograd.gradcheck(fast_gelu, inputs, eps=1e-3) with float64 inputs. gradcheck numerically estimates the Jacobian and compares it to your analytic backward. Failures here mean a bug in your gradient formula, not just a performance problem.

Saved tensor memory

Every tensor stored with save_for_backward stays alive until .backward() is called. For activation functions on large activations this can double peak memory. Consider recomputation (gradient checkpointing) for memory-critical training.

Chapter 07

Triton: Python-Level Kernels

Writing CUDA C++ is powerful but verbose. Triton lets you write GPU kernels in Python-like syntax, handling warp scheduling, vectorization, and memory coalescing automatically. It is the recommended path for most custom PyTorch ops in 2024 and is built into torch.compile.

Programming model

You write at the tile level: "load a block of BLOCK_SIZE elements, compute on them, store them back." Triton figures out the warp layout. You never write threadIdx or blockDim.

Auto-tuning

@triton.autotune + @triton.heuristics let you declare a search space of configs (block sizes, number of warps, pipeline stages) and Triton benchmarks them and caches the winner per problem shape.

torch.compile integration

Triton kernels decorated with @triton.jit are first-class citizens inside torch.compile. The compiler can fuse Triton kernels with adjacent aten ops in the same graph pass.

PYTHON — TRITON SOFTMAX KERNEL

import triton
import triton.language as tl
import torch

@triton.jit
def softmax_kernel(
    X_ptr, Out_ptr,
    stride_row,           # bytes between rows
    N: tl.constexpr,      # number of columns (compile-time constant)
    BLOCK: tl.constexpr,  # tile size (power of 2)
):
    row = tl.program_id(0)              # one program per row
    cols = tl.arange(0, BLOCK)
    mask = cols < N

    # Load row tile from HBM
    x = tl.load(X_ptr + row * stride_row + cols, mask=mask, other=-float("inf"))

    # Numerically stable softmax: subtract max first
    x = x - tl.max(x, axis=0)
    x = tl.exp(x)
    x = x / tl.sum(x, axis=0)

    tl.store(Out_ptr + row * stride_row + cols, x, mask=mask)


def triton_softmax(x: torch.Tensor) -> torch.Tensor:
    rows, cols = x.shape
    out = torch.empty_like(x)
    BLOCK = triton.next_power_of_2(cols)
    softmax_kernel[(rows,)](
        x, out,
        stride_row=x.stride(0),
        N=cols,
        BLOCK=BLOCK,
        num_warps=4 if BLOCK <= 2048 else 8,
    )
    return out

Chapter 08

Profiling & Benchmarking

You cannot optimize what you cannot measure. This chapter covers GPU-side timing with CUDA Events, high-level traces with PyTorch Profiler, and deep kernel analysis with Nsight Compute — applied to the kernels you wrote in previous chapters.

CUDA Events (microsecond precision)

Place start.record() and end.record() directly in the CUDA stream. Call end.synchronize() before start.elapsed_time(end). This is the only accurate way to time a GPU kernel — CPU timers measure async launch latency, not execution time.

Warm-up iterations

Always run 10–50 warm-up iterations before timing. Cold runs include kernel compilation, cache warming, and driver overhead. Warm runs reflect the steady-state performance your users will experience.

PyTorch Profiler

torch.profiler.profile captures a timeline of CPU and GPU activity. The tensorboard_trace_handler writes a Chrome trace you can view at chrome://tracing or in TensorBoard — invaluable for finding CPU-GPU sync stalls.

Nsight Compute (ncu)

The deepest profiler: occupancy, warp stall reasons, HBM bandwidth, arithmetic throughput, L2 hit rate, and a roofline chart per kernel. Run ncu --set full python train.py to capture everything, then open the report in the GUI.

Bandwidth vs compute

Calculate measured bandwidth as bytes / time; compare to HBM peak (e.g. 2 TB/s on A100 HBM2e). Calculate TFLOP/s as ops / time; compare to peak (e.g. 312 TF32 TFLOP/s). The gap tells you which ceiling you are hitting.

Microbenchmark discipline

Vary one parameter at a time. Use the same input tensors. Repeat at least 100 iterations and report median, not mean (outliers from driver preemption skew means). Use torch.cuda.reset_peak_memory_stats() between runs if measuring memory.

PYTHON — FULL BENCHMARK HARNESS

import torch

def benchmark(fn, *args, warmup=25, repeats=200):
    # Warm-up: compile kernels, warm caches
    for _ in range(warmup):
        fn(*args)
    torch.cuda.synchronize()

    start = torch.cuda.Event(enable_timing=True)
    end   = torch.cuda.Event(enable_timing=True)
    times = []

    for _ in range(repeats):
        start.record()
        fn(*args)
        end.record()
        torch.cuda.synchronize()
        times.append(start.elapsed_time(end))  # ms

    times.sort()
    median_ms = times[len(times) // 2]
    return median_ms

# Example: compare custom GELU vs torch.nn.functional.gelu
x = torch.randn(4096, 4096, device="cuda", dtype=torch.float16)

t_ref  = benchmark(torch.nn.functional.gelu, x)
t_fast = benchmark(fast_gelu, x)

bytes_rw = 2 * x.numel() * x.element_size()  # read + write
bw_ref   = bytes_rw / (t_ref  * 1e-3) / 1e12
bw_fast  = bytes_rw / (t_fast * 1e-3) / 1e12

print(f"Reference: {t_ref:.3f} ms  ({bw_ref:.2f} TB/s)")
print(f"Custom:    {t_fast:.3f} ms  ({bw_fast:.2f} TB/s)")

Chapter 09

Multi-GPU & CUDA Streams

Single-GPU kernels saturate one device. CUDA streams enable overlap of computation and data transfer. Device guards let a single Python process control multiple GPUs. And PyTorch's distributed primitives scale custom ops to hundreds of GPUs without rewriting the kernel.

CUDA Streams

A CUDA stream is an ordered queue of operations on one GPU. Operations in different streams can run concurrently if the hardware has capacity. Use streams to overlap a kernel on one batch with a data transfer for the next batch — hiding PCIe latency behind computation.

Device Guards

torch.cuda.device(n) or c10::DeviceGuard in C++ sets the active device for the duration of a block. Always guard before allocating or launching on a specific GPU — without a guard, torch.cuda.current_device() determines where memory lands.

PYTHON — STREAM-BASED PIPELINE (COMPUTE ↔ TRANSFER OVERLAP)

import torch

compute_stream  = torch.cuda.Stream()
transfer_stream = torch.cuda.Stream()

for i, batch in enumerate(dataloader):
    # Transfer next batch on the transfer stream (non-blocking)
    with torch.cuda.stream(transfer_stream):
        batch_gpu = batch.to("cuda", non_blocking=True)

    # Wait for transfer to finish before computing
    compute_stream.wait_stream(transfer_stream)

    with torch.cuda.stream(compute_stream):
        out = model(batch_gpu)
        loss = criterion(out, labels_gpu)
        loss.backward()
        optimizer.step()
        optimizer.zero_grad()

torch.cuda.synchronize()   # wait for all streams before exiting

PYTHON — MULTI-GPU WITH DistributedDataParallel

import os
import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

def setup(rank, world_size):
    os.environ["MASTER_ADDR"] = "localhost"
    os.environ["MASTER_PORT"] = "12355"
    dist.init_process_group("nccl", rank=rank, world_size=world_size)

def train(rank, world_size):
    setup(rank, world_size)
    torch.cuda.set_device(rank)

    model = MyModel().cuda(rank)
    # DDP wraps the model; forward/backward are unchanged
    model = DDP(model, device_ids=[rank])

    # Custom CUDA ops registered via TORCH_LIBRARY work transparently
    # with DDP — gradients are all-reduced automatically
    optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4)
    for batch in dataloader:
        out  = model(batch["x"].cuda(rank))
        loss = out.sum()
        loss.backward()
        optimizer.step(); optimizer.zero_grad()

    dist.destroy_process_group()

Chapter 10

Packaging & Production

A kernel that works in your Jupyter notebook needs to become a versioned, installable wheel that builds on CI, plays nicely with torch.compile, handles multiple CUDA architectures, and degrades gracefully when a GPU is absent. This chapter closes the loop from research code to shipped software.

01

Multi-arch compilation. Use -gencode arch=compute_XY,code=sm_XY for every architecture you need to support. For a public package, target sm_70 (Volta), sm_80 (Ampere), sm_89 (Ada), and sm_90 (Hopper). PTX fallback (code=compute_90) handles future chips.

02

CPU fallback. Always provide a CPU implementation. Wrap both in a dispatcher: if x.is_cuda(): return cuda_impl(x) else: return cpu_impl(x). This lets tests run on CPU-only CI machines and helps users without a GPU.

03

torch.compile compatibility. Register ops with TORCH_LIBRARY and provide an abstract (meta) function via torch.library.impl_abstract that computes output shapes and dtypes without executing. Without this, torch.compile will skip or break at your op.

04

Version pinning and ABI. Your extension must be recompiled for each major PyTorch version. Pin the PyTorch ABI tag in your wheel name (cp311-cp311-linux_x86_64). CI should build against the same PyTorch version as your target environment.

05

Testing pyramid. Unit-test correctness with torch.allclose. Test gradients with torch.autograd.gradcheck. Benchmark with your harness from Chapter 8. Smoke-test on CPU. Run the full suite in CI on every push.

06

Documentation and type stubs. Export type stubs (.pyi files) so IDEs see your op's signature. Document expected tensor shapes, dtypes, and device constraints in the docstring. Future you — and your colleagues — will be grateful.

PYTHON — torch.library ABSTRACT FUNCTION (torch.compile support)

import torch
from torch.library import Library, impl, impl_abstract

lib = Library("my_ops", "DEF")
lib.define("gelu(Tensor x) -> Tensor")

@impl(lib, "gelu", "CUDA")
def gelu_cuda_impl(x):
    return my_ext.gelu(x)

@impl(lib, "gelu", "CPU")
def gelu_cpu_impl(x):
    return torch.nn.functional.gelu(x)   # fallback

# Abstract implementation: returns a tensor with the same shape/dtype
# torch.compile calls this during graph tracing (no actual compute)
@impl_abstract("my_ops::gelu")
def gelu_abstract(x):
    return torch.empty_like(x)

PYTHON — setup.py PRODUCTION WHEEL

from setuptools import setup, find_packages
from torch.utils.cpp_extension import BuildExtension, CUDAExtension
import torch

# Target all common modern CUDA architectures
ARCHS = ["70", "80", "89", "90"]
gencode = []
for arch in ARCHS:
    gencode += [f"-gencode=arch=compute_{arch},code=sm_{arch}"]
gencode += ["-gencode=arch=compute_90,code=compute_90"]  # PTX fallback

setup(
    name="my_cuda_ops",
    version="0.1.0",
    packages=find_packages(),
    ext_modules=[CUDAExtension(
        "my_cuda_ops._C",
        sources=["csrc/ops.cpp", "csrc/gelu_kernel.cu"],
        extra_compile_args={
            "cxx":  ["-O3", "-std=c++17"],
            "nvcc": ["-O3", "--use_fast_math"] + gencode,
        },
    )],
    cmdclass={"build_ext": BuildExtension},
)
