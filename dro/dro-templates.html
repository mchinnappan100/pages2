03 / Components

Technical Component Details

Each template tier addresses a distinct layer of the order-to-activate lifecycle.

🔀

1. Decomposition Templates

Pre-defined rules governing how commercial Order Line Items break down into technical Fulfillment Order Line Items.

  • Scope controls: 1:1 and 1:N instance generation
  • Conditional execution based on product attributes
  • Configurable split logic for bundles
See Example YAML 
decomposition_template:
  name: "digital-service-seat-decompose"
  trigger_product_family: "SaaS"
  split_by: "seat_count"
  target_foli_type: "DigitalProvisioningItem"
  conditions:
    - field: "order_type"
      operator: "equals"
      value: "NEW"
🏗️

2. Reusable Orchestration Step Groups

Standardized fulfillment building blocks for common integration and provisioning patterns.

  • Pre-configured step sequences with dependency mapping
  • Drag-and-drop assembly for new fulfillment plans
  • Parallel and sequential execution branch support
See Example Patterns
Common step groups: Billing System Sync, Third-Party Provisioning, Asset Creation, Entitlement Assignment
🗺️

3. Attribute & Field Mapping Rules

Standardized transformation templates to pass data from high-level order items to detailed technical items.

  • Direct field propagation rules
  • Value transformation lookup tables
  • Calculated fields and default value injection
See Mapping Example
Maps Order.ShippingPostalCode → technical NetworkNode.PostcodeID via a lookup table of regional node assignments.
🚨

4. Jeopardy & Fallout Management Templates

Automated monitoring and remediation policies for order fallout.

  • Jeopardy Thresholds: Visual alerts when steps exceed SLAs
  • Fallout Workflows: Auto-retry, queue routing, task creation
  • Escalation Paths: Multi-tier escalation with notifications
See SLA Example
SLA threshold expressed in ISO 8601: PT4H (4-hour window). Triggers jeopardy alert, auto-retry ×3, then routes to manual operations queue.

  4. Test in a sandbox — validate decomposition, orchestration steps, and jeopardy triggers.
  5. Publish improvements back: dro-cli template publish --from ./my-template.yaml
Appendix

YAML Template Conventions

Conventions that ensure portability, discoverability, and DRY composition across the template library.

📄

File Naming

  • Extension: .dro.yaml
  • Names: lowercase, hyphen-separated, version suffix
  • Example: digital-service-activation-v2.dro.yaml
🏷️

Required Metadata

  • Every template must include a metadata block
  • Required fields: name, version, author, tags
  • Semantic versioning: MAJOR.MINOR.PATCH
♻️

DRY Composition

  • Step group references use $ref notation
  • Shared lookup tables extracted to _shared/
  • Avoid copy-paste between templates
⏱️

SLA Duration Format

  • Use ISO 8601 duration strings
  • PT4H → 4 hours
  • P1DT2H → 1 day, 2 hours
