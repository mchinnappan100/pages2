Context

Where the "70% of the internet" number comes from

01
📊

The statistic is real…

PHP powers roughly 77% of all websites whose server-side language is known (W3Techs, 2026). WordPress alone accounts for ~43% of all websites globally — and WordPress runs on PHP.

⚠️

…but the risk is nuanced

The vast majority of those 77% run shared-hosting stacks where PHP-FPM is already isolated per-user, or managed platforms (WP.com, WP Engine) that patched within hours of disclosure.

🚨

Who is actually at highest risk

Self-hosted servers running mod_php inside Apache with no memory caps, old PHP 8.1 (EOL — no patch ever), and sites that cannot update because a theme or plugin has a hard version dependency.

✅

Who is already protected

Managed WordPress platforms, Cloudflare Workers, containerised PHP-FPM with cgroup memory limits, and any installation running 8.2.35 / 8.3.36 / 8.4.27 / 8.5.12 or later.

A PHP-FPM worker is a long-running process that handles many requests sequentially. Between requests, the Zend Engine resets its internal state — but only partially. Both CVEs exploit windows where that reset is incomplete or interrupted.

mod_php inside Apache (highest-risk configuration)

Browser
→
Apache + mod_php
PHP runs in-process
→
App code

With mod_php, PHP shares the Apache worker's memory space directly. There is no process isolation between requests. An exploit that corrupts the PHP heap can affect the entire Apache worker — and a demonstrated exploit for CVE-2026-109618 triggers before any application code runs.

🔄

Worker reuse model

PHP workers are expensive to spin up, so they are reused across thousands of requests. This is a performance win — but it means any state that leaks between requests (global variables, internal structs) persists until the worker is recycled.

🧠

Zend memory arena

PHP uses a custom memory allocator (Zend MM). Per-request memory is allocated from an arena and bulk-freed at request end. If PHP is killed mid-cleanup (OOM), that arena may hold partially-initialized structs that the next cleanup pass treats as valid.

🌐

Global vs. request scope

PHP distinguishes "persistent" (process-lifetime) allocations from per-request ones. The stale-state bug (CVE-2026-109619) arises when a pointer to a freed per-request object is stored in a persistent (global) slot and read by the next request's init phase.

⚡

Pre-application attack surface

Both bugs are triggered during PHP's own request setup — before index.php loads. No WAF rule, no application firewall, and no PHP-level input sanitisation can stop them. The only defence is the C-level fix in the PHP binary itself.

CVE Details

The two critical vulnerabilities

03
CVE-2026-109618
RCE via Out-of-Memory Corruption
CVSS 9.2 · CRITICAL

Root cause

PHP's Zend Engine initialises internal request data structures in multiple stages. If the OS kills the process mid-initialisation (triggered by hitting memory_limit), some structures are only partially built.

When PHP then runs its cleanup phase, it iterates those structures assuming they are complete. Treating a half-built struct as valid leads to a type confusion on the heap — which an attacker can groom into arbitrary code execution.

Attack surface

  • Attacker sends a crafted POST body large enough to trigger the OOM condition
  • Works unauthenticated — no application code needs to run
  • Highest risk with mod_php (demonstrated public exploit)
  • PHP-FPM is also affected but process isolation limits blast radius

CVE-2026-109619
RCE via Stale Global State After Request Teardown
CVSS 9.2 · CRITICAL

Root cause

PHP stores a pointer to a per-request internal object in a global (persistent) slot during session upload-progress tracking. If the request ends abnormally (fatal error, execution timeout), the teardown path skips resetting that slot.

The next request begins, reads the stale pointer — which now points to freed memory in the heap — before normal initialisation has a chance to overwrite it. On a worker that receives attacker-controlled allocation patterns, this becomes a use-after-free → RCE.

Attack surface

  • Requires session.upload_progress.enabled=On (default in many distros)
  • Attacker must be able to send two sequential requests to the same worker
  • Also triggered by attacker-reachable fatal errors and execution timeouts
  • Affects PHP-FPM, mod_php, FrankenPHP, LiteSpeed, and php-cgi

Mitigations

What to do — and what won't save you

05

⚠️ The PHP Security Team's official position: "There are no complete mitigations. Updating is the only safe choice."

The partial workarounds below reduce attack surface but do not close the vulnerabilities. Use them only as a temporary bridge while you prepare the upgrade.

CVE-2026-109618 — Reduce OOM exposure

Set a generous memory limit so requests fail gracefully rather than mid-init:

memory_limit = -1

Or cap inbound body size to reduce the attack surface:

post_max_size = 8M

Use OS-level cgroup memory limits on containers rather than PHP's own limit.

CVE-2026-109619 — Disable session upload progress

This is the primary attack trigger. Disable it in php.ini and restart all workers:

session.upload_progress.enabled = 0

On PHP 8.5 only, also set:

fatal_error_backtraces = 0

Audit your app for any attacker-reachable code paths that cause fatal errors or timeouts.

PHP-FPM: restart workers regularly

Force worker recycling to limit how long stale state can persist:

pm.max_requests = 500

Pair with a low request_terminate_timeout so hung workers are killed promptly.

What does NOT help

❌ WAF rules — the exploit fires before app code loads

❌ Application-level input validation — same reason

❌ disable_functions — no user function is called

❌ open_basedir — filesystem restrictions, not memory safety

❌ Updating WordPress / plugins — the bug is in the PHP binary itself

Tooling

Automated vulnerability checker

06

php-vuln-check.js — Node.js CLI (zero dependencies)

# check local PHP binary
node php-vuln-check.js

# check a single site via HTTP response headers
node php-vuln-check.js --url https://example.com

# bulk-check a list of URLs (one per line)
node php-vuln-check.js --file hosts.txt

# JSON output — pipe into monitoring or alerting
node php-vuln-check.js --file hosts.txt --json

# exit code 1 if any host is vulnerable or EOL
# exit code 0 if all hosts are patched

The checker reads the X-Powered-By and Server HTTP response headers to detect exposed PHP versions. Servers that suppress those headers are reported as HEADER_HIDDEN — which is good practice but requires a direct local check. Source: scripts/php-vuln-check.js in this repo.
