Level 01

Overview

Salesforce guidance: Create one Salesforce user for every integration so each calling system has its own data/functionality scope and audit trail. Avoid sharing a single integration user across multiple unrelated integrations.
🔌

What is an Integration User?

An integration user is a dedicated Salesforce user account created exclusively for API-based access by an external system. It holds no interactive UI access and operates under the principle of least privilege.

  • API-only — no Salesforce UI access permitted
  • One user per calling system or integration domain
  • Uses the Salesforce Integration user license
  • Profile: Minimum Access - API Only Integrations
  • Additional access granted via permission sets / permission set groups
▶ See Example User Naming Convention 
INT_Billing        → billing-system integration
INT_ERP            → ERP integration
INT_DataWarehouse  → data warehouse sync
INT_Agent          → AI agent / external service

Username format:
  int.billing@company.com
  int.erp@company.com.dev      ← sandbox suffix

Result: every API action is attributable to a specific integration system in the audit log.

🎯

Why One User Per Integration?

Sharing a single integration user across multiple integrations creates a broad security blast radius, pollutes the audit trail, and makes credential rotation risky.

  • Security: a compromised shared user exposes all integrations simultaneously
  • Traceability: logs show which system created or modified each record
  • Auditability: access reviews are per-integration, not per-user union
  • Troubleshooting: errors are scoped to one integration, not a shared pool
  • Rotation: revoking one user's credentials doesn't affect others
▶ See Shared vs Dedicated Comparison 
❌ Shared user (anti-pattern):
   INT_USER
   ├── ERP    (Account, Order, Product)
   ├── Billing (Account, Payment, Invoice)
   └── DW     (Account, CustomObj, ...)
   Compromise = union of ALL permissions

✅ Dedicated users (recommended):
   INT_ERP     → ERP permissions only
   INT_BILLING → Billing permissions only
   INT_DW      → DW permissions only
   Compromise = isolated blast radius

Result: Salesforce cites security, traceability, and auditability as the three reasons for one user per integration.

📋

Audit Trail Advantage

Salesforce Setup Audit Trail and Event Log Files record the username associated with every API action. Dedicated users make those logs immediately actionable.

  • Records show "Created by: INT_ERP" — immediately meaningful
  • Shared users show "Created by: INT_INTEGRATION" — ambiguous
  • Per-integration users enable targeted incident investigation
  • Simplifies SOC 2 / ISO 27001 access reviews
  • Integration-level permission reviews are clean and bounded
▶ See Audit Log Comparison 
❌ Shared user audit log:
   Created by: INT_INTEGRATION
   Created by: INT_INTEGRATION
   Updated by: INT_INTEGRATION
   → Which system did this? Unknown.

✅ Dedicated user audit log:
   Created by: INT_ERP
   Created by: INT_BILLING
   Updated by: INT_DW
   → Instantly attributable, scoped to one system.

Result: meaningful audit logs without any additional tooling.

Level 02

Architecture

🏗️

The Four Boundaries

Salesforce integration architecture separates concerns across four distinct boundaries. Each boundary should be designed and managed independently.

  • Integration boundary = User — one user per integration
  • Authorization boundary = Permission Set / PSG — what the user can access
  • Authentication boundary = External Client App / OAuth — how the user authenticates
  • Profile = Minimum/API-only baseline — shared thin foundation
▶ See Boundary Model 
                Integration User License
                         │
                         ▼
          Minimum Access - API Only (profile)
                         │
           ┌─────────────┼─────────────┐
           ▼             ▼             ▼
       INT_ERP      INT_BILLING      INT_DW
           │             │             │
           ▼             ▼             ▼
      ERP Perm Set  Billing Perm Set  DW Perm Set

Result: one thin profile, many users, each with their own authorization surface.

🗂️

Recommended User Configuration

Each integration user should follow a consistent setup pattern. The profile provides the API-only baseline; permission sets carry all functional access.

  • License: Salesforce Integration
  • Profile: Minimum Access - API Only Integrations
  • 1 permission set (or PSG) per integration — no extra shared permissions
  • MFA exemption permission set assigned (API-only users must be exempt)
  • No UI access, no interactive login
▶ See Setup Checklist per User 
Setup › Users › New User
  License:   Salesforce Integration
  Profile:   Minimum Access - API Only Integrations
  Username:  int.erp@company.com
  Email:     integration-ops@company.com

Permission Sets assigned:
  [ ] ERP_Integration        ← functional access
  [ ] Salesforce_API_Integration (PSL if needed)
  [ ] MFA_Exempt_Integration ← required for API-only

Note: without the MFA exemption permission set, API-only users may be blocked by org-wide MFA enforcement policies.

🌐

Multi-Environment Identity Model

Preserve the same logical integration identity across all environments while keeping credentials and usernames isolated via sandbox suffixes.

  • DEV → int.erp@company.com.dev
  • QA → int.erp@company.com.qa
  • UAT → int.erp@company.com.uat
  • PROD → int.erp@company.com
  • Same permission set structure in each environment — different credentials
▶ See Environment Mapping 
Logical identity: INT_ERP
  DEV:  int.erp@co.com.dev  → DEV OAuth consumer
  QA:   int.erp@co.com.qa   → QA  OAuth consumer
  UAT:  int.erp@co.com.uat  → UAT OAuth consumer
  PROD: int.erp@co.com      → PROD OAuth consumer

Each environment:
  ✅ Same permission set structure
  ✅ Isolated OAuth credentials
  ✅ Independent MFA exemption
  ✅ Separate audit trail

Result: rotate any environment's credentials without affecting the others.

Level 03

License & Profile

Edition restriction: The Salesforce Integration user license is only available in Enterprise, Unlimited, Performance, and Developer editions. It is not available in Professional or Essentials editions. Seats are limited by default — contact your Salesforce Account Executive for add-on licenses.
🪪

Salesforce Integration User License

The Salesforce Integration user license is designed specifically for API-only integrations. It includes the Minimum Access - API Only Integrations profile and the Salesforce API Integration permission set license.

  • Includes: Minimum Access - API Only Integrations profile
  • Includes: Salesforce API Integration permission set license (PSL)
  • Available in: Enterprise, Unlimited, Performance, Developer
  • Not available in: Professional, Essentials
  • Seats limited by default — add-ons available from your AE
▶ See License vs PSL Distinction 
Salesforce Integration (user license)
  └── Grants API-only user account

Salesforce API Integration (permission set license)
  └── Grants System Administrator-level permissions
      for use cases that require elevated access
      (assign as a permission set, not a user license)

Typical setup:
  User License:  Salesforce Integration
  Profile:       Minimum Access - API Only
  PSL assigned:  Only if elevated access is needed
  Custom PS:     ERP_Integration (functional scope)

Caution: assigning the Salesforce API Integration PSL grants near-admin level access. Only use it if the integration genuinely requires it.

🔒

Profile Restriction Behavior

The Minimum Access - API Only Integrations profile enforces API-only access at a level that cannot be overridden. These restrictions apply even on cloned profiles — they are hardcoded into the license tier.

  • Users assigned this profile cannot log into the Salesforce UI
  • API-only restriction cannot be disabled, even on a clone of the profile
  • Replaces the deprecated API Only System Integrations profile
  • Additional permissions must come via permission sets — not profile edits
  • Attempting to grant UI access via the profile will have no effect
▶ See What You Can and Cannot Modify 
Minimum Access - API Only Integrations profile:
  ✅ Can add:    permission sets / PSGs
  ✅ Can modify: custom permission sets assigned to user
  ❌ Cannot:     disable API-only restriction on profile
  ❌ Cannot:     grant UI login via cloned profile
  ❌ Cannot:     turn off individual API restrictions

Correct pattern:
  Profile = thin API-only baseline (never edit)
  Permission Sets = all functional access

Rule: keep the profile untouched; build all access in permission sets.

🔑

Authentication Methods

Integration users authenticate differently depending on the API being used. Choose the appropriate authentication method based on the protocol your integration requires.

  • REST API: create an External Client App and implement OAuth 2.0 flow
  • SOAP API / Bulk API: use the SOAP-specific login() call
  • Client Credentials Flow: server-to-server with no user interaction
  • JWT Bearer Flow: certificate-based, no interactive login required
  • Named Credentials: managed auth for Salesforce-to-external callouts
▶ See Auth Method Selection 
REST API (external → Salesforce):
  → External Client App + OAuth 2.0
  → Client Credentials Flow (server-to-server)
  → JWT Bearer Flow (certificate-based)

SOAP API / Bulk API:
  → SOAP login() call
  → username + password + security token

Salesforce → External (outbound):
  → Named Credentials + External Credentials
  → manages auth lifecycle outside codebase

Tip: OAuth Client Credentials Flow is the modern, recommended method for server-to-server REST integrations.

Level 04

Security Model

Core principle: The integration boundary is the user. The authorization boundary is the permission set. The authentication boundary is the External Client App / OAuth. Keep these concerns cleanly separated.
🛡️

Least Privilege Per Integration

Each integration user should have exactly the access it needs — no more. Sharing profiles across users blurs this boundary; per-user permission sets sharpen it.

  • Avoid creating one large permission set shared across multiple integrations
  • Scope each permission set to objects, fields, and Apex for that integration only
  • Review permission sets quarterly — remove unused access
  • Use permission set groups to bundle related permissions cleanly
  • Never use the System Administrator profile for integration users
▶ See Least Privilege Example 
❌ Anti-pattern (over-privileged):
   INT_SHARED_USER
   └── PS: Integration_All_Access
       ├── Account: CRUD
       ├── Order:   CRUD
       ├── Invoice: CRUD
       ├── Payment: CRUD
       └── 40 more objects...

✅ Correct (scoped):
   INT_ERP → PS: ERP_Integration
     ├── Account: Read, Edit
     ├── Order:   Create, Read, Edit
     └── Product: Read

   INT_BILLING → PS: Billing_Integration
     ├── Account: Read
     ├── Invoice: Create, Read
     └── Payment: Create, Read

Result: INT_ERP cannot touch Invoice or Payment records even if compromised.

🔐

MFA Exemption for API-Only Users

Salesforce org-wide MFA enforcement applies to all users by default. API-only integration users must be explicitly exempted — they cannot complete an MFA challenge during a programmatic login flow.

  • Org-wide MFA enforcement blocks API users without an exemption
  • Assign the Waive Multi-Factor Authentication for Exempt Users permission
  • Create a dedicated "MFA Exempt — Integration" permission set
  • Assign this permission set to all integration users
  • Do not assign the MFA exemption to interactive human users
▶ See MFA Exemption Setup 
Create Permission Set: MFA_Exempt_Integration
  System Permission:
    ✅ Waive Multi-Factor Authentication
       for Exempt Users

Assign to:
  INT_ERP, INT_BILLING, INT_DW, INT_Agent

Do NOT assign to:
  Any human/interactive user accounts

Verify:
  Test API login after MFA enforcement enabled
  Confirm no MFA challenge is presented

Warning: missing this step is the most common cause of integration failures after an org enables mandatory MFA.

💥

Credential Compromise Blast Radius

The isolation model directly limits the damage caused by a compromised integration user. With dedicated users, the attacker inherits only one integration's permissions.

  • Shared user compromise: attacker gets the union of all integrations' access
  • Dedicated user compromise: attacker gets one integration's scoped access only
  • Incident response is faster — revoke one user, one OAuth consumer
  • Other integrations continue operating uninterrupted during investigation
  • Forensic scope is bounded — only one system's logs need examination
▶ See Blast Radius Comparison 
❌ Shared INT_USER compromised:
   Attacker has access to:
   ├── Account (ERP scope)
   ├── Order / Product (ERP scope)
   ├── Invoice / Payment (Billing scope)
   └── CustomObj / DW schema (DW scope)

✅ INT_ERP compromised:
   Attacker has access to:
   └── Account, Order, Product only
   → Billing and DW data: unaffected
   → Revoke INT_ERP only, others keep running

Result: dedicated users contain breach impact to a single integration boundary.

Best Practices

What Great Teams Do

✓ One User Per Integration

Every external system that calls Salesforce APIs gets its own dedicated integration user. Never share one user account across unrelated integrations regardless of how similar their access patterns appear.

❌ INT_SHARED → ERP + Billing + DW
✅ INT_ERP     → ERP only
✅ INT_BILLING → Billing only
✅ INT_DW      → Data warehouse only

✓ Use the Correct License and Profile

Always use the Salesforce Integration user license with the Minimum Access - API Only Integrations profile. Never assign the System Administrator profile to an integration user.

✅ License:  Salesforce Integration
✅ Profile:  Minimum Access - API Only
❌ Profile:  System Administrator
❌ Profile:  Standard User (has UI access)

✓ Build Access in Permission Sets, Not Profiles

The profile is a thin, immutable baseline. All functional access — objects, fields, Apex classes, API permissions — should come through per-integration permission sets or permission set groups.

Profile:  Minimum Access (never edit this)
PS:       ERP_Integration
  ├── Account: Read, Edit
  ├── Order: Create, Read, Edit
  └── Product_Read_API (Apex class)

✓ Assign MFA Exemption to All Integration Users

API-only users cannot complete an MFA challenge. Create a dedicated exemption permission set and assign it to every integration user before org-wide MFA enforcement is enabled.

PS: MFA_Exempt_Integration
  System Perm:
    Waive Multi-Factor Authentication
    for Exempt Users → ✅

Assign to: all INT_* users
Do NOT assign to: human users

✓ Use OAuth Client Credentials for Server-to-Server

For modern REST integrations, use OAuth 2.0 Client Credentials Flow via an External Client App. It removes interactive login from the flow entirely and is Salesforce's currently recommended server-to-server pattern.

External Client App (ECA)
  └── OAuth Client Credentials Flow
       └── INT_ERP user as the "run-as" user
            └── clientCredentialsFlowUser
                 set to int.erp@company.com

✓ Isolate Credentials Per Environment

Each environment (DEV, QA, UAT, PROD) must have its own OAuth consumer credentials. Never copy a client ID or secret from one sandbox to another. Use sandbox username suffixes to keep identities distinct.

DEV:  int.erp@co.com.dev  → DEV OAuth creds
QA:   int.erp@co.com.qa   → QA  OAuth creds
UAT:  int.erp@co.com.uat  → UAT OAuth creds
PROD: int.erp@co.com      → PROD OAuth creds

✓ Store Integration Credentials in a Secret Store

Never store client IDs, secrets, or user passwords in source code, config files committed to Git, or CI/CD pipeline logs. Use an enterprise secret store and inject credentials at runtime.

✅ Vault / AWS Secrets Manager / Azure KV
✅ CI/CD masked secret variables
❌ config.json: { "clientSecret": "..." }
❌ .env files checked into Git
❌ Hardcoded in Apex / integration code

✓ Verify Editions Before Planning Seat Count

The Salesforce Integration license is only available in Enterprise, Unlimited, Performance, and Developer editions. Confirm edition compatibility and available seats before architecture planning, especially in multi-org environments.

✅ Enterprise, Unlimited, Performance,
   Developer — Salesforce Integration license
❌ Professional, Essentials — not available

Default seats: limited
Add-ons: contact your Salesforce AE

✓ Apply Scoped Least-Privilege Permission Sets

Each integration's permission set should contain only the objects, fields, and Apex access that integration genuinely uses. Regularly audit and trim unused access — especially after integration changes.

ERP_Integration PS:
  Account: Read, Edit        ✅
  Order: Create, Read, Edit  ✅
  Invoice: (none)            ← not needed
  Payment: (none)            ← not needed

Quarterly review:
  [ ] Remove fields no longer in use
  [ ] Remove Apex classes no longer called

✓ Keep the Profile Thin — Never Customize It

The Minimum Access - API Only Integrations profile is designed to be a stable, immutable baseline. Its API-only restrictions cannot be disabled even on a clone. Treat it as read-only and put all customization in permission sets.

❌ Clone profile → add permissions
❌ Try to disable API-only restriction
✅ Leave profile as-is
✅ Add all functional access via PS/PSG

✓ Name Users and Permission Sets Consistently

Establish a naming convention for integration users and their permission sets that makes the integration boundary immediately obvious in Setup, audit logs, and access reviews.

Users:
  INT_[System]       e.g. INT_ERP
  int.[sys]@co.com   e.g. int.erp@co.com

Permission Sets:
  [System]_Integration    ERP_Integration
  MFA_Exempt_Integration  (shared)

Permission Set Groups:
  [System]_Integration_PSG

✓ Automate Post-Sandbox-Refresh Provisioning

After a sandbox refresh, integration users and their permission sets may need to be re-provisioned. Automate the setup pipeline so credentials are regenerated and stored reliably after any refresh.

After sandbox refresh:
  1. Re-run user provisioning script
  2. Recreate/reassign permission sets
  3. Re-deploy External Client App (ECA)
  4. Retrieve new OAuth consumer creds
  5. Update secret store entries
  6. Verify end-to-end API flow
