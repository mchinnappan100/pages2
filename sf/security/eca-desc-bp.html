Writing a Great External Client App Description

Salesforce lets you leave the ECA description blank — and most admins do. Here is what a good description looks like, what it must cover, and how to make it a habit.

Level 01

Why the Description Matters

The description field accepts a null value, so it gets skipped during setup. Six months later, nobody remembers why the app exists, who owns it, or whether it is safe to delete.

The real problem: an ECA with no description is an OAuth entry point into your org that no one can explain. In a security review, "we don't know what this does" usually ends with the app being disabled — often in the middle of a business process.
🕵️

Security & Audit Reviews

Reviewers can judge an app in seconds when the purpose, scopes and owner are written down.

  • Justifies every OAuth scope granted
  • Shows who approved the integration
  • Speeds up access recertification
▶ See Example 
Auditor question : "Why does this app have the 'full' scope?"
Without description: nobody knows → app disabled
With description   : "Scopes: api, refresh_token only. No full."
                     → reviewed in 30 seconds
Result: shorter reviews, fewer surprise shutdowns.
👤

Ownership & Offboarding

People change teams and leave. The description is the one place that survives with the metadata.

  • Names a team or DL, not just one person
  • Tells you who to ask before changes
  • Prevents orphaned integrations
▶ See Example 
OWNER: Integration Platform Team
CONTACT: integrations@example.com
→ survives when the original admin leaves
Result: every app has an accountable owner.
🔁

Redeploy & Sandbox Refresh

Local ECAs are not copied on sandbox refresh, so you will redeploy them. The description travels in Git with the metadata.

  • Explains which external system to reconnect
  • Points to where the secret lives (not the secret)
  • Lists post-deploy steps
▶ See Example 
SECRET: Vault path secret/sf/qa/billing-app
After refresh: redeploy → retrieve new consumer key
→ update Vault → verify OAuth flow
Result: refreshes become a runbook, not archaeology.
🧹

Cleanup & Lifecycle

Unused apps are risk. A review date and ticket reference make it safe to retire what is no longer needed.

  • Records why and when it was created
  • Sets an expected review cadence
  • Links to the approval ticket
▶ See Example 
TICKET: SEC-1423 | CREATED: 2026-03-12
REVIEW: every 6 months | NEXT: 2026-09
Result: stale apps get found and retired.
Level 02

Anatomy of a Good Description

A great description answers nine questions. You do not need an essay — one short labeled line per item is enough.

🎯

1 · Purpose

One sentence: which system connects, and what business job it does.

▶ See Example 
PURPOSE: Lets Acme Billing sync closed-won
Opportunities into Salesforce nightly.
👥

2 · Owner & Contact

Technical owner team, business owner, and a shared mailbox or channel.

▶ See Example 
OWNER: Integration Platform Team
BIZ OWNER: Finance Ops
CONTACT: integrations@example.com
🔌

3 · External System

Name, vendor, version or hosting, so people know what is on the other end.

▶ See Example 
SYSTEM: Acme Billing v4 (SaaS) — Acme Inc.
HOST: billing.example.com
🔑

4 · OAuth Flow & Scopes

Which flow is used and why each scope is needed. This is what reviewers look for.

▶ See Example 
FLOW: Authorization Code + PKCE
SCOPES: api (read/write Opportunity),
        refresh_token (nightly job, no re-login)
🧑‍💻

5 · Run-As User & Access

For Client Credentials Flow, name the run-as user and the permission set that limits it.

▶ See Example 
RUN-AS: integ.billing@example.com
PERMSET: Billing_Integration (least privilege)
🗂️

6 · Data Touched

Objects and the highest data classification involved.

▶ See Example 
DATA: Opportunity, Account (read); Invoice__c (write)
CLASSIFICATION: Internal — no PII
🌐

7 · Environment

State which org this record belongs to and the callback host, since values differ per environment.

▶ See Example 
ENV: PROD
CALLBACK HOST: billing.example.com
🔐

8 · Secret Location (pointer only)

Tell people where the secret is stored — never the secret itself.

▶ See Example 
SECRET: Vault path secret/sf/prod/billing
SECRET OWNER: SecOps
📅

9 · Lifecycle & Support

Ticket, creation date, review cadence, and a runbook link.

▶ See Example 
TICKET: SEC-1423 | CREATED: 2026-03-12
REVIEW: 6 months
RUNBOOK: wiki.example.com/eca/billing
Never put in the description: consumer secrets, tokens, passwords, personal phone numbers, or any value you would not want a read-only admin to see. The description is plain text in metadata and in Git.
Level 03

A Copy-Ready Template

Use short labels so descriptions look the same across your org and are easy to scan and search. Keep each value on one line.

PURPOSE: <system> <does what> for <business process>.
OWNER: <team> | BIZ OWNER: <department> | CONTACT: <shared mailbox or channel>
SYSTEM: <external app, vendor, version/host>
FLOW: <Auth Code + PKCE | Client Credentials | JWT Bearer>
SCOPES: <scope — reason>, <scope — reason>
RUN-AS: <integration user> | PERMSET: <permission set>
DATA: <objects touched> | CLASSIFICATION: <public/internal/confidential>
ENV: <DEV|QA|UAT|PROD>
SECRET: <secret store path> | SECRET OWNER: <team>
TICKET: <ID> | CREATED: <YYYY-MM-DD> | REVIEW: <cadence> | RUNBOOK: <link>
Tip: if line breaks do not survive in your view of the field, separate items with | on a single line. The labels keep it readable either way.

Where it lives in metadata

The description is part of the ExternalClientApplication metadata, so it is source-controlled and deployed together with the app.

▶ See vimcApp.eca-meta.xml with a description 
<?xml version="1.0" encoding="UTF-8"?>
<ExternalClientApplication xmlns="http://soap.sforce.com/2006/04/metadata">
  <contactEmail>integrations@example.com</contactEmail>
  <description>PURPOSE: Acme Billing syncs closed-won Opps nightly. OWNER: Integration Platform Team | FLOW: Auth Code + PKCE | SCOPES: api, refresh_token | SECRET: Vault secret/sf/prod/billing | TICKET: SEC-1423</description>
  <distributionState>Local</distributionState>
  <isProtected>false</isProtected>
  <label>vimcApp</label>
</ExternalClientApplication>
Result: the description is reviewed in pull requests like any other change.
Best Practices

What Great Teams Do

✓Never Leave It Blank

Salesforce allows a null description, but treat it as required in your own standards. Even a two-line description beats nothing.

❌ description: (null)
✅ description: PURPOSE: ... | OWNER: ... | TICKET: ...

✓Explain Why, Not Just What

The label already says what the app is called. Use the description for the reason it exists and why each scope was granted.

❌ "Billing app"
✅ "Syncs closed-won Opps to Acme Billing nightly.
    api scope: write Invoice__c. refresh_token: unattended job."

✓Point to Secrets, Never Include Them

Reference the vault path or secret name so engineers can find it, and nothing more.

❌ SECRET: 3MVG9...key / A1B2C3...secret
✅ SECRET: Vault secret/sf/prod/billing

✓Name a Team, Not Only a Person

Use a distribution list, queue or channel so the contact outlives any single employee.

❌ OWNER: jsmith
✅ OWNER: Integration Platform Team (#sf-integrations)

✓Write Environment Context

Because credentials, callback URLs and org-scoped IDs differ per environment, state which environment the record serves. Keep the common wording the same across DEV, QA, UAT and PROD.

DEV : ENV: DEV  | CALLBACK HOST: dev.example.com
QA  : ENV: QA   | CALLBACK HOST: qa.example.com
PROD: ENV: PROD | CALLBACK HOST: app.example.com

✓Use a Fixed, Searchable Format

Consistent labels let you grep Git, export metadata to a spreadsheet, and compare apps at a glance.

grep -r "OWNER:" force-app/main/default/externalClientApps/

✓Update It When the App Changes

Adding a scope, switching flows or changing the owner? Change the description in the same pull request. A stale description is worse than none.

PR checklist:
[ ] Scopes changed?   → description updated
[ ] Flow changed?     → description updated
[ ] Owner changed?    → description updated

✓Enforce It in CI/CD

Do not rely on memory. Fail the pipeline when an ECA has no description or is missing required labels.

#!/usr/bin/env bash
# Fail if any ECA is missing a description or required labels
status=0
for f in force-app/main/default/externalClientApps/*.eca-meta.xml; do
  desc=$(sed -n 's:.*<description>\(.*\)</description>.*:\1:p' "$f")
  if [ -z "$desc" ]; then
    echo "❌ $f: description is empty"; status=1; continue
  fi
  for label in PURPOSE OWNER SCOPES TICKET; do
    echo "$desc" | grep -q "$label:" || { echo "❌ $f: missing $label"; status=1; }
  done
done
exit $status

✓Review Descriptions on a Schedule

Add description review to your periodic access review. Confirm the owner still exists, scopes match, and the app is still needed.

Every 6 months, for each ECA:
1. Owner still valid?
2. Scopes still justified?
3. Used in the last 90 days?
4. Update REVIEW date — or retire the app

ECA Description Reference

A quick standard you can adopt. "Must" items should block a deployment; "Should" items should be reviewed.

The principle: the description is the app's documentation that travels with the metadata. If someone can understand purpose, owner, access and lifecycle from this one field, the ECA is governable.
