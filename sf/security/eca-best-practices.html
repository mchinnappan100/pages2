Level 01

Overview

Spring '26 update: Salesforce restricted creation of new Connected Apps beginning in Spring '26 and recommends External Client Apps for all new integrations. ECA uses a modular, more secure metadata model than the legacy Connected App.
🔌

What is an External Client App?

An External Client App (ECA) is Salesforce's modern replacement for the Connected App, designed for OAuth 2.0 integrations with external systems. It separates configuration into distinct, deployable metadata components.

  • Successor to the legacy Connected App model
  • Modular metadata — each concern is a separate file
  • Deployable via Metadata API and SFDX CLI
  • Supports environment-isolated OAuth consumers
  • OAuth consumer credentials kept separate from app config
▶ See Real Metadata (vimcApp) 
<?xml version="1.0" encoding="UTF-8"?>
<ExternalClientApplication
  xmlns="http://soap.sforce.com/2006/04/metadata">
  <contactEmail>mchinnappan@salesforce.com</contactEmail>
  <distributionState>Local</distributionState>
  <isProtected>false</isProtected>
  <label>vimcApp</label>
  <orgScopedExternalApp>
    00Daj00000tLpCj:vimcApp
  </orgScopedExternalApp>
</ExternalClientApplication>

File: externalClientApps/vimcApp.eca-meta.xml
distributionState: Local means the ECA lives only in this org (not packaged).
orgScopedExternalApp embeds the source org ID — this changes per environment.

Result: rotating QA credentials never affects DEV or PROD.

⚖️

ECA vs Connected App

Connected Apps store all OAuth configuration in a single monolithic record. External Client Apps decompose that into independently deployable components.

  • Connected App: one record, all settings bundled together
  • ECA: four separate metadata types per app
  • ECA supports deploying with a fresh OAuth consumer per target org
  • ECA Global OAuth Settings explicitly mark secrets as sensitive
  • New Connected App creation restricted from Spring '26
▶ See Example 
Connected App (legacy)
└── ConsumerKey + ConsumerSecret + Policies
    all in one record — hard to separate

External Client App (current)
├── ExternalClientApplication     ← app identity
├── ExtlClntAppOauthSettings      ← non-sensitive config
├── ExtlClntAppGlobalOauthSettings← sensitive credentials
└── ExtlClntAppOauthConfigurablePolicies ← policies

Result: sensitive credentials can be managed independently of app configuration.

🔑

OAuth Credential Anatomy

Salesforce uses industry-standard OAuth 2.0 terminology mapped to its own naming convention. Critically: the consumerSecret is never stored in the metadata XML — only the consumerKey is. The secret is generated by Salesforce and is only accessible via the Setup UI after deployment.

  • consumerKey = OAuth client_id — stored in metadata XML
  • consumerSecret = OAuth client_secret — UI-only, never in XML
  • After deployment, retrieve the secret once from Salesforce Setup
  • Store the secret immediately in an approved secrets manager
  • isConsumerSecretOptional controls whether the secret is required at runtime
▶ See Real GlobalOauthSettings XML (vimcApp) 
<ExtlClntAppGlobalOauthSettings>
  <callbackUrl>http://localhost:9876/callback</callbackUrl>
  <consumerKey>3MVG9XgkMlifdwVDx4z97pX...</consumerKey>
  <externalClientApplication>vimcApp</externalClientApplication>
  <isConsumerSecretOptional>true</isConsumerSecretOptional>
  <isPkceRequired>true</isPkceRequired>
  <isRefreshTokenRotationEnabled>true</isRefreshTokenRotationEnabled>
  <shouldRotateConsumerKey>false</shouldRotateConsumerKey>
  <shouldRotateConsumerSecret>false</shouldRotateConsumerSecret>
  <!-- no consumerSecret element — it is never written to XML -->
</ExtlClntAppGlobalOauthSettings>

Key fact: consumerSecret does not appear in this file. Retrieve it from Salesforce Setup UI after deployment and store it in your secret store.

Level 02

Architecture

🗂️

Five Metadata Components

Every External Client App is composed of five distinct Salesforce metadata types, each with a different sensitivity level and deployment strategy.

  • ExternalClientApplication — app identity; contains org-scoped orgScopedExternalApp
  • ExtlClntAppOauthSettings — OAuth scopes and flows; contains org-scoped oauthLink
  • ExtlClntAppGlobalOauthSettings — consumerKey, callbackUrl, flow toggles (consumerSecret is UI-only, never in XML)
  • ExtlClntAppOauthConfigurablePolicies — session policies; contains clientCredentialsFlowUser only when Client Credentials Flow is enabled (sandbox-suffixed, env-specific)
  • ExtlClntAppConfigurablePolicies — top-level enablement; isEnabled and isOauthPluginEnabled must be true for OAuth to work
▶ See SFDX Source Structure + env-specific fields 
force-app/main/default/
├── externalClientApps/
│   └── vimcApp.eca-meta.xml
│       orgScopedExternalApp: 00Daj00000tLpCj:vimcApp  ← org-scoped
├── extlClntAppOauthSettings/
│   └── vimcApp_oauth.extlClntAppOauthSettings-meta.xml
│       oauthLink: 00Daj00000tLpCj:888aj0000028zzd     ← org-scoped
├── extlClntAppGlobalOauthSettings/
│   └── vimcApp_glbloauth.extlClntAppGlobalOauthSettings-meta.xml
│       consumerKey: 3MVG9...     ← env-specific
│       callbackUrl: http://...   ← env-specific
│       consumerSecret: (not in XML — Setup UI only)
├── extlClntAppOauthConfigurablePolicies/
│   ├── vimcApp_oauthPlcy.extlClntAppOauthConfigurablePolicies-meta.xml
│   │   (no clientCredentialsFlowUser — CCF disabled for vimcApp)
│   └── ModelsAPIApp_oauthPlcy.extlClntAppOauthConfigurablePolicies-meta.xml
│       clientCredentialsFlowUser: user@example.com.af300
│       ← only present because CCF is enabled for ModelsAPIApp
└── extlClntAppConfigurablePolicies/
    └── vimcApp_plcy.extlClntAppConfigurablePolicies-meta.xml
        isEnabled: true
        isOauthPluginEnabled: true  ← must be true for OAuth to function

5 metadata types total. ExtlClntAppConfigurablePolicies is the top-level switch — if isOauthPluginEnabled is false, OAuth will not work even if all other files are correct. clientCredentialsFlowUser only appears when isClientCredentialsFlowEnabled: true.

🌐

Environment Isolation Model

Each Salesforce environment in the promotion chain should be treated as fully independent, with its own OAuth consumer identity.

  • DEV — its own client ID and secret
  • QA — its own client ID and secret
  • UAT — its own client ID and secret
  • PROD — its own client ID and secret
  • Revoking one environment's credentials does not affect others
▶ See Isolation Diagram 
         Git (common app metadata)
                      |
       +--------------+--------------+
       |              |              |
      DEV             QA            UAT
       |              |              |
  DEV_CLIENT_ID  QA_CLIENT_ID  UAT_CLIENT_ID
  DEV_SECRET     QA_SECRET     UAT_SECRET
       |              |              |
  Dev System     QA System     UAT System

Result: full environment isolation from a single source of metadata truth.

📋

Retrieve Metadata via CLI

Use the Salesforce CLI (sf v2) to retrieve External Client App metadata from the source environment before committing to Git.

  • Use sf project retrieve start
  • Specify the metadata type explicitly
  • Retrieve each component type separately or via package manifest
  • Review retrieved files before committing — exclude secrets
▶ See CLI Commands 
# Retrieve app metadata
sf project retrieve start \
  --metadata ExternalClientApplication \
  --target-org SOURCE_ORG

# Retrieve OAuth settings
sf project retrieve start \
  --metadata ExtlClntAppOauthSettings \
  --target-org SOURCE_ORG

# Deploy to target
sf project deploy start \
  --manifest manifest/package.xml \
  --target-org TARGET_ORG

Result: repeatable, CLI-driven migrations suitable for CI/CD automation.

Level 03

Migration Models

Key principle: Deploying an External Client App to another org does not automatically generate new credentials. The outcome depends entirely on how the Global OAuth Settings are configured during deployment.
🔗

Option A — Reference Source Org Consumer

The target org references the Global OAuth Settings that belong to the source org. Both environments share the same OAuth consumer identity.

  • Target org does not receive its own consumer key/secret
  • Environments are coupled to the source org's credentials
  • If source org's Global OAuth Settings are removed, dependent apps break
  • Suitable only when environments are intentionally shared
  • Generally not appropriate for DEV / QA / UAT / PROD promotion chains
▶ See Risk Diagram 
Sandbox A (source)
  Client ID: ABC
  Client Secret: XYZ
        |
        +------ Sandbox B (target)
                  references same
                  ABC / XYZ
                  ← coupled!

Risk: rotating Sandbox A credentials breaks Sandbox B with no warning.

✅

Option B — New Global OAuth Settings (Preferred)

Salesforce provides a documented deployment process called "Deploy an External Client App with a New Global OAuth Settings File". The target org receives its own independent OAuth consumer credentials.

  • Target org gets its own consumer key and secret
  • Source and target environments are fully decoupled
  • Rotating one environment's secret does not affect others
  • Preferred for all independent DEV / QA / UAT / PROD environments
  • Salesforce officially documents and supports this model
▶ See Isolation Diagram 
Source Sandbox
  Client ID:  SRC_KEY
  Client Secret: SRC_SEC
        |
        | Deploy ECA with NEW
        | Global OAuth Settings
        v
Target Sandbox
  Client ID:  TGT_KEY   ← brand new
  Client Secret: TGT_SEC ← brand new

Result: full credential isolation — the recommended enterprise model.

🔄

Sandbox Refresh Behavior

Salesforce explicitly states that local External Client Apps are not copied when a sandbox is cloned or refreshed. Packaged ECAs behave differently.

  • A sandbox refresh will remove locally created ECAs
  • Your pipeline must be capable of re-deploying the ECA post-refresh
  • Source-controlled metadata makes re-provisioning repeatable
  • Post-refresh: re-deploy, retrieve new credentials, update secret store
  • Never assume a refreshed sandbox preserved the ECA
▶ See Post-Refresh Checklist 
After sandbox refresh:
  1. Re-run ECA deployment pipeline
  2. Retrieve new consumer key from org
  3. Store new consumer secret in secret store
  4. Update integration app config
  5. Verify OAuth flow end-to-end
  6. Confirm callback URL is correct

Warning: skipping step 2–4 will cause integration failures after refresh.

Source Control

What Goes in Git

Golden rule: Application metadata is promoted through Git. OAuth credentials belong to the target environment and must never be source-controlled as plain text.
✅

Commit These Files

All four metadata files are safe to commit — none contain the consumerSecret. However, every file contains at least one value that is environment-specific and will differ after deployment to a target org.

  • externalClientApps/*.eca-meta.xml — orgScopedExternalApp is org-scoped
  • extlClntAppOauthSettings/ — oauthLink is org-scoped
  • extlClntAppGlobalOauthSettings/ — consumerKey and callbackUrl differ per env
  • extlClntAppOauthConfigurablePolicies/ — env-specific only when CCF is enabled; clientCredentialsFlowUser carries a sandbox-suffixed username
  • extlClntAppConfigurablePolicies/ — top-level switch; isOauthPluginEnabled must be true for OAuth to work
  • Package manifest (pkg.xml or manifest/package.xml)
▶ See Real Examples (vimcApp) 
<!-- vimcApp.eca-meta.xml -->
<orgScopedExternalApp>
  00Daj00000tLpCj:vimcApp   ← org-scoped, changes per env
</orgScopedExternalApp>

<!-- vimcApp_oauth.extlClntAppOauthSettings-meta.xml -->
<commaSeparatedOauthScopes>
  RefreshToken, MCP
</commaSeparatedOauthScopes>
<oauthLink>
  00Daj00000tLpCj:888aj0000028zzd  ← org-scoped, changes per env
</oauthLink>

Note: org-scoped IDs are safe to commit but will have different values in each target environment after deployment — do not treat them as reusable constants.

🚫

Never Commit These

The Global OAuth Settings metadata contains live consumer credentials. It must be handled outside of Git and stored in a secrets management system.

  • Global OAuth Settings containing consumerSecret
  • Any file with a raw client_secret value
  • Environment-specific config.json files with embedded secrets
  • .env files with OAuth credentials
  • Sandbox-specific callback URLs if they contain PII or tokens
▶ See .gitignore Pattern 
# .gitignore
extlClntAppGlobalOauthSettings/
*.secret
*.env
config.*.json
secrets/

Also note: orgScopedExternalApp inside .eca-meta.xml encodes the source org ID (e.g. 00Daj00000tLpCj:vimcApp). It is safe to commit but will be org-specific — the target org will have a different value after deployment.

Warning: once a secret is in Git history, treat it as compromised — rotate immediately.

🔐

Secrets Management Architecture

The consumerSecret is never written to any metadata file. After deploying the ECA, the secret must be retrieved once from Salesforce Setup UI and stored immediately in a dedicated secrets manager.

  • After deployment: retrieve secret from Salesforce Setup (one-time action)
  • Store it immediately in an enterprise secret store (Vault, AWS Secrets Manager, etc.)
  • One secret per environment — never shared across DEV/QA/UAT/PROD
  • CI/CD pipeline injects secret at runtime via environment variable
  • Rotate secrets independently per environment without affecting others
▶ See Secret Lifecycle Flow 
1. Deploy ECA metadata from Git
        |
        v
2. Salesforce generates consumerSecret
   (visible once in Setup UI)
        |
        v
3. Operator copies secret → Secret Store
   QA_SECRET   → Vault/AWS Secrets Mgr
   UAT_SECRET  → Vault/AWS Secrets Mgr
   PROD_SECRET → Vault/AWS Secrets Mgr
        |
        v
4. Integration app reads secret at runtime
   via environment variable injection
   (never stored in files or Git)

Result: secret never appears in metadata, Git history, or CI/CD logs.

Best Practices

What Great Teams Do

✓ Isolate OAuth Consumers Per Environment

Each Salesforce environment must have its own consumer key and secret. Sharing credentials across environments creates coupling that makes rotation, revocation, and auditing unreliable.

❌ DEV, QA, UAT all share CLIENT_ID = ABC
✅ DEV  → DEV_CLIENT_ID
   QA   → QA_CLIENT_ID
   UAT  → UAT_CLIENT_ID
   PROD → PROD_CLIENT_ID

✓ Never Copy Credentials Between Sandboxes

Manually copying a client ID and secret from DEV to QA defeats the purpose of environment isolation. Use Salesforce's "new Global OAuth Settings" deployment to let each org establish its own consumer identity.

❌ Copy/paste DEV secret into QA config
✅ Deploy ECA with new Global OAuth Settings
   → Salesforce creates QA-specific credentials

✓ Source Control Metadata, Not Credentials

The ExternalClientApplication, OauthSettings, and Policies metadata is portable and environment-agnostic. The Global OAuth Settings containing the secret is environment-specific and must stay out of Git.

✅ Git: externalClientApps/
✅ Git: extlClntAppOauthSettings/
✅ Git: extlClntAppOauthConfigurablePolicies/
❌ Git: extlClntAppGlobalOauthSettings/

✓ Retrieve the Secret from Setup UI — Not the XML

The consumerSecret is never written to the GlobalOauthSettings metadata file. After deploying the ECA, retrieve the secret once from Salesforce Setup UI and store it immediately in a secrets manager. Never try to read it from the XML.

After deploy:
  Setup → External Client Apps
        → vimcApp → View Secret
        → Copy → store in Vault/AWS

✅ AWS Secrets Manager / Vault
✅ CI/CD secret variables (masked)
❌ config.json with "clientSecret": "..."
❌ Expecting secret in .xml file

✓ Deploy with New Global OAuth Settings

When deploying to an independent target environment, always use the Salesforce-documented "Deploy an External Client App with a New Global OAuth Settings File" process to ensure the target org gets its own consumer identity.

sf project deploy start \
  --manifest manifest/package.xml \
  --target-org TARGET_ORG
# Then retrieve new credentials from target

✓ Use Environment-Specific Callback URLs

The callback URL registered in Salesforce must exactly match the URL used by the external application. Configure a separate callback URL per environment to avoid cross-environment redirect attacks.

DEV:  https://dev.example.com/oauth/callback
QA:   https://qa.example.com/oauth/callback
UAT:  https://uat.example.com/oauth/callback
PROD: https://app.example.com/oauth/callback

✓ Verify the OAuth Flow After Every Deployment

An ECA deployment is not complete until you verify the end-to-end OAuth flow in the target environment. A successful metadata deployment does not guarantee a working integration.

Post-deploy verification checklist:
[ ] ECA exists in target org
[ ] OAuth plugin is enabled
[ ] Callback URL is correct
[ ] Client ID exists and is retrievable
[ ] External app authenticates successfully
[ ] Token refresh works

✓ Plan for Sandbox Refreshes

Salesforce does not copy local External Client Apps when a sandbox is refreshed. Your deployment pipeline must be capable of re-provisioning the ECA from scratch after any sandbox refresh.

After sandbox refresh:
1. Re-run ECA deploy from Git
2. Retrieve new consumer key
3. Store new secret in secret store
4. Update integration app config
5. Re-verify OAuth flow

✓ Separate Config from Secrets in the Pipeline

The CI/CD pipeline should treat ECA metadata and OAuth credentials as two separate concerns. Metadata flows from Git; secrets flow from the secret store. They are combined only at deploy time.

Git → ECA config → Pipeline
SecretStore → CLIENT_SECRET → Pipeline
                    |
              Merged at deploy
                    |
              Target Sandbox

✓ Prefer ECA Over Connected Apps

For all new Salesforce integrations, use External Client Apps. Salesforce restricted creation of new Connected Apps beginning in Spring '26 and officially recommends ECAs for all new OAuth-based integrations.

❌ New Connected App (restricted Spring '26)
✅ External Client App
   └── Modular metadata model
   └── Supports new Global OAuth Settings
   └── Deployable via Metadata API

✓ Make Integration Apps Environment-Aware

External applications consuming the Salesforce API must be configured with the correct credentials and login URL for each environment. Hard-coding any single environment's credentials is a common source of cross-environment bugs.

config.dev.json  → DEV clientId + loginUrl
config.qa.json   → QA  clientId + loginUrl
config.uat.json  → UAT clientId + loginUrl
config.prod.json → PROD clientId + loginUrl
# Secrets injected at runtime, not stored here

✓ Update clientCredentialsFlowUser Only When CCF Is Enabled

clientCredentialsFlowUser only appears in the policies file when isClientCredentialsFlowEnabled: true. When present, it contains a sandbox-suffixed username that must match a real user in the target org. When CCF is disabled (like vimcApp), the field is absent entirely.

vimcApp (CCF disabled):
  isClientCredentialsFlowEnabled: false
  → no clientCredentialsFlowUser field

ModelsAPIApp (CCF enabled):
  isClientCredentialsFlowEnabled: true
  clientCredentialsFlowUser:
    DEV:  user@example.com.af300
    QA:   user@example.com.qa1
    PROD: user@example.com

✓ Expect Org-Scoped IDs to Differ Per Environment

Two metadata files contain org-scoped IDs that encode the source org's 18-character ID. These values are safe to commit but will have different values after deployment to each target environment — never hard-code or compare them across orgs.

orgScopedExternalApp (in .eca-meta.xml):
  DEV:  00Daj00000tLpCj:vimcApp
  QA:   00Dxx00000YYYYY:vimcApp  ← different

oauthLink (in OauthSettings XML):
  DEV:  00Daj00000tLpCj:888aj0000028zzd
  QA:   00Dxx00000YYYYY:888xx0000000zzz  ← different

✓ Rotate Credentials Independently Per Environment

Because each environment has its own OAuth consumer, secrets can be rotated independently without any risk of disrupting other environments. Build this into your security operations runbook.

Rotate QA secret:
  1. Generate new secret in QA org
  2. Update QA entry in secret store
  3. Redeploy QA integration with new secret
  4. Verify QA OAuth flow
  → DEV, UAT, PROD unaffected
Enterprise Standard

ECA Deployment Reference

Reference table for what should be source-controlled vs environment-specific in an enterprise DEV → QA → UAT → PROD promotion pipeline.

Item Source Controlled Environment Specific Storage Location
External Client App metadata Yes No Git
OAuth Settings Yes Some values Git
OAuth Configurable Policies Yes When CCF enabled Git — clientCredentialsFlowUser only present when CCF is on; must match target org username
Configurable Policies (top-level) Yes No Git — isOauthPluginEnabled: true required for OAuth to function
Global OAuth Settings (file) No Yes Generated by Salesforce
Client ID (consumer key) No Yes Retrieve from target org post-deploy
Client Secret (consumer secret) No Yes Salesforce Setup UI → Secret store (never in XML)
Callback URL Configuration Yes Per-environment config or secret store
Salesforce Login URL Configuration Yes Per-environment config
Integration user credentials Configuration Yes Secret store
API endpoints (external system) Configuration Yes Per-environment config
Package manifest (package.xml) Yes No Git
CI/CD pipeline definition Yes No Git (no embedded secrets)
The architectural principle: ECA metadata is portable and lives in Git. OAuth consumer identity is environment-specific and belongs to the target org. Secrets never touch the filesystem or source history.
