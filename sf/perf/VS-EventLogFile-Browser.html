Section 01

What Is the EventLogFile Browser?

01
🏛️

Native Salesforce Tool

The EventLogFile Browser is a built-in Salesforce feature accessible from Setup → Event Monitoring → Event Log File Browser. It lets administrators browse and download raw event log CSV files directly from the platform UI.

Available in Enterprise, Performance, Unlimited, Developer editions
Requires the Event Monitoring add-on license (or included in Shield)
No local tooling or installation required — browser only
Also accessible via the EventLogFile REST API: /services/data/vXX.0/sobjects/EventLogFile
Real-time event monitoring available (1-hour intervals) as a separate add-on
📥

What It Does

The ELF Browser is a download interface. You select a date, pick an event type, and download a CSV file containing every event of that type recorded in your org on that day.

Filter by event type and date range
Download CSV — one file per event type per day
View log file size and row count before downloading
No aggregation, no visualisation, no percentile analysis
CSV files can be opened in Excel, imported into Splunk, or fed into custom scripts

You navigate to Setup → Event Monitoring → Event Log File Browser and see:

Date Event Type Size Rows 2026-09-05 ApexExecution 2.4 MB 12,847 [Download] 2026-09-05 ApexTrigger 890 KB 4,201 [Download] 2026-09-05 RestApi 5.1 MB 31,440 [Download] 2026-09-05 ApexCallout 340 KB 1,823 [Download]
Clicking Download gives you a raw CSV. You then open it in Excel, write a SOQL query against it, or pipe it into a script to find slowest entry points — all manual steps.
🔑

Licensing & Access

Event Monitoring data access requires a specific license. The ELF Browser surfaces this data — but only for orgs where the license is active.

Event Monitoring add-on: purchased separately — gives ELF access without full Shield
Salesforce Shield: includes Event Monitoring + Platform Encryption + Field Audit Trail
Developer Edition: limited access — some event types available for testing
Required profile permission: View Event Log Files
SF Perf Monitor uses the same license — it calls the same EventLogFile SOQL API the browser uses
Section 02

The Five Core Event Types

02

Salesforce records dozens of event types. SF Perf Monitor focuses on the five that carry actionable performance timing data — each with a distinct identity column and duration field.

🏃

ApexExecution

Records every synchronous Apex execution — anonymous blocks, future methods, batch execute, and scheduled Apex invocations. The highest-signal event type for Apex performance.

Identity: ENTRY_POINT — class.method or anonymous
Duration: RUN_TIME (total wall time) + EXEC_TIME (CPU only)
DB_TOTAL_TIME — total time spent in database calls
NUMBER_SOQL_QUERIES — SOQL query count per transaction
NUMBER_DML_STATEMENTS — DML statement count per transaction
CPU_TIME — Salesforce governor CPU time consumed
⚙️

ApexTrigger

Records every trigger execution — before/after insert, update, delete, undelete. Bulkification issues show up clearly in the trigger execution times vs. record counts.

Identity: TRIGGER_NAME
Duration: RUN_TIME + EXEC_TIME
TRIGGER_TYPE — before/after insert/update/delete/undelete
NUMBER_SOQL_QUERIES — critical for detecting SOQL-in-loop
ROWS_PROCESSED — number of records in the trigger batch
🌐

RestApi

Records every inbound REST API request — Salesforce standard REST endpoints including SOQL queries via REST, CRUD operations, and Chatter API calls.

Identity: URI — the request path
Duration: RUN_TIME
METHOD — GET / POST / PATCH / DELETE
STATUS_CODE — HTTP response code
ROWS_PROCESSED — records returned or modified
Integration latency baseline — compare across deploy dates
🔗

ApexRestApi

Records invocations of custom @RestResource Apex classes — your own REST endpoints exposed to external systems and integrations.

Identity: URI — the custom endpoint path
Duration: RUN_TIME
METHOD — HTTP method of the request
STATUS_CODE — response status
Critical for SLA monitoring on integration endpoints
📡

ApexCallout

Records every outbound HTTP callout from Apex — calls to external APIs, web services, named credentials, and platform events. Shows the latency of external dependencies.

Identity: URL — the endpoint called
Duration: TIME — round-trip callout time in ms
METHOD — HTTP method (GET / POST / PUT)
STATUS_CODE — HTTP response from external system
Use to distinguish: "is it our Apex, or the external API?"

Section 05

Investigation Workflow

05
🔍

With ELF Browser Only

The manual path — effective but slow. Good for one-off investigations or when SF Perf Monitor is not available.

1. Setup → Event Monitoring → choose date and event type
2. Download CSV (can be several MB)
3. Open in Excel / Numbers — sort by RUN_TIME descending
4. Filter to ENTRY_POINT of interest — manually compute avg, P95
5. Cross-reference REQUEST_ID against ApexLog manually in Dev Console
6. Repeat for each event type and each day

Finding P95 for OrderService manually in Excel:

1. Download ApexExecution CSV (2.4 MB, 12,847 rows) 2. Filter column A (ENTRY_POINT) = "OrderService*" → 847 matching rows 3. Sort by RUN_TIME descending 4. P95 = row at rank ceil(0.95 × 847) = row 805 → RUN_TIME at row 805 = 4,200 ms 5. Write formula: =PERCENTILE(C2:C848, 0.95) → 4,200 ms ← matches manual sort ✓ 6. Repeat for each of the 5 event types…
This takes 15–30 minutes per event type per day. SF Perf Monitor does it in under 3 seconds for all 5 types at once.
⚡

With SF Perf Monitor

The same data, fully automated — from org credentials to interactive dashboard in one command.

1. node server.js -o my-org — fetches all 5 event types automatically
2. Dashboard opens at localhost:3000 — P95, slow %, KPI cards rendered instantly
3. Click the slowest bar → drill-down: KPI strip + sparkline + row table
4. ⚡ View Source → Monaco editor with 8 anti-pattern rules highlighted
5. 🔍 badge on row → click → ApexLog body in Monaco viewer
6. 🤖 Ask AI to fix → source + findings + P95 injected into AI Sidekick

Same investigation, with SF Perf Monitor:

$ node server.js -o production-org [startup] Fetching ApexExecution… 12,847 rows [startup] Fetching ApexTrigger… 4,201 rows [startup] Fetching RestApi… 31,440 rows [startup] Fetching ApexRestApi… 2,109 rows [startup] Fetching ApexCallout… 1,823 rows [startup] Done in 4.2s — open http://localhost:3000 Dashboard shows: OrderService.processOrder P95: 4,200 ms Slow%: 31% ← immediately visible 🔴 CRITICAL: SOQL inside loop (line 42) ← auto-detected
Total time from command to actionable finding: under 10 seconds.
🗓️

Ongoing Monitoring (Scheduled)

For continuous oversight — not just ad-hoc investigations — SF Perf Monitor adds automated scheduled delivery that ELF Browser has no equivalent for.

Settings → Auto-Fetch Schedule: set a cron expression (e.g. 0 8 * * 1-5)
Each run: fetches latest ELF data → regenerates all charts → sends Action Plan
Slack: Block Kit card with health status + top-5 slowest + critical issues
Teams: Adaptive Card v1.4 with health-colour-coded status
Email: dark-theme HTML report with KPI grid + per-event table
ELF Browser: no scheduling, no delivery, no comparison over time
Section 06

Limits, Gotchas & Best Practices

06

! Data Is Available After ~1 Hour

EventLogFile records are not real-time. 24-hour log files become available approximately 1 hour after the end of the log day. Don't expect yesterday's logs immediately at midnight.

Real-time alternative: Event Monitoring Real-Time → Separate add-on license → 1-hour interval files (vs 24-hour) → Available ~1 hour after the hour closes → Same API, same CSV format

! 30-Day Retention Limit

Salesforce retains EventLogFile data for 30 days by default (1 day with some editions). SF Perf Monitor caches CSVs locally — meaning data persists past the 30-day window as long as you fetched it while it was available.

Cache location: data/_.csv → Persists indefinitely on your local machine → Re-downloaded only on "Refresh" or auto-fetch → gitignored — never committed to the repo → Back it up manually if long-term retention needed

! One File Per Day Per Event Type

Each EventLogFile record covers exactly one event type for one day. If you want a full picture, you must fetch all five types — the ELF Browser requires five separate downloads; SF Perf Monitor fetches all five in one startup sequence.

ELF Browser: 5 downloads × 1 click each = 5 manual steps SF Perf Monitor: → SOQL: SELECT Id, EventType, LogFile FROM EventLogFile WHERE EventType = 'ApexExecution' AND LogDate = TODAY → Runs for all 5 types in parallel on startup

✓ Use REQUEST_ID to Correlate Logs

Every EventLogFile row has a REQUEST_ID. When --debug-logs is enabled, SF Perf Monitor joins EventLogFile rows against ApexLog records on this field — a 🔍 badge appears on any row with a matching debug log.

Correlation flow: ELF row REQUEST_ID: 4bERC00000001234 → O(1) index lookup in DL.index → 🔍 badge appears on the row → Click → lazy-fetch ApexLog body → Monaco viewer opens the full debug log

✓ Large Files: Use the Cache

A busy RestApi log can exceed 50 MB. The first fetch takes time — subsequent refreshes skip the download if the file hasn't changed. SF Perf Monitor caches CSV to data/ and only re-downloads on explicit refresh.

Cache-hit path (fast): GET /api/fetch → check data/_RestApi.csv → file exists + same log date → skip download → parse + index in memory (~200ms for 30k rows) Force re-download: → Click 🔄 Refresh in the dashboard toolbar → Or delete data/_.csv manually

✓ Threshold Tuning

The default slow threshold is 3000 ms. Tune it to match your org's SLA — a batch job at 8000 ms may be fine; a UI-driven Apex call at 3000 ms is not. Use -t flag or Settings → Threshold.

Threshold guidance by event type: ApexExecution (UI-triggered) : 2000 – 3000 ms ApexExecution (batch/future) : 10000 – 30000 ms ApexTrigger : 1000 – 2000 ms RestApi / ApexRestApi : 1000 – 3000 ms ApexCallout : 3000 – 8000 ms → Use -t per run, or Settings slider per session

✓ Governor Limit Fields Are Leading Indicators

NUMBER_SOQL_QUERIES and NUMBER_DML_STATEMENTS in the CSV are per-transaction governor usage counts. High values here predict future limit errors before they occur.

Warning signs in drill-down stats: SOQL queries > 80 (limit = 100) ← 80% headroom used DML statements > 120 (limit = 150) ← 80% headroom used CPU time > 8000 ms (limit = 10000) ← 80% headroom used → Address before the org grows further

✓ Security: No Shell Interpolation

SF Perf Monitor calls sf data query via execFileAsync('sf', [...args]) — never via shell string interpolation. Org aliases and event type strings are passed as array elements, never concatenated into a shell command.

Safe: execFileAsync('sf', [ 'data', 'query', '--query', 'SELECT Id, EventType FROM EventLogFile', '--target-org', orgAlias, ← array element, not string '--json' ]) Never: exec(`sf data query -q "..." -o ${orgAlias}`) ← command injection risk if alias contains shell chars
