Section 01

The Tools

01
📊

SF Perf Monitor

A local Node.js dashboard that downloads EventLogFile data from your Salesforce org and visualises real runtime performance — P95 latencies, slow rates, trend charts — against actual production traffic.

ApexExecution · ApexTrigger · RestApi · ApexRestApi · ApexCallout
P50 / P75 / P90 / P95 / P99 / Max percentile breakdown
Trend chart, heatmap, drill-down, KPI cards
Slack, Teams, Email notifications on schedule
Fully offline — node server.js, no cloud dependency

You fetch yesterday's ApexExecution logs for your production org and immediately see:

OrderService.processOrder Occurrences : 847 Avg : 1,820 ms P95 : 4,200 ms ← 40% over threshold Slow % : 31% Max : 9,340 ms
Click the bar → drill-down panel → ⚡ View Source → Monaco editor opens OrderService with SOQL-in-loop flagged in the hints bar. One click to ask the AI Sidekick to fix it.
🕸️

SF Graphy

An Apex Knowledge Graph explorer that parses your entire SFDX project or live org and renders all class dependencies as a D3 force-directed graph — instantly showing who calls what, which classes inherit from whom, and where SOQL targets land.

CALLS · EXTENDS · IMPLEMENTS · QUERIES · USES · DML edges
Top-N / BFS focus-hops / node-type / edge-type filters
God class · orphan · cycle · shortest-path analysis
Complexity heatmap · mini-map navigator · pin nodes
SVG · PNG · JSON · GraphML export

You click AccountService in the graph and the detail panel shows:

AccountService (Class) Inbound edges : 23 ← called by 23 classes Outbound edges : 8 SOQL queries : 5 DML operations : 3 Impact (BFS) : 41 classes depend on this ⚠ Cycle with : AccountRepository
"Shortest Path" analysis shows the exact call chain from AccountController to AccountRepository in 3 hops.
🤖

Salesforce Apex Guru

A Salesforce-native AI service (GA Spring '25) that performs deep static analysis on a single Apex class or trigger at a time, returning AI-generated recommendations about code quality, performance risks, and anti-patterns — entirely inside the Salesforce platform UI.

One class or trigger per analysis session
AI trained on Salesforce platform patterns and idioms
Accessible from Setup → Apex Guru or Developer Console
No local tooling required — browser only
Included in the Salesforce platform (usage limits apply)

You open AccountService in Setup → Apex Guru and it returns:

⚠ Performance Risk — High SOQL query inside a for loop at line 42. Recommendation: Collect all record Ids first, then execute a single bulk SOQL query outside the loop using an Id Set. ⚠ Code Quality — Medium Large method (87 lines) could be refactored into smaller, testable units. ℹ Suggestion Consider using a Selector pattern for SOQL to improve testability and reduce duplication.
Section 02

Feature Comparison

02
🔭

Analysis Scope

The most fundamental difference: how much of the codebase each tool can see at once.

SF Graphy: entire org or SFDX project — all classes simultaneously, with cross-class relationships
Apex Guru: one class or trigger per session — no cross-class graph
Graphy tested on orgs with 738–1,431 Apex classes
Guru excels at deep reasoning about the selected class's internal logic
📡

Data Source

Where each tool gets its evidence — the fundamental difference between runtime observation and static inspection.

SF Perf Monitor: live EventLogFile CSV from production — real requests, real timings
SF Graphy: Apex source (.cls files or Tooling API) — structural relationships
Apex Guru: static source code only — no runtime signal
SF Perf Monitor can show a class is slow even when no static anti-pattern exists (e.g. slow SOQL on large data volume)
🗺️

Visualisation

How each tool presents findings — text vs. interactive graph.

SF Graphy: D3 v7 force-directed graph — pan, zoom, pin nodes, mini-map
SF Perf Monitor: Chart.js bar charts, trend area chart, hour×day heatmap
Apex Guru: text recommendations list — no graph or chart output
Graphy exports: SVG, PNG (2×), JSON (Gephi/Cytoscape), GraphML
🏛️

Architectural Analysis

Finding systemic problems that only become visible across the full codebase.

SF Graphy — God Classes: nodes with ≥ 35% of max degree — over-coupled classes
SF Graphy — Orphans: classes with zero connections — dead code candidates
SF Graphy — Cycles: mutual A→B→A dependencies — compiler/test risk
SF Graphy — Impact BFS: "what breaks if I change this?" — transitive dependency count
Apex Guru: no architectural view — single-class scope
💬

AI Assistance

How each tool leverages AI and what context it brings to the conversation.

Apex Guru: Salesforce-trained LLM, deep Apex idiom knowledge, per-class context
AI Sidekick: Ollama / Claude / OpenAI / xAI / Gemini — user's choice of model
AI Sidekick injects structured graph context: god classes, cycles, selected node stats, runtime P95/slow%
AI Sidekick "Ask AI to fix" flow: source + perf metrics + anti-pattern findings in one prompt
AI Sidekick requires --enable-ai flag; keys stored in localStorage only
📤

Export & Integration

Getting results out and into the rest of your workflow.

SF Perf Monitor: PNG · SVG · HTML · PDF dashboard; Action Plan to Slack / Teams / Email
SF Graphy: SVG · PNG · JSON · GraphML graph export; convergence-first export (fully settled layout)
Apex Guru: copy-paste text from UI — no structured export
SF Perf Monitor runs headless in CI via node server.js with cron scheduling
Section 03

When to Use Each

03
🤖

Reach for Apex Guru when…

You need deep AI reasoning about a specific class's internal logic, and you want to stay entirely inside the Salesforce browser UI.

You want AI feedback on a single class without leaving the browser
You need a Salesforce-trained LLM that understands platform-specific idioms (selector pattern, trigger handler, custom metadata)
You're doing active development and want quick inline recommendations before committing
You have no local development environment available
You want to operate entirely within Salesforce's trust boundary
📊

Reach for SF Perf Monitor when…

You need real production evidence — not hypothetical static risk, but measured runtime impact from actual user traffic.

You're investigating a reported slowness in production — "the app is slow after 5pm"
You want P95/P99 runtimes, slow %, and trend over time for every Apex entry point
You need to prove a class is the bottleneck before spending time refactoring it
You want automated daily / weekly perf reports sent to Slack or Teams
You need to correlate an ApexLog record with the exact EventLogFile row that triggered it
🕸️

Reach for SF Graphy when…

You need to understand the structure of the codebase — who depends on whom, what the blast radius of a change is, where the coupling is too tight.

You're planning a refactor and need to know which classes will be affected
You've joined a new project and want an architectural orientation in minutes
You want to find god classes, orphaned dead code, and circular dependencies across the full org
You need to work offline — analyze an SFDX project with no org connection
You want to export the dependency graph for a team design review or architecture board
🔗

Use both together when…

The most powerful workflow combines all three tools in sequence — each answering a different question at the right moment.

Step 1: SF Graphy → orient architecturally, find god classes, spot cycles before starting work
Step 2: SF Perf Monitor → identify which of those classes are actually slow in production
Step 3: Apex Guru → deep-dive the specific class that is both structurally problematic and runtime slow
This avoids the trap of refactoring well-written code that isn't a bottleneck, and ignoring ugly-but-fast code
Section 04

Deep Dives

04
🏛️

Architecture Visibility

Apex Guru has no concept of the graph. It cannot tell you that a class is called by 23 other classes, that changing it will cascade to 41 dependents, or that there is a circular dependency.

SF Graphy answers: "Who calls AccountService?" — 23 callers rendered instantly
SF Graphy answers: "What breaks if I change it?" — BFS impact count: 41 classes
SF Graphy answers: "Is there a cycle?" — AccountService ↔ AccountRepository cycle detected
Apex Guru answers: "Is the internal logic of AccountService well written?" — yes, very well
SF Graphy — AccountService node detail: Inbound : 23 edges (callers) Outbound : 8 edges (callees) SOQL : 5 queries DML : 3 operations Impact : 41 classes transitively depend on this ⚠ Cycle : AccountRepository Apex Guru — AccountService analysis: "Good use of selector pattern. Consider extracting the bulk update logic into a separate helper method for improved testability." (no cross-class view)
⏱️

Runtime vs. Static Evidence

Apex Guru works from source only — it can flag a SOQL-in-loop pattern, but it cannot tell you the class fired 847 times yesterday with a P95 of 4,200 ms and a 31% slow rate. That requires runtime data.

Static analysis may flag a SOQL-in-loop that never fires with more than 1 record — low actual risk
SF Perf Monitor reveals classes that are slow due to data volume — no static rule catches that
Runtime slow % > 30% is a hard prioritization signal — refactor this class before anything else
Combining both: use Apex Guru on the classes SF Perf Monitor identifies as hotspots
📐

Scale

Apex Guru is designed for focused, one-class sessions. SF Graphy handles large enterprise orgs with hundreds of classes using filtering and progressive rendering.

SF Graphy tested on orgs with 738 and 1,431 Apex classes
Top-N slider limits the rendered subgraph (default 80 highest-degree nodes)
BFS focus-hops: render only N hops from the selected class
Mini-map navigator for orientation when zoomed in on a dense cluster
Apex Guru: no concept of scale — single class always
🧠

AI Context Quality

Both tools use AI, but the context each LLM receives is fundamentally different — which determines the quality of the answer.

Apex Guru: Salesforce-specific training, deep Apex idiom reasoning, best-practice library knowledge
AI Sidekick: injects graph summary (god classes, cycles, node count), selected node stats, runtime P95/slow%, anti-pattern findings
AI Sidekick answers: "Why is this class a god class and how should I break it apart?" — backed by 23-caller graph evidence
Apex Guru answers: "How should I refactor this method?" — backed by deep Salesforce pattern knowledge

AI Sidekick context injected for AccountService (graph + runtime):

Graph summary: 142 nodes, 318 edges God classes: AccountService (31 connections), OrderManager (28 connections) Cycles: AccountService ↔ AccountRepository Selected node: AccountService Kind: Class · Degree: 31 SOQL: 5 · DML: 3 Inbound: 23 · Outbound: 8 Impact BFS: 41 classes Runtime (from EventLogFile): P95: 4,200 ms · Slow%: 31% Anti-patterns: SOQL in loop (line 42), System.debug spam (8 instances)
With this context, the AI can reason: "This class is slow and structurally over-coupled — here's a concrete decomposition strategy."
Best Practices

The Complementary Workflow

05

✓ Orient Architecturally First

Before touching any class, open SF Graphy and spend five minutes with the full graph. Identify god classes, cycles, and the blast radius of the area you plan to work in.

SF Graphy checklist before starting a refactor: □ Are there circular dependencies in this area? □ How many classes call the class I'm changing? □ Is this class a god class (high-degree node)? □ Export the subgraph for the design review doc

✓ Confirm Hotspots with Runtime Data

Don't refactor a class just because it looks complex. Confirm it is actually slow in production with SF Perf Monitor before investing time in changes.

SF Perf Monitor signal worth acting on: ✅ Slow% > 20% over last 7 days ✅ P95 > 2× your threshold (e.g. > 6000ms) ✅ Occurrences > 100/day (high traffic path) ⚠ Slow% = 50% but Occurrences = 2 (low risk)

✓ Deep-Dive with Apex Guru

Once SF Graphy and SF Perf Monitor have pointed you at the right class, take it to Apex Guru for deep AI-powered static analysis. Now the context is right and the recommendation is actionable.

Sequence: 1. SF Graphy → AccountService is a god class 2. SF Perf Monitor → P95=4200ms, Slow%=31% 3. Apex Guru → "SOQL in loop at line 42, extract repository layer, increase test coverage to 85%" ✅ All three arrows point at the same target

✓ Export Graphs for Design Reviews

SF Graphy's SVG and GraphML exports make architectural findings shareable. Drop the SVG into a design doc, or import GraphML into Gephi for advanced layout analysis.

Export workflow: → Click ⬇ SVG: simulation runs to convergence, fully-spread layout saved as standalone .svg → Click ⬇ JSON: import into Gephi / Cytoscape → Click ⬇ GraphML: Gephi, yEd, draw.io support → Paste SVG into Confluence / Notion page

✓ Schedule Automated Perf Reports

Use SF Perf Monitor's cron scheduling to send weekly Action Plan summaries to your Slack channel automatically. Catch regressions before users report them.

Settings → Auto-Fetch Schedule: Expression : 0 8 * * 1 (Mon 8am) → Fetches EventLogFile data → Regenerates Action Plan → Posts Block Kit summary to #sf-perf-alerts → Attaches dashboard PNG if Snap-to-Slack enabled

✓ Use AI Sidekick for Graph-Level Questions

When you need to reason about the whole graph — not a single class — the AI Sidekick with graph context injection produces far richer answers than any per-class tool.

AI Sidekick quick prompts with graph context: "Which god classes should I refactor first?" "Are there any circular dependencies?" "What are the highest-risk classes to change?" "Summarise the architecture of this codebase" "Which classes are tightly coupled to Account?"
