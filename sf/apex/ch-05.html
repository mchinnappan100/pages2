01

Trigger Syntax & Events

Triggers fire automatically when records are inserted, updated, deleted, or undeleted. They can run before or after the operation commits to the database.

Trigger Declaration

trigger AccountTrigger on Account (
    before insert, before update, before delete,
    after  insert, after  update, after  delete, after undelete
) {
    // Delegate ALL logic to a handler class
    AccountTriggerHandler handler = new AccountTriggerHandler();

    if (Trigger.isBefore) {
        if (Trigger.isInsert) handler.onBeforeInsert(Trigger.new);
        if (Trigger.isUpdate) handler.onBeforeUpdate(Trigger.new, Trigger.oldMap);
        if (Trigger.isDelete) handler.onBeforeDelete(Trigger.old);
    } else {
        if (Trigger.isInsert) handler.onAfterInsert(Trigger.new);
        if (Trigger.isUpdate) handler.onAfterUpdate(Trigger.new, Trigger.oldMap);
        if (Trigger.isDelete) handler.onAfterDelete(Trigger.old);
        if (Trigger.isUndelete) handler.onAfterUndelete(Trigger.new);
    }
}
One trigger per object: Never create multiple triggers on the same object — they fire in an unpredictable order. Put all logic in a single trigger that delegates to a handler class.
⏪

before triggers

Fire before the record is saved to the database. Ideal for validation and field population.

  • Records in Trigger.new do not yet have an Id (on insert)
  • Modifications to Trigger.new are automatically saved — no DML needed
  • Use for field defaulting, validation, normalisation
  • Calling addError() rolls back the save
// before insert — set default values
trigger OpportunityTrigger on Opportunity (before insert) {
    for (Opportunity opp : Trigger.new) {
        // Default close date if not set
        if (opp.CloseDate == null) {
            opp.CloseDate = Date.today().addDays(30);
        }
        // Validate amount
        if (opp.Amount != null && opp.Amount < 0) {
            opp.Amount.addError('Amount cannot be negative.');
        }
    }
}
⏩

after triggers

Fire after the record is committed. Records have Ids, and related records can be queried/modified.

  • Records in Trigger.new are read-only (already committed)
  • Must use DML to persist any changes
  • Use for creating/updating related records
  • Use for callouts and platform events (after commit)
// after insert — create a related task for each new opportunity
trigger OpportunityTrigger on Opportunity (after insert) {
    List<Task> tasks = new List<Task>();
    for (Opportunity opp : Trigger.new) {
        tasks.add(new Task(
            Subject      = 'Follow-up call',
            WhatId       = opp.Id,     // Id is now available
            ActivityDate = Date.today().addDays(3),
            OwnerId      = opp.OwnerId
        ));
    }
    if (!tasks.isEmpty()) insert tasks;
}
02

Trigger Context Variables

Apex exposes a rich set of implicit variables inside every trigger. These are the foundation of all trigger logic.

Trigger.new
List<SObject>
New versions of records being inserted or updated. Read-only in after triggers.
Trigger.old
List<SObject>
Original (pre-update) versions of records. Available in update and delete triggers.
Trigger.newMap
Map<Id,SObject>
Map of new record Id → new record. Not available in before insert (no Id yet).
Trigger.oldMap
Map<Id,SObject>
Map of record Id → old version. Available in update and delete triggers.
Trigger.isInsert
Boolean
True if trigger fired due to an insert DML.
Trigger.isUpdate
Boolean
True if trigger fired due to an update DML.
Trigger.isDelete
Boolean
True if trigger fired due to a delete DML.
Trigger.isUndelete
Boolean
True if trigger fired after an undelete operation.
Trigger.isBefore
Boolean
True if trigger is running before the DML commits.
Trigger.isAfter
Boolean
True if trigger is running after the DML commits.
Trigger.size
Integer
Total number of records in the current batch (max 200).
Trigger.isExecuting
Boolean
True when Apex is currently executing in a trigger context.

Detecting field changes with Trigger.old and Trigger.new

// only act on records where Stage actually changed
trigger OpportunityTrigger on Opportunity (after update) {
    List<Opportunity> closedWon = new List<Opportunity>();

    for (Opportunity opp : Trigger.new) {
        Opportunity oldOpp = Trigger.oldMap.get(opp.Id);

        // oldMap comparison prevents redundant processing
        Boolean justClosedWon = opp.StageName == 'Closed Won'
            && oldOpp.StageName != 'Closed Won';

        if (justClosedWon) {
            closedWon.add(opp);
        }
    }

    if (!closedWon.isEmpty()) {
        OpportunityTriggerHandler.processClosedWon(closedWon);
    }
}
03

Salesforce Order of Execution

Understanding the save order is critical for debugging unexpected trigger behaviour and designing reliable automations.

When a record is saved, Salesforce runs in this order:

  1. Loads the original record from the database
  2. Runs system validation rules (required fields, field type, max length)
  3. Executes all before triggers
  4. Runs custom validation rules
  5. Saves the record to the database (but does not commit)
  6. Executes all after triggers
  7. Executes assignment rules (Leads, Cases)
  8. Executes auto-response rules (Cases)
  9. Executes workflow rules (if any field update workflows fire, starts from step 1 again)
  10. Executes escalation rules
  11. Executes Flows (Record-Triggered)
  12. Commits the transaction to the database
  13. Executes post-commit logic (email alerts, outbound messages, async Apex)
⚠ Re-entry: If a workflow field update fires, the trigger runs again — steps 1–9 repeat. This is one source of infinite recursion. Protect with a static Boolean flag.

The Trigger Handler Framework

A trigger handler framework separates the trigger shell (event routing) from business logic (handler class). This is the industry-standard pattern for production orgs.

Abstract Base Handler (reusable across objects)

// Base class — all handlers extend this
public virtual class TriggerHandler {

    // Recursion guard — static so it persists in the transaction
    private static Set<String> bypassedHandlers = new Set<String>();

    public static void bypass(String handlerName) {
        bypassedHandlers.add(handlerName);
    }
    public static void clearBypass(String handlerName) {
        bypassedHandlers.remove(handlerName);
    }
    private Boolean isBypassed() {
        return bypassedHandlers.contains(
            String.valueOf(this).split(':')[0]);
    }

    // Entry point — called from trigger
    public void run() {
        if (isBypassed()) return;

        if (Trigger.isBefore) {
            if (Trigger.isInsert)  beforeInsert(Trigger.new);
            if (Trigger.isUpdate)  beforeUpdate(Trigger.new, Trigger.oldMap);
            if (Trigger.isDelete)  beforeDelete(Trigger.old);
        } else {
            if (Trigger.isInsert)  afterInsert(Trigger.new);
            if (Trigger.isUpdate)  afterUpdate(Trigger.new, Trigger.oldMap);
            if (Trigger.isDelete)  afterDelete(Trigger.old);
            if (Trigger.isUndelete) afterUndelete(Trigger.new);
        }
    }

    // Virtual methods — override only what you need
    protected virtual void beforeInsert(List<SObject> newList)  {}
    protected virtual void beforeUpdate(List<SObject> newList,
        Map<Id,SObject> oldMap) {}
    protected virtual void beforeDelete(List<SObject> oldList)  {}
    protected virtual void afterInsert(List<SObject> newList)   {}
    protected virtual void afterUpdate(List<SObject> newList,
        Map<Id,SObject> oldMap) {}
    protected virtual void afterDelete(List<SObject> oldList)   {}
    protected virtual void afterUndelete(List<SObject> newList) {}
}

Concrete Handler — Account

public with sharing class AccountTriggerHandler extends TriggerHandler {

    protected override void beforeInsert(List<SObject> newList) {
        List<Account> accounts = (List<Account>) newList;
        setDefaultRating(accounts);
    }

    protected override void afterInsert(List<SObject> newList) {
        List<Account> accounts = (List<Account>) newList;
        createWelcomeTask(accounts);
    }

    protected override void beforeUpdate(List<SObject> newList,
            Map<Id,SObject> oldMap) {
        List<Account> accounts = (List<Account>) newList;
        Map<Id,Account> oldAccMap = (Map<Id,Account>) oldMap;
        validateNameChange(accounts, oldAccMap);
    }

    // ---- private helpers ----------------------------------------

    private void setDefaultRating(List<Account> accounts) {
        for (Account acc : accounts) {
            if (acc.Rating == null) acc.Rating = 'Warm';
        }
    }

    private void createWelcomeTask(List<Account> accounts) {
        List<Task> tasks = new List<Task>();
        for (Account acc : accounts) {
            tasks.add(new Task(
                Subject      = 'Welcome call',
                WhatId       = acc.Id,
                ActivityDate = Date.today().addDays(1)
            ));
        }
        if (!tasks.isEmpty()) insert tasks;
    }

    private void validateNameChange(List<Account> accounts,
            Map<Id,Account> oldMap) {
        for (Account acc : accounts) {
            if (acc.Name != oldMap.get(acc.Id).Name) {
                // log the change
            }
        }
    }
}

// Trigger — one line of real logic
trigger AccountTrigger on Account (
    before insert, before update, before delete,
    after  insert, after  update, after  delete, after undelete
) {
    new AccountTriggerHandler().run();
}

Essential Trigger Patterns

🔄

Recursion Prevention

After triggers that perform DML will re-fire the trigger. A static Boolean flag stops the second execution.

  • Static variable persists for the whole transaction
  • Set it to true before the DML that would re-trigger
  • Check it at the very top of the handler
  • More advanced: use the bypass set from the framework above
public with sharing class ContactTriggerHandler {
    // Static — shared across all calls in the transaction
    private static Boolean hasRun = false;

    public void afterUpdate(List<Contact> newList,
            Map<Id, Contact> oldMap) {
        if (hasRun) return; // prevent recursion
        hasRun = true;

        // Logic that causes an update DML (which re-fires trigger)
        List<Contact> toUpdate = new List<Contact>();
        for (Contact c : newList) {
            if (c.Title != oldMap.get(c.Id).Title) {
                c.Description = 'Title updated: ' + c.Title;
                toUpdate.add(c);
            }
        }
        if (!toUpdate.isEmpty()) update toUpdate;
    }
}
📊

Bulk Pattern (Map-Based Lookup)

The canonical pattern for relating child records to their parents without SOQL in a loop.

  • Collect all parent Ids in a Set from the trigger batch
  • Query all parent records in one SOQL
  • Build a Map for O(1) lookup
  • Process all children in a single loop
  • Collect updates, then bulk DML once
// After insert on Opportunity — update parent Account's Rating
trigger OpportunityTrigger on Opportunity (after insert) {

    // 1. Collect parent IDs
    Set<Id> accountIds = new Set<Id>();
    for (Opportunity opp : Trigger.new) {
        if (opp.AccountId != null) accountIds.add(opp.AccountId);
    }

    // 2. One SOQL query — build Map
    Map<Id, Account> accountMap = new Map<Id, Account>(
        [SELECT Id, Rating FROM Account WHERE Id IN :accountIds]
    );

    // 3. Process — no SOQL inside loop
    List<Account> toUpdate = new List<Account>();
    for (Opportunity opp : Trigger.new) {
        Account acc = accountMap.get(opp.AccountId);
        if (acc != null && opp.Amount > 100000) {
            acc.Rating = 'Hot';
            toUpdate.add(acc);
        }
    }

    // 4. One bulk DML
    if (!toUpdate.isEmpty()) update toUpdate;
}
❌

addError() — Blocking Saves

Call addError() in a before trigger to block the save and show the user an error message.

  • Call on the record: record.addError('message')
  • Call on a field: record.FieldName.addError('msg')
  • Rolls back the entire transaction
  • Error appears on the UI record page and in API responses
  • Only works in before triggers
trigger ContactTrigger on Contact (before insert, before update) {
    for (Contact c : Trigger.new) {
        // Validate domain whitelist
        if (!String.isBlank(c.Email) &&
            !c.Email.endsWith('@trusted.com')) {
            // Field-level error — shows on the Email field
            c.Email.addError(
                'Only @trusted.com email addresses are allowed.'
            );
        }
        // Record-level error
        if (c.Birthdate != null &&
            c.Birthdate > Date.today()) {
            c.addError('Birthdate cannot be in the future.');
        }
    }
}
🛑

Trigger Bypass via Custom Metadata

Allow admins to disable a trigger without a deployment, using Custom Metadata or Custom Settings.

  • Create a Custom Metadata Type: Trigger_Setting__mdt
  • Fields: Object API Name, Is_Active__c
  • Query in the trigger; skip if not active
  • No code deployment needed to enable/disable
// Custom Metadata Type: Trigger_Setting__mdt
// Fields: Object_Name__c (text), Is_Active__c (checkbox)

public with sharing class TriggerSettings {
    private static Map<String, Boolean> cache;

    public static Boolean isActive(String objectName) {
        if (cache == null) {
            cache = new Map<String, Boolean>();
            for (Trigger_Setting__mdt s :
                    [SELECT Object_Name__c, Is_Active__c
                     FROM Trigger_Setting__mdt]) {
                cache.put(s.Object_Name__c, s.Is_Active__c);
            }
        }
        return cache.containsKey(objectName)
            ? cache.get(objectName)
            : true; // default active if no record found
    }
}

// In trigger
trigger AccountTrigger on Account (before insert) {
    if (!TriggerSettings.isActive('Account')) return;
    new AccountTriggerHandler().run();
}

Best Practices

One Trigger Per Object

Multiple triggers on the same object fire in unpredictable order. One trigger delegates to one handler class.

❌ AccountTrigger1.trigger + AccountTrigger2.trigger
✅ AccountTrigger.trigger → AccountTriggerHandler.cls

No Logic in the Trigger File

The trigger file should only route events. All business logic lives in the handler class, making it unit-testable without DML triggers.

❌ trigger T on Account (before insert) { for (Account a : Trigger.new) { a.Rating = 'Warm'; } }
✅ trigger T on Account (before insert) { new AccountTriggerHandler().run(); }

Bulkify — Never SOQL or DML in Loops

Triggers process up to 200 records at once. Every loop iteration that issues a query wastes a governor limit slot.

❌ for (Account a : Trigger.new) { insert new Task(WhatId = a.Id); }
✅ List<Task> tasks = new List<Task>(); for (...) { tasks.add(...); } insert tasks;

Use before for Field Defaults

In before triggers, modifications to Trigger.new are saved automatically — no extra DML needed, saving a DML statement.

❌ after insert → update records; (wastes a DML statement)
✅ before insert → set fields on Trigger.new directly

Prevent Recursion with Static Guards

after triggers that issue DML will re-fire the trigger. Use a static Boolean or the handler bypass pattern to prevent infinite loops.

❌ No guard → after update DML re-fires → LimitException
✅ if (hasRun) return; hasRun = true;

Use addError() for User-Facing Validation

addError() blocks the save at the database level and surfaces the message in the UI — far better than throwing an exception.

❌ throw new ValidationException('Bad email');
✅ record.Email.addError('Only @trusted.com allowed.');
