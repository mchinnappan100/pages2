01

@future Methods

The simplest form of async Apex. A @future method is fire-and-forget — it runs in a separate, queued transaction with a higher governor limit budget.

🚀

@future Syntax & Rules

Simple, stateless async execution. Ideal for one-off async operations and callouts from triggers.

  • Must be static
  • Return type must be void
  • Parameters must be primitive or collections of primitives — no sObjects
  • Cannot call another @future method
  • Max 50 @future calls per transaction
  • Add (callout=true) to allow HTTP callouts
public with sharing class IntegrationService {

    // @future with callout=true — for making HTTP requests
    @future(callout=true)
    public static void syncToExternalSystem(List<Id> accountIds) {
        // Runs in a separate transaction — fresh limits
        List<Account> accounts =
            [SELECT Id, Name, Phone FROM Account
             WHERE Id IN :accountIds];

        // Build JSON payload
        String payload = JSON.serialize(accounts);

        // Make HTTP callout
        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:My_Named_Credential/api/sync');
        req.setMethod('POST');
        req.setBody(payload);
        req.setHeader('Content-Type', 'application/json');

        Http http = new Http();
        HttpResponse res = http.send(req);
        System.debug('Response: ' + res.getStatusCode());
    }
}

// Calling from a trigger (cannot make callout directly)
trigger AccountTrigger on Account (after insert) {
    List<Id> ids = new List<Id>();
    for (Account a : Trigger.new) ids.add(a.Id);
    IntegrationService.syncToExternalSystem(ids);
}
⚠️

@future Limitations

Know the constraints before choosing @future over Queueable.

  • No return value — fire-and-forget only
  • Cannot pass sObjects (only primitive Ids)
  • Cannot chain — @future cannot call @future
  • Cannot monitor execution status
  • Cannot be called from Batch Apex
  • Use Queueable when you need any of the above

Queueable Apex

Queueable is the modern, flexible replacement for @future. It is chainable, accepts complex types, and returns a job ID for monitoring.

Queueable — Chainable, Stateful Async

// Queueable class — implements Queueable interface
public with sharing class AccountSyncJob implements Queueable, Database.AllowsCallouts {

    private List<Account> accounts; // sObjects allowed!

    public AccountSyncJob(List<Account> accs) {
        this.accounts = accs;
    }

    public void execute(QueueableContext ctx) {
        // Full governor limits in this execution context
        for (Account acc : accounts) {
            // Make callout per account (or batch them)
            HttpRequest req = new HttpRequest();
            req.setEndpoint('callout:ERP/accounts/' + acc.Id);
            req.setMethod('PUT');
            req.setBody(JSON.serialize(acc));
            new Http().send(req);
        }

        // CHAIN: enqueue next job when done
        // (max 1 chain in non-test context)
        if (!Test.isRunningTest()) {
            List<Account> remaining = getNextBatch();
            if (!remaining.isEmpty()) {
                System.enqueueJob(new AccountSyncJob(remaining));
            }
        }
    }

    private List<Account> getNextBatch() {
        // Return next batch to process (pagination logic)
        return new List<Account>();
    }
}

// Enqueue the job — returns a Job ID
Id jobId = System.enqueueJob(new AccountSyncJob(accounts));
System.debug('Queued job: ' + jobId);
Queueable advantages over @future: Accepts sObjects and non-primitive types; chainable; returns a job ID for monitoring; can implement Database.AllowsCallouts for HTTP callouts; easier to test.

Batch Apex

Batch Apex is designed for processing massive data volumes — millions of records — by breaking them into governor-safe chunks of up to 2,000 records each.

Database.Batchable — The Three Methods

global with sharing class ContactCleanupBatch
    implements Database.Batchable<SObject>, Database.Stateful {

    // Database.Stateful — instance variables persist across execute() calls
    global Integer totalProcessed = 0;
    global Integer totalUpdated   = 0;

    // 1. start() — defines what records to process
    global Database.QueryLocator start(Database.BatchableContext bc) {
        // QueryLocator supports up to 50M rows; no heap concern
        return Database.getQueryLocator(
            'SELECT Id, Email, Phone FROM Contact WHERE IsActive__c = true'
        );
    }

    // 2. execute() — called once per chunk (default 200, max 2000 records)
    global void execute(Database.BatchableContext bc, List<SObject> scope) {
        List<Contact> contacts = (List<Contact>) scope;
        List<Contact> toUpdate = new List<Contact>();

        for (Contact c : contacts) {
            totalProcessed++;
            if (String.isBlank(c.Email)) {
                c.DoNotCall = true;
                toUpdate.add(c);
                totalUpdated++;
            }
        }

        if (!toUpdate.isEmpty()) {
            Database.update(toUpdate, false); // partial success
        }
    }

    // 3. finish() — runs once after all chunks complete
    global void finish(Database.BatchableContext bc) {
        // Send summary email
        Messaging.SingleEmailMessage mail = new Messaging.SingleEmailMessage();
        mail.setToAddresses(new List<String>{'admin@example.com'});
        mail.setSubject('Batch Complete');
        mail.setPlainTextBody(
            'Processed: ' + totalProcessed +
            ' | Updated: ' + totalUpdated
        );
        Messaging.sendEmail(new List<Messaging.SingleEmailMessage>{mail});
    }
}

// Launch the batch
Id batchId = Database.executeBatch(new ContactCleanupBatch(), 200);
📊

Batch Scope Size

The second parameter to Database.executeBatch() controls chunk size.

  • Default: 200 records per execute() call
  • Maximum: 2,000 records per execute() call
  • Use smaller chunks when using callouts (100 max)
  • Larger chunks = fewer transactions = faster overall
  • Max 5 active batches queued/running simultaneously
💾

Database.Stateful

Without Stateful, instance variables reset between execute() calls. Add it to maintain running totals or error lists.

  • Without Stateful: each execute() starts fresh
  • With Stateful: instance variables persist across all chunks
  • Use for counters, error collections, progress tracking
  • Stateful batches are slightly slower — use only when needed

Scheduled Apex

Scheduled Apex runs on a cron schedule. Use it to kick off batch jobs, clean up data, or send reports at regular intervals.

Schedulable Interface

// A class that can be scheduled
global with sharing class DailyReportScheduler implements Schedulable {

    global void execute(SchedulableContext ctx) {
        // Common pattern: launch a batch from a scheduler
        Database.executeBatch(new ContactCleanupBatch(), 200);
    }
}

// Schedule via Apex (in Developer Console / anonymous Apex)
// Cron expression: Seconds Minutes Hours Day Month DayOfWeek Year
// Run every day at 2 AM
String cron = '0 0 2 * * ?';
String jobName = 'Daily Contact Cleanup';
System.schedule(jobName, cron, new DailyReportScheduler());

// Schedule via UI: Setup → Apex Classes → Schedule Apex
// Or query scheduled jobs:
// SELECT Id, CronExpression, State FROM CronTrigger
Cron syntax: Seconds Minutes Hours Day_of_Month Month Day_of_Week [Year]. Use ? for "don't care" in Day_of_Month or Day_of_Week. Max 100 scheduled jobs per org.

HTTP Callouts & Named Credentials

Apex can call external REST and SOAP services. Callouts from synchronous context (triggers) must be made via @future or Queueable to avoid the mixed DML/callout restriction.

REST Callout with Named Credential

@future(callout=true)
public static void fetchWeatherData(String city) {
    // Named Credential handles auth — no hard-coded credentials
    HttpRequest req = new HttpRequest();
    req.setEndpoint('callout:WeatherAPI/current?city=' + city);
    req.setMethod('GET');
    req.setTimeout(10000); // 10 seconds

    Http http = new Http();
    HttpResponse res;
    try {
        res = http.send(req);
        if (res.getStatusCode() == 200) {
            Map<String, Object> data =
                (Map<String, Object>) JSON.deserializeUntyped(res.getBody());
            String temp = String.valueOf(data.get('temperature'));
            System.debug('Temperature in ' + city + ': ' + temp);
        } else {
            System.debug('Error: ' + res.getStatusCode()
                + ' ' + res.getStatus());
        }
    } catch (CalloutException e) {
        System.debug('Callout failed: ' + e.getMessage());
    }
}

// In tests: mock the response with HttpCalloutMock
@IsTest
class CalloutTest {
    @IsTest static void testWeather() {
        Test.setMock(HttpCalloutMock.class, new WeatherMock());
        Test.startTest();
        IntegrationService.fetchWeatherData('London');
        Test.stopTest();
    }
}

Best Practices

Choose the Right Async Type

Use @future for simple one-off async. Use Queueable for complex types or chaining. Use Batch for millions of records. Use Scheduled to kick off batch on a timer.

❌ Using @future when you need chaining or sObject params
✅ Queueable for chaining, Batch for volume, @future for simple callouts

Never Make Callouts from Triggers Directly

Triggers that have performed DML cannot make callouts in the same transaction. Dispatch to @future(callout=true) or Queueable + Database.AllowsCallouts.

❌ Callout directly in after insert trigger
✅ @future(callout=true) called from trigger

Use Named Credentials

Never hard-code credentials or endpoint URLs. Named Credentials store auth separately, support OAuth, and are environment-specific.

❌ req.setEndpoint('https://api.example.com?key=abc123');
✅ req.setEndpoint('callout:MyNamedCredential/path');

Use Database.Stateful Sparingly

Stateful batches consume more resources. Only implement it when you genuinely need to accumulate data across chunks (e.g., error summaries, running totals).

❌ implements Database.Batchable, Database.Stateful // always
✅ Add Database.Stateful only when state between chunks is required

Always Implement finish() Notifications

Batch jobs run asynchronously. If they fail silently, you won't know. Use finish() to send an email, create a record, or fire a Platform Event.

❌ global void finish(Database.BatchableContext bc) { }
✅ finish() sends summary email or Platform Event on completion

Mock Callouts in Tests

Real HTTP callouts are not allowed in tests. Always register an HttpCalloutMock to return a controlled response and test both success and error paths.

❌ Test fails with "Callouts not allowed" error
✅ Test.setMock(HttpCalloutMock.class, new MyMock());
