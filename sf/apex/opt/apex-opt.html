01

Executive Summary

Salesforce Apex applications frequently access metadata, configuration, and effectively immutable information multiple times within the same transaction — yet the underlying data does not change during the transaction's lifetime. The Apex Runtime Optimization Engine (AROE) intercepts these redundant retrievals transparently, inside the runtime itself, with no external tools, no plugins, and no code changes required from the developer.

Redundant Patterns Eliminated Automatically

  • Repeated Custom Metadata Type queries
  • Repeated Custom Settings lookups
  • Repeated Schema.describe calls
  • Repeated configuration record retrievals
  • Repeated object/field metadata resolution
  • Repeated framework initialization

The Runtime Does The Work

  • Optimization happens inside the Apex Runtime — not a linter, not a CLI, not a plugin
  • Developers write ordinary Apex — the engine handles deduplication
  • Works automatically for existing code and managed packages
  • Inspired by compiler CSE, loop-invariant code motion, and memoization
02

Problem Statement

A common Apex pattern retrieves the same configuration object multiple times within a single method. When ConfigService.getConfig('ORDER') executes the same metadata lookup three times, the transaction performs unnecessary work.

Explicitly Out of Scope (v1)

05

Key Concept

The developer does not need to know that the optimization occurred. No annotations. No plugins. No CLI. The runtime intercepts eligible calls, serves the cached result, and the developer's code behaves identically — with less work done.

06

Internal AST Analysis — No External Tool Needed

The runtime represents Apex code as an internal Abstract Syntax Tree and compares call sites based on class, method, arguments, receiver, context, and data dependencies to identify redundant computation — all inside the runtime, invisible to the developer. No external analyzer, linter, or plugin is invoked.

How the Runtime Detects Redundancy

The runtime's internal analysis pipeline identifies redundant computation as a normal step during Apex execution. No developer action is required — the runtime observes call patterns, checks its purity catalog, and manages the transaction cache transparently.

09

Internal Control & Data Flow Analysis

Simple call matching is insufficient — the runtime uses internal control and data flow analysis to handle branches, loops, variable mutations, and multiple execution paths, all without surfacing these details to the developer.

Internal Runtime Analysis (no external tool) ═══════════════════════════════════════════ AST ↓ Control Flow Graph ← built inside runtime ↓ Data Flow Analysis ← built inside runtime ↓ Redundant Computation Detection ↓ Purity Catalog Check ↓ Transaction Cache → result reused silently
10

Loop Invariant Code Motion — Automatic

Metadata lookup inside a loop processing 1,000 records causes 1,000 redundant metadata calls. The runtime detects this automatically and reuses the transaction cache for every iteration after the first — no developer annotation or external tool needed.

11

Compiler Optimization Analogies

Dead-Code Elimination

Remove code paths that can never execute.

Common Subexpression Elimination

Detect identical subexpressions and compute them only once. The most relevant analogy for this proposal.

Loop-Invariant Code Motion

Hoist computations outside loops when the value doesn't change per iteration.

Memoization

Cache function results keyed on arguments — the core mechanism of the runtime optimizer.

Constant Propagation

Recognize that two variables holding the same literal constant produce identical call arguments.

Transaction-Local Caching

Scope the cache to a single transaction to preserve correctness guarantees.

12

Runtime Transaction Cache

The cache lives only for the duration of the transaction. When the transaction ends, the cache is discarded. This avoids correctness concerns associated with persistent caching while eliminating redundant work.

Cache Key Structure

A transaction cache key conceptually contains: Namespace + Metadata Operation + Object/Type + Arguments + Relevant API Version.

Eligibility Model

Tier 1 — Safe

Known Immutable Metadata

  • Field metadata
  • Describe information
  • Platform metadata definitions
Tier 2 — Conditional

Transaction-Stable Operations

  • Configuration services
  • Framework metadata providers
  • Cached platform services
Tier 3 — Unsafe

Mutable Application Data

  • Arbitrary SOQL queries
  • DML-adjacent state
  • User-context-dependent data
14

Metadata Purity Contract

PURE

Same inputs → same result, no side effects. Strong optimization candidate.

TRANSACTION_STABLE

Result stable within transaction, may depend on transaction context. Optimizable.

MUTABLE

Result can change during the transaction. Do not optimize.

UNKNOWN

Purity cannot be proven. Conservative default — do not optimize.

Correctness & Security Considerations

Side Effects Must Not Be Memoized

Methods that increment counters, write DML, or modify state must never be cached regardless of argument similarity.

Mutable Data

SOQL queries may observe DML changes mid-transaction. These must remain in Tier 3 and never be auto-cached.

User Context Isolation

The cache key and eligibility model must account for User, Permission, Sharing, Locale, Currency, and Session context.

Cross-User Safety

Transaction-local scope substantially reduces the risk of User A's result leaking to User B. The runtime must enforce this boundary.

Proposed MVP — Four Phases

Phase 1 — Runtime Foundation

Built-in Purity Catalog & Transaction Cache

  • Internal purity catalog for known Salesforce metadata APIs
  • Transaction-local cache for Schema describe, Custom Metadata, known immutable metadata
  • Zero developer action — existing code benefits immediately
  • Measure: CPU, heap, latency, cache hit rate
Phase 2 — Internal Analysis

Internal AST + Control Flow + Data Flow

  • Runtime builds internal CFG and data-flow graph during execution
  • Detects repeated describe calls, Custom Metadata access, loop-invariant metadata
  • Still no external tools — all analysis runs inside the runtime
Phase 3 — Deeper Optimization

Common Subexpression Elimination & Loop Motion

  • CSE: identical subexpressions computed only once per transaction
  • Loop invariant code motion applied automatically
  • Constant propagation for argument equivalence detection
Phase 4 — Adaptive Runtime

Telemetry-Driven Adaptive Optimization

  • Aggregate runtime telemetry identifies high-frequency redundant patterns
  • Platform continuously expands the purity catalog
  • Runtime self-improves without developer involvement
