Apex Unit Testing

Apex requires ≥75% code coverage to deploy. But coverage is a floor, not a goal. Write tests that assert correct behaviour — not just execution.

🧪

Anatomy of a Test Class

Every test class must be annotated with @IsTest and cannot contain logic that runs in production.

  • @IsTest on the class
  • @IsTest on each test method
  • Test.startTest() / Test.stopTest() reset limits and flush async
  • System.assertEquals(expected, actual, msg)
  • System.assertNotEquals() and System.assert()
  • @TestSetup — shared test data created once
@IsTest
private class DiscountCalculatorTest {

    // @TestSetup runs once; data is rolled back after each test
    @TestSetup
    static void makeData() {
        Account acc = new Account(Name = 'Test Corp', Type = 'Customer');
        insert acc;
    }

    @IsTest
    static void testApplyDiscount_happyPath() {
        // Arrange
        Account acc = [SELECT Id FROM Account WHERE Name = 'Test Corp' LIMIT 1];
        DiscountCalculator calc = new DiscountCalculator(100);

        // Act
        Test.startTest();
        Decimal result = calc.applyDiscount(10);
        Test.stopTest();

        // Assert
        System.assertEquals(90, result,
            'A 10% discount on 100 should equal 90');
    }

    @IsTest
    static void testApplyDiscount_zeroDiscount() {
        DiscountCalculator calc = new DiscountCalculator(50);
        System.assertEquals(50, calc.applyDiscount(0),
            'Zero discount should return original price');
    }

    @IsTest
    static void testApplyDiscount_negativeThrows() {
        DiscountCalculator calc = new DiscountCalculator(100);
        try {
            calc.applyDiscount(-5);
            System.assert(false, 'Expected exception was not thrown');
        } catch (IllegalArgumentException e) {
            System.assert(e.getMessage().contains('negative'),
                'Error message should mention negative');
        }
    }
}
🏭

Test Data Factory Pattern

A single TestDataFactory class creates reusable test records across all test classes.

  • Centralises record creation logic
  • Changes to required fields updated in one place
  • Annotate the factory with @IsTest
  • Returns Lists for bulk test scenarios
  • Supports both inserted and uninserted records
  • Prevents duplicated setup code across tests
@IsTest
public class TestDataFactory {

    public static Account createAccount(Boolean doInsert) {
        Account acc = new Account(
            Name    = 'Test Account',
            Type    = 'Customer',
            Industry = 'Technology'
        );
        if (doInsert) insert acc;
        return acc;
    }

    public static List<Contact> createContacts(
            Account acc, Integer count, Boolean doInsert) {
        List<Contact> contacts = new List<Contact>();
        for (Integer i = 0; i < count; i++) {
            contacts.add(new Contact(
                FirstName = 'Test',
                LastName  = 'Contact' + i,
                Email     = 'test' + i + '@factory.com',
                AccountId = acc.Id
            ));
        }
        if (doInsert) insert contacts;
        return contacts;
    }

    public static Opportunity createOpportunity(
            Account acc, Boolean doInsert) {
        Opportunity opp = new Opportunity(
            Name       = 'Test Opp',
            AccountId  = acc.Id,
            StageName  = 'Prospecting',
            CloseDate  = Date.today().addDays(30),
            Amount     = 10000
        );
        if (doInsert) insert opp;
        return opp;
    }
}

// Usage in any test class
@IsTest
static void myTest() {
    Account acc = TestDataFactory.createAccount(true);
    List<Contact> contacts = TestDataFactory.createContacts(acc, 5, true);
    System.assertEquals(5, contacts.size());
}

Testing Async Apex

Test.startTest() / Test.stopTest() is the key to testing async methods synchronously.

  • Test.stopTest() forces async to execute synchronously
  • @future, Queueable, and Batch all run at stopTest()
  • Test batch with Database.executeBatch() inside start/stop
  • Batch scope in tests defaults to 200 unless set
  • governor limits reset at startTest()
@IsTest
static void testBatchJob() {
    // Create 10 contacts with blank email
    Account acc = TestDataFactory.createAccount(true);
    List<Contact> contacts = new List<Contact>();
    for (Integer i = 0; i < 10; i++) {
        contacts.add(new Contact(
            LastName  = 'Test' + i,
            AccountId = acc.Id
            // Email deliberately blank
        ));
    }
    insert contacts;

    Test.startTest();
    // Execute batch — runs synchronously at stopTest()
    Id batchId = Database.executeBatch(
        new ContactCleanupBatch(), 200);
    Test.stopTest();

    // Assert results after batch completes
    List<Contact> updated = [SELECT DoNotCall FROM Contact
                               WHERE AccountId = :acc.Id];
    for (Contact c : updated) {
        System.assertEquals(true, c.DoNotCall,
            'Contacts without email should be marked DoNotCall');
    }
}

// Testing Queueable
@IsTest
static void testQueueable() {
    Account acc = TestDataFactory.createAccount(true);
    Test.startTest();
    System.enqueueJob(new AccountSyncJob(
        new List<Account>{acc}));
    Test.stopTest();
    // Assert side effects
}

Mocking Callouts

HTTP callouts are blocked in tests. Use HttpCalloutMock to return controlled responses.

  • Implement HttpCalloutMock interface
  • Return a preset HttpResponse
  • Register with Test.setMock()
  • Write separate mocks for success and error paths
  • Also mock external web services: WebServiceMock
  • Use StaticResourceCalloutMock for large payloads
// Mock implementation
@IsTest
global class SuccessCalloutMock implements HttpCalloutMock {
    global HttpResponse respond(HttpRequest req) {
        HttpResponse res = new HttpResponse();
        res.setStatusCode(200);
        res.setHeader('Content-Type', 'application/json');
        res.setBody('{"status":"ok","id":"12345"}');
        return res;
    }
}

@IsTest
global class ErrorCalloutMock implements HttpCalloutMock {
    global HttpResponse respond(HttpRequest req) {
        HttpResponse res = new HttpResponse();
        res.setStatusCode(500);
        res.setBody('{"error":"Internal Server Error"}');
        return res;
    }
}

// Using the mock in a test
@IsTest
static void testCallout_success() {
    Test.setMock(HttpCalloutMock.class, new SuccessCalloutMock());
    Test.startTest();
    IntegrationService.syncToExternalSystem(
        new List<Id>{ [SELECT Id FROM Account LIMIT 1].Id });
    Test.stopTest();
    // Assert the sync logged correctly
}

@IsTest
static void testCallout_error() {
    Test.setMock(HttpCalloutMock.class, new ErrorCalloutMock());
    Test.startTest();
    IntegrationService.syncToExternalSystem(
        new List<Id>{ [SELECT Id FROM Account LIMIT 1].Id });
    Test.stopTest();
    // Assert error was handled gracefully
}

Code Coverage — The Right Way

75% coverage is the deployment minimum. World-class orgs aim for 90%+ with meaningful assertions — not just code execution.

Coverage Anti-Patterns to Avoid

  • Coverage without assertions: running code counts toward coverage but verifies nothing. Always assert.
  • SeeAllData=true: Never use @IsTest(SeeAllData=true) — it makes tests org-dependent and brittle.
  • Hard-coded Ids: Record Ids differ between orgs. Use queries or TestDataFactory.
  • Testing only the happy path: Test null inputs, empty lists, boundary conditions, and exception paths.
⚠ SeeAllData=true is banned in production-quality code: Tests that depend on org data break when data changes or when deployed to a fresh org. Create all test data explicitly inside the test or TestSetup method.

Apex Security: Sharing, FLS & CRUD

Salesforce has three layers of security that Apex code can enforce or bypass. Understand each layer and code defensively.

🔒

Record-Level Security (Sharing)

Controls which records a user can see, based on OWD, role hierarchy, and sharing rules.

  • with sharing — enforces sharing rules
  • without sharing — bypasses sharing
  • inherited sharing — uses caller's context
  • Default (no keyword) = inherits from calling class
  • Always use with sharing as default
  • Only use without sharing with explicit justification
// DEFAULT — use for all service classes
public with sharing class AccountService {
    public List<Account> getMyAccounts() {
        // Only returns accounts the running user can see
        return [SELECT Id, Name FROM Account];
    }
}

// WITHOUT SHARING — explicit bypass (document WHY)
// Use case: system-level operation that must see all records
// e.g., data migration run by admin-level process
public without sharing class DataMigrationHelper {
    // Runs as system — ignores sharing rules
    public void processAllRecords() {
        for (Account a : [SELECT Id FROM Account]) {
            // process regardless of visibility
        }
    }
}

// INHERITED SHARING — pass-through
// The sharing context of the CALLER is used
public inherited sharing class SharedUtility {
    public static Integer countRecords(String objectName) {
        // Visibility depends on who calls this
        return Database.countQuery(
            'SELECT COUNT() FROM ' + objectName);
    }
}
🔐

Field-Level Security (FLS) & CRUD

Enforce object and field access programmatically for defence-in-depth.

  • WITH SECURITY_ENFORCED in SOQL (API 48+)
  • Security.stripInaccessible() — remove inaccessible fields post-query
  • Check CRUD: Schema.SObjectType.Account.isCreateable()
  • Check FLS: Schema.SObjectType.Account.fields.Name.isAccessible()
  • UserInfo.getUserType() for context-aware checks
  • stripInaccessible before returning data to LWC
// stripInaccessible — remove fields the user can't see
public with sharing class SecureAccountController {
    @AuraEnabled(cacheable=true)
    public static List<Account> getAccounts() {
        List<Account> accs =
            [SELECT Id, Name, AnnualRevenue, SSN__c
             FROM Account LIMIT 100];

        // Strip fields user cannot read
        SObjectAccessDecision decision =
            Security.stripInaccessible(
                AccessType.READABLE, accs);

        return decision.getRecords();
    }

    // CRUD check before DML
    public static void createAccount(Account acc) {
        if (!Schema.SObjectType.Account.isCreateable()) {
            throw new SecurityException(
                'Insufficient privileges to create Account');
        }
        insert acc;
    }
}

// WITH SECURITY_ENFORCED in SOQL
List<Account> secure =
    [SELECT Id, Name, AnnualRevenue
     FROM Account
     WITH SECURITY_ENFORCED // throws if user can't read any field
     LIMIT 100];
💉

SOQL Injection Prevention

SOQL injection is the #1 Apex security vulnerability. Always use bind variables or escape user input.

  • Never concatenate user input directly into SOQL
  • Use bind variables in static SOQL: WHERE Name = :name
  • For dynamic SOQL: String.escapeSingleQuotes(input)
  • Whitelist allowed field/object names
  • Use Schema.getGlobalDescribe() to validate object names
  • Run the Security Source Scanner / Checkmarx in CI
// ❌ VULNERABLE — user can inject: ' OR Name != '
public List<Account> searchVulnerable(String searchTerm) {
    return Database.query(
        'SELECT Id FROM Account WHERE Name LIKE \'%'
        + searchTerm + '%\''  // DANGER: raw concat
    );
}

// ✅ SAFE — bind variable in static SOQL
public List<Account> searchSafe(String searchTerm) {
    String pattern = '%' + searchTerm + '%';
    return [SELECT Id, Name FROM Account WHERE Name LIKE :pattern];
}

// ✅ SAFE — dynamic SOQL with escapeSingleQuotes
public List<Account> searchDynamic(String searchTerm) {
    String safe = '%' + String.escapeSingleQuotes(searchTerm) + '%';
    return Database.query(
        'SELECT Id, Name FROM Account WHERE Name LIKE \'' + safe + '\''
    );
}

// ✅ Whitelist-validated object names for dynamic queries
public Integer countSafe(String objectApiName) {
    // Validate object exists via Schema
    if (!Schema.getGlobalDescribe().containsKey(objectApiName)) {
        throw new IllegalArgumentException('Invalid object: ' + objectApiName);
    }
    return Database.countQuery('SELECT COUNT() FROM ' + objectApiName);
}

Deployment Strategies

Apex code is metadata that must be deployed — not published. Choose the right tool for each scenario.

SFDX / Salesforce CLI — The Modern Standard

// Deploy specific metadata to target org
sf project deploy start \
  --source-dir force-app/main/default/classes/AccountService.cls \
  --target-org my-sandbox

// Deploy and run all tests
sf project deploy start \
  --source-dir force-app \
  --test-level RunAllTestsInOrg \
  --target-org production

// Retrieve changes from org
sf project retrieve start \
  --metadata ApexClass:AccountService \
  --target-org my-sandbox

// Run tests only
sf apex run test \
  --class-names AccountServiceTest \
  --target-org my-sandbox \
  --result-format human

// Scratch org workflow
sf org create scratch --definition-file config/project-scratch-def.json
sf project deploy start --target-org scratch-org
sf apex run test --target-org scratch-org --result-format human
Deployment checklist: 75%+ overall code coverage · All test classes pass · No hard-coded Ids · Validation rules reviewed · Named Credentials configured in target org.
📦

Change Sets

UI-based deployment between connected orgs. Simple but limited.

  • No version control integration
  • Orgs must be connected in Setup
  • Outbound change set → upload → deploy
  • Cannot retrieve from org via change set
  • Cannot include profiles/permission sets easily
  • Best for simple one-off deployments
🚀

2nd-Generation Packages (2GP)

The enterprise standard for modular, versioned deployments.

  • Source-driven (stored in VCS)
  • Locked versioning — subscribers get specific version
  • Namespaced — prevents naming conflicts
  • Unlocked packages for internal apps
  • Managed packages for ISV/AppExchange
  • sf package version create

Best Practices

Assert Behaviour, Not Just Coverage

Every test method must have at least one System.assertEquals. Coverage without assertions is worthless.

❌ @IsTest static void test() { new MyClass().run(); } // no assert
✅ System.assertEquals(expected, actual, 'Descriptive failure message');

Never Use SeeAllData=true

Tests must create all their own data. Org-dependent tests break in sandboxes and fresh deployments.

❌ @IsTest(SeeAllData=true) // org data dependency
✅ TestDataFactory.createAccount(true); // self-contained

Test Edge Cases and Error Paths

Test null inputs, empty lists, the maximum limit, and exception scenarios — not just the golden path.

❌ Only test the success case with valid data
✅ Also test: null input, empty list, duplicate, over-limit, exception path

with sharing on Every Class

Sharing context has security implications. Be explicit — never let the context be ambiguous or inherited accidentally.

❌ public class MyService { } // sharing context unknown
✅ public with sharing class MyService { }

Use stripInaccessible Before Returning to LWC

Before returning query results to a Lightning component, strip fields the user cannot read to prevent data leakage.

❌ return [SELECT Id, SSN__c FROM Contact]; // may leak sensitive fields
✅ return Security.stripInaccessible(AccessType.READABLE, results).getRecords();

Deploy via SFDX, Not Change Sets

Change Sets have no version control, no rollback, and no automation. SFDX integrates with Git, CI/CD, and scratch orgs.

❌ Manual change set for every deployment
✅ sf project deploy start --test-level RunAllTestsInOrg
