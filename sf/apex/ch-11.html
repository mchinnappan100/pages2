Event-Driven Architecture Overview

Platform Events and CDC are Salesforce's implementation of the publish-subscribe (pub/sub) pattern. They decouple producers from consumers, enabling resilient, scalable integrations.

Platform Events

Custom event objects you define. Publishers push messages; any number of subscribers react independently. Events are retained for 72 hours (default) — missed events can be replayed.

  • Defined in Setup → Platform Events
  • Custom fields just like sObjects
  • Published via EventBus.publish() or DML insert
  • Subscribed via Apex trigger, Flow, or CometD

Change Data Capture (CDC)

Salesforce automatically generates change events for standard and custom objects. Subscribers receive the before/after state of every create, update, delete, and undelete.

  • Enable CDC in Setup → Change Data Capture
  • Subscribe via Apex trigger on AccountChangeEvent
  • Includes changed fields, header metadata, and Replay ID
  • 72-hour retention; up to 3-day replay

Defining Platform Events

Platform Event Object Definition (Setup)

// Platform Event: Order_Placed__e
// Fields: Order_Number__c (Text), Amount__c (Number),
//         Customer_Id__c (Text), Status__c (Text)

// In Apex the event is just an sObject with __e suffix
Order_Placed__e event = new Order_Placed__e(
    Order_Number__c = 'ORD-2024-001',
    Amount__c       = 599.99,
    Customer_Id__c  = '001000000000001',
    Status__c       = 'NEW'
);

// The __e suffix is what makes it a Platform Event, not a record
// Fields must be defined in Setup before using them here
03

Publishing Platform Events

📡

EventBus.publish()

The preferred method for publishing — decouples the event from the current DML transaction.

  • Published AFTER transaction commits
  • Transaction rollback does NOT cancel the event
  • Use when event should survive rollback
  • Returns Database.SaveResult[]
  • Errors in SaveResult, not exception
  • Max 150 calls per transaction
// Preferred: EventBus.publish() — event committed even if tx rolls back
public with sharing class OrderService {

    public static void placeOrder(Order__c order) {
        insert order; // DML

        // Publish event — decoupled from the insert transaction
        // If insert commits, the event fires regardless of what happens next
        Order_Placed__e event = new Order_Placed__e(
            Order_Number__c = order.OrderNumber__c,
            Amount__c       = order.TotalAmount__c,
            Customer_Id__c  = order.AccountId,
            Status__c       = 'NEW'
        );

        Database.SaveResult result = EventBus.publish(event);
        if (!result.isSuccess()) {
            for (Database.Error err : result.getErrors()) {
                System.debug('Event publish failed: ' + err.getMessage());
            }
        }
    }

    // Bulk publish
    public static void publishBatch(List<Order__c> orders) {
        List<Order_Placed__e> events = new List<Order_Placed__e>();
        for (Order__c o : orders) {
            events.add(new Order_Placed__e(
                Order_Number__c = o.OrderNumber__c,
                Amount__c       = o.TotalAmount__c
            ));
        }
        List<Database.SaveResult> results = EventBus.publish(events);
    }
}
⚠️

insert vs EventBus.publish()

Understanding the transactional difference is critical for reliability.

  • insert event — inside the transaction
  • If transaction rolls back, event is NOT sent
  • EventBus.publish() — outside transaction
  • Event IS sent even after rollback
  • Use insert only in tests or when rollback should cancel event
  • Default to EventBus.publish() in production

Subscribing with Apex Triggers

Platform Event Trigger

// Trigger on Platform Event — fires after event is published
// Only 'after insert' is supported for Platform Events
trigger OrderPlacedTrigger on Order_Placed__e (after insert) {

    List<Task> tasks = new List<Task>();

    for (Order_Placed__e event : Trigger.new) {
        // EventBus.TriggerContext provides event metadata
        System.debug('Replay ID: '
            + event.ReplayId);   // for replay/idempotency

        // React to the event — create a follow-up task
        if (event.Amount__c > 10000) {
            tasks.add(new Task(
                Subject      = 'High-value order review: '
                               + event.Order_Number__c,
                ActivityDate = Date.today().addDays(1),
                Priority     = 'High'
            ));
        }
    }

    if (!tasks.isEmpty()) insert tasks;
}

// Key facts about Platform Event triggers:
// - Only 'after insert' fires (events are immutable)
// - No Trigger.old / Trigger.oldMap
// - Governor limits: 200 SOQL queries, 150 DML (async limits)
// - Max 2,000 events per transaction batch
// - EventBus.TriggerContext.currentEvent() for resume token

ReplayId — At-Least-Once Delivery & Replay

// Platform Events are retained for 72 hours (standard) or 3 days (high-volume)
// Use ReplayId to resume from a specific event if a subscriber missed messages

// In a CometD subscriber (external), pass replayId:
// {"channel": "/event/Order_Placed__e", "replayFrom": -2}
// -1 = latest events only
// -2 = all retained events (replay from beginning of retention window)
// specific ID = replay from that event

// In Apex, access the Replay ID of the current event
trigger OrderPlacedTrigger on Order_Placed__e (after insert) {
    for (Order_Placed__e evt : Trigger.new) {
        String replayId = evt.ReplayId;
        // Store replayId in a Custom Setting to resume
        // from last-processed event on restart
        System.debug('Processing event ' + replayId);
    }
}

Change Data Capture (CDC)

CDC automatically generates change events whenever a record is created, updated, deleted, or undeleted. No custom event definition needed — just enable CDC and subscribe.

CDC Trigger — Reacting to Record Changes

// CDC trigger fires on AccountChangeEvent
// Enable CDC for Account in Setup → Change Data Capture
trigger AccountCDCTrigger on AccountChangeEvent (after insert) {

    for (AccountChangeEvent event : Trigger.new) {
        // ChangeEventHeader contains metadata about the change
        EventBus.ChangeEventHeader header = event.ChangeEventHeader;

        String changeType = header.changeType;
        // changeType: CREATE, UPDATE, DELETE, UNDELETE, GAP_CREATE,
        //             GAP_UPDATE, GAP_DELETE, GAP_UNDELETE

        List<String> changedFields = header.changedFields;
        List<String> recordIds    = header.recordIds;

        System.debug('Change type: ' + changeType);
        System.debug('Changed fields: ' + changedFields);
        System.debug('Affected records: ' + recordIds);

        if (changeType == 'UPDATE'
                && changedFields.contains('Industry')) {
            // React specifically to Industry field change
            handleIndustryChange(recordIds, event.Industry);
        }

        if (changeType == 'CREATE') {
            // New account created — sync to external system
            syncToExternalSystem(recordIds);
        }
    }
}

private static void handleIndustryChange(
        List<String> ids, String newIndustry) {
    // Update related records, notify downstream systems
    System.debug('Industry changed to: ' + newIndustry
                 + ' for ' + ids.size() + ' accounts');
}

private static void syncToExternalSystem(List<String> ids) {
    // Enqueue a Queueable for async callout
    System.enqueueJob(new AccountSyncJob(ids));
}
GAP events: If Salesforce cannot deliver all change events (e.g., high volume), it sends GAP events (GAP_CREATE, GAP_UPDATE). Your trigger must handle these gracefully — typically by re-querying the full record state.
06

Best Practices

Prefer EventBus.publish() Over insert

Events published with EventBus.publish() are sent even if the publishing transaction rolls back — making integrations more reliable.

❌ insert myEvent; // cancelled on rollback
✅ EventBus.publish(myEvent); // survives rollback

Make Subscribers Idempotent

Platform Events guarantee at-least-once delivery. Your subscriber might receive the same event twice. Use the ReplayId or a unique event field to detect and skip duplicates.

❌ Always process every event unconditionally
✅ Check processed event log by ReplayId before acting

Handle GAP Events in CDC Triggers

GAP events mean change events were missed. React by re-querying the full record state rather than relying on the (missing) delta.

❌ Ignore GAP_UPDATE events
✅ if (type.startsWith('GAP')) { reQueryAndSync(ids); }

Don't Put Heavy Logic in Event Triggers

Platform Event triggers run asynchronously with async governor limits. Keep them lightweight — enqueue a Queueable for heavy processing.

❌ 50 SOQL queries inside the event trigger
✅ System.enqueueJob(new ProcessEventJob(event.Id));

Use CDC Instead of After-Update Triggers for Integrations

CDC provides richer metadata (changed fields, before-state) and retains events for replay — far superior to a raw trigger for integration use cases.

❌ after update trigger → immediate callout
✅ CDC trigger → Queueable callout (decoupled, replayable)

Store ReplayId for Resumable Subscriptions

Persist the last-processed ReplayId in a Custom Setting. If your subscriber restarts, resume from the stored ID to avoid missing events during downtime.

✅ Custom_Setting__c.Last_Replay_Id__c = event.ReplayId;
