Classes, Constructors & Access Modifiers

Classes are the fundamental unit of code organisation. Understanding access modifiers and sharing keywords is essential for secure, well-designed Apex.

🏛️

Class Anatomy

Every production Apex class should follow this structure.

  • Access modifier: public (most common) or global (managed packages)
  • Sharing keyword: always declare with sharing
  • class keyword followed by class name (PascalCase)
  • Optional extends / implements
  • Instance variables, static variables, constructors, methods
public with sharing class OrderService {

    // Static constant
    private static final Integer MAX_LINE_ITEMS = 100;

    // Instance variable
    private String currency;

    // No-arg constructor
    public OrderService() {
        this('USD');
    }

    // Overloaded constructor
    public OrderService(String curr) {
        this.currency = curr;
    }

    // Instance method
    public Decimal calculateTotal(List<OrderItem__c> items) {
        Decimal total = 0;
        for (OrderItem__c item : items) {
            total += item.Quantity__c * item.UnitPrice__c;
        }
        return total;
    }

    // Static utility — no instantiation needed
    public static Boolean isValid(Order__c ord) {
        return ord != null && !String.isBlank(ord.Name);
    }
}
🔐

Access Modifiers

Access modifiers control visibility of classes, methods, and variables.

  • private — accessible only within the same class
  • protected — accessible in subclasses (virtual/abstract hierarchy)
  • public — accessible within same namespace
  • global — accessible across namespaces (managed packages)
  • Default (no modifier) = private for variables, public for outer class
public with sharing class BankAccount {
    private Decimal balance;      // only this class
    protected String currency;    // subclasses too
    public Id ownerId;            // any code in namespace
    public static Integer count;  // shared across all instances

    // Getter — exposes read-only access to private field
    public Decimal getBalance() {
        return balance;
    }

    // Private helper
    private void validate(Decimal amount) {
        if (amount <= 0) throw new IllegalArgumentException(
            'Amount must be positive');
    }

    public void deposit(Decimal amount) {
        validate(amount);
        balance += amount;
    }
}
🔄

Static vs. Instance Members

Static members belong to the class; instance members belong to each object.

  • Static variables are shared across all instances in a transaction
  • Static methods do not require object instantiation
  • Use static for utilities, caches, and factory methods
  • Static state persists for the lifetime of the transaction
  • Use ClassName.staticMethod() not instance.staticMethod()
public with sharing class TriggerHelper {
    // Static flag — prevents recursive trigger execution
    // Shared across ALL instances in this transaction
    public static Boolean hasRun = false;

    // Static factory method
    public static TriggerHelper getInstance() {
        return new TriggerHelper();
    }

    // Instance method — each object has its own state
    private List<String> log = new List<String>();

    public void addLog(String msg) {
        log.add(msg);
    }

    public List<String> getLog() {
        return log.clone();
    }
}
🏷️

Properties (get / set)

Apex supports property syntax with automatic backing variable or custom logic.

  • Auto-property: public String Name { get; set; }
  • Read-only: public String Name { get; private set; }
  • Custom logic in getter/setter blocks
  • Used heavily in Visualforce controller properties
public with sharing class Product {
    // Auto property
    public String Name { get; set; }

    // Read-only property
    public Id ProductCode { get; private set; }

    // Computed property with lazy-load
    private Decimal cachedTax;
    public Decimal TaxAmount {
        get {
            if (cachedTax == null) {
                cachedTax = Price * 0.08;
            }
            return cachedTax;
        }
    }

    // Property with validation in setter
    private Decimal priceValue;
    public Decimal Price {
        get { return priceValue; }
        set {
            if (value < 0) throw new IllegalArgumentException(
                'Price cannot be negative');
            priceValue = value;
            cachedTax = null; // invalidate cache
        }
    }
}

Inheritance — extends

Apex supports single inheritance (one parent class only). A class must be declared virtual or abstract to be extended.

Extending a virtual class

// Base class — must be virtual to be extendable
public virtual with sharing class Notification {
    protected String recipient;

    public Notification(String r) { this.recipient = r; }

    // virtual method — can be overridden
    public virtual void send(String message) {
        System.debug('Sending to ' + recipient + ': ' + message);
    }

    // final method — cannot be overridden
    public String getRecipient() { return recipient; }
}

// Subclass overrides send()
public with sharing class EmailNotification extends Notification {
    private String fromAddress;

    public EmailNotification(String to, String from) {
        super(to); // must call parent constructor
        this.fromAddress = from;
    }

    public override void send(String message) {
        // Custom email implementation
        Messaging.SingleEmailMessage mail = new Messaging.SingleEmailMessage();
        mail.setToAddresses(new List<String>{ recipient });
        mail.setPlainTextBody(message);
        Messaging.sendEmail(new List<Messaging.SingleEmailMessage>{ mail });
    }
}

// Polymorphism in action
Notification n = new EmailNotification('user@example.com', 'noreply@co.com');
n.send('Your order has shipped!');
Apex single inheritance: A class can extend only one parent, but can implement multiple interfaces. The class hierarchy is sealed unless marked virtual or abstract.
03

Interfaces

Interfaces define a contract — a set of method signatures that any implementing class must fulfil. They enable dependency injection and make code testable.

📜

Defining & Implementing Interfaces

Interfaces contain only method signatures — no implementation, no instance variables.

  • Methods are implicitly public abstract
  • A class can implement multiple interfaces
  • Use implements keyword; multiple separated by commas
  • Implementing class must provide all methods
// Interface — a contract
public interface Discountable {
    Decimal applyDiscount(Decimal originalPrice);
    String getDiscountDescription();
}

public interface Taxable {
    Decimal calculateTax(Decimal price);
}

// Class implementing two interfaces
public with sharing class PremiumProduct
    implements Discountable, Taxable {

    public Decimal applyDiscount(Decimal originalPrice) {
        return originalPrice * 0.90; // 10% off
    }

    public String getDiscountDescription() {
        return '10% Premium Member Discount';
    }

    public Decimal calculateTax(Decimal price) {
        return price * 0.085; // 8.5% tax
    }
}

// Polymorphic usage through interface type
Discountable item = new PremiumProduct();
Decimal finalPrice = item.applyDiscount(100); // 90
💉

Interfaces for Dependency Injection

Coding to interfaces (not concrete classes) makes units independently testable.

  • Service depends on an interface, not a specific implementation
  • Tests inject a mock or stub that implements the interface
  • Production code injects the real implementation
  • This pattern is the key to unit-testing code that does callouts or DML
// Interface — contract for email sending
public interface IEmailSender {
    void send(String to, String subject, String body);
}

// Real implementation
public class SalesforceEmailSender implements IEmailSender {
    public void send(String to, String subject, String body) {
        Messaging.SingleEmailMessage m = new Messaging.SingleEmailMessage();
        m.setToAddresses(new List<String>{to});
        m.setSubject(subject);
        m.setPlainTextBody(body);
        Messaging.sendEmail(new List<Messaging.SingleEmailMessage>{m});
    }
}

// Service depends on interface — testable!
public with sharing class WelcomeService {
    private IEmailSender emailSender;

    public WelcomeService(IEmailSender sender) {
        this.emailSender = sender;
    }

    public void welcomeUser(String email, String name) {
        emailSender.send(email, 'Welcome!', 'Hi ' + name);
    }
}

// In tests: inject a mock
public class MockEmailSender implements IEmailSender {
    public List<String> sentTo = new List<String>();
    public void send(String to, String s, String b) {
        sentTo.add(to);
    }
}

Salesforce System Interfaces

  • Database.Batchable<SObject> — Batch Apex

  • Schedulable — Scheduled Apex
  • Database.Stateful — maintain state across batch chunks
  • Comparable — custom sort order for objects
  • Iterator<T> / Iterable<T> — custom iteration

Virtual & Abstract Classes

Virtual classes provide default behaviour that subclasses can override. Abstract classes enforce that subclasses implement specific methods.

virtual — Overridable Base

  • Can be instantiated directly
  • Methods marked virtual CAN be overridden
  • Methods not marked virtual CANNOT be overridden
  • Subclass uses override keyword
  • Call parent with super.methodName()

abstract — Enforced Contract

  • Cannot be instantiated directly
  • Abstract methods have no body — must be implemented
  • Can have concrete methods with implementations
  • Subclass must implement all abstract methods
  • Best for template method pattern

Abstract Class — Template Method Pattern

// Abstract base — defines the algorithm skeleton
public abstract with sharing class ReportGenerator {

    // Template method — defines the steps, not overridable
    public final String generate() {
        String header  = buildHeader();
        String content = buildContent(); // abstract — must implement
        String footer  = buildFooter();
        return header + '\n' + content + '\n' + footer;
    }

    // Concrete default implementation
    protected virtual String buildHeader() {
        return '=== Report ===';
    }

    // Abstract — each subclass must implement
    protected abstract String buildContent();

    // Concrete default
    protected virtual String buildFooter() {
        return '=== End ===';
    }
}

// Concrete subclass
public with sharing class SalesReport extends ReportGenerator {
    protected override String buildContent() {
        Decimal total = [SELECT SUM(Amount) total
                         FROM Opportunity
                         WHERE CloseDate = THIS_YEAR][0].get('total');
        return 'Total Sales This Year: $' + total;
    }

    // Override header too
    protected override String buildHeader() {
        return '=== Annual Sales Report ===';
    }
}

// Usage
ReportGenerator gen = new SalesReport();
String report = gen.generate();

Inner Classes & Wrapper Classes

Inner classes are defined inside another class. They are commonly used as data-transfer objects, wrappers for LWC, and result/request objects.

📦

Inner Classes

Defined inside an outer class, useful for grouping related types.

  • Access outer class private members? No — inner classes are separate
  • Can be public or private
  • Accessed as OuterClass.InnerClass
  • No limit on nesting depth (but keep it shallow)
  • Static inner classes only (no non-static inner classes)
public with sharing class AccountService {

    // Inner class as a result wrapper
    public class AccountResult {
        public Boolean success;
        public String  message;
        public Account record;

        public AccountResult(Boolean s, String m, Account r) {
            this.success = s;
            this.message = m;
            this.record  = r;
        }
    }

    public AccountResult createAccount(String name) {
        Account acc = new Account(Name = name);
        try {
            insert acc;
            return new AccountResult(true, 'Created', acc);
        } catch (DmlException e) {
            return new AccountResult(false, e.getMessage(), null);
        }
    }
}

// Usage
AccountService svc = new AccountService();
AccountService.AccountResult r = svc.createAccount('ACME');
if (!r.success) System.debug('Error: ' + r.message);
🎁

Wrapper Classes for LWC

A very common pattern: wrap sObject data with computed fields for Lightning components.

  • Combine sObject data with UI-specific fields (e.g., isSelected)
  • Return List<WrapperClass> from @AuraEnabled method
  • Must have public properties (not private) for serialisation
  • All properties serialised to JSON automatically
public with sharing class OpportunityController {

    public class OppWrapper {
        @AuraEnabled public Opportunity record;
        @AuraEnabled public Boolean isHighValue;
        @AuraEnabled public String  statusBadge;

        public OppWrapper(Opportunity opp) {
            this.record     = opp;
            isHighValue     = opp.Amount != null && opp.Amount > 50000;
            statusBadge     = isHighValue ? 'High Value' : 'Standard';
        }
    }

    @AuraEnabled(cacheable=true)
    public static List<OppWrapper> getOpportunities() {
        List<OppWrapper> results = new List<OppWrapper>();
        for (Opportunity opp :
                [SELECT Id, Name, Amount, StageName
                 FROM Opportunity ORDER BY Amount DESC LIMIT 50]) {
            results.add(new OppWrapper(opp));
        }
        return results;
    }
}

Comparable Interface — Custom Sort

Implementing Comparable for custom sort order

public with sharing class LeadScore implements Comparable {
    public Lead   record;
    public Integer score;

    public LeadScore(Lead l, Integer s) {
        record = l; score = s;
    }

    // compareTo: return negative if this < other
    //            return 0 if equal
    //            return positive if this > other
    public Integer compareTo(Object other) {
        LeadScore that = (LeadScore) other;
        if (this.score == that.score) return 0;
        return this.score > that.score ? -1 : 1; // descending
    }
}

// Sort a List of LeadScore by score descending
List<LeadScore> scores = buildScores();
scores.sort(); // calls compareTo internally
System.debug('Top Lead: ' + scores[0].record.Name);

Best Practices

Always declare with sharing

Omitting the sharing keyword inherits the calling class's sharing context, which is unpredictable. Be explicit.

❌ public class MyService { }
✅ public with sharing class MyService { }

Program to Interfaces

Declare variables using the interface type so implementations can be swapped without changing callers.

❌ SalesforceEmailSender s = new SalesforceEmailSender();
✅ IEmailSender s = new SalesforceEmailSender();

Avoid global unless Packaging

global is permanent — once published in a managed package you can never remove it. Use public in non-packaged orgs.

❌ global class MyUtil { } // org-only code
✅ public class MyUtil { }

Single-Level Inheritance Preferred

Deep class hierarchies are hard to reason about. Prefer composition over multiple levels of inheritance in most cases.

❌ C extends B extends A extends Base extends Root
✅ C implements IContractA, IContractB + has-a relationship

Use abstract for Mandatory Contracts

If all subclasses MUST implement a method, make it abstract — the compiler will enforce it.

❌ virtual void process() { throw new Exception('implement'); }
✅ abstract void process();

Wrapper Classes for AuraEnabled

Don't expose raw sObjects from @AuraEnabled methods when you need computed/UI-specific fields — use a wrapper class.

❌ return oppList; // no UI-specific fields
✅ return new List<OppWrapper>(oppList);
