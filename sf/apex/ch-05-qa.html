In a before insert trigger, you modify a field on a record in Trigger.new. Do you need to call update to save the change?
✓ Correct: B

In a before trigger, modifications to records in Trigger.new are automatically included in the pending save — no extra DML needed. This is one of the key advantages of before triggers for field defaulting and normalisation. After triggers, however, have read-only records and require explicit DML to persist changes.

2
Which trigger context variable is NOT available in a before insert trigger?
✓ Correct: B

Trigger.newMap is keyed by record Id. In a before insert trigger, records have not yet been assigned an Id (that happens at the database save step). Therefore Trigger.newMap is null/unavailable. It becomes available in after insert and all update/delete contexts where Ids exist.

3
What is the maximum number of records that can be processed in a single trigger batch execution?
✓ Correct: B — 200

Salesforce processes DML operations in batches of up to 200 records per trigger execution. If you perform a bulk DML on 1,000 records, the trigger fires 5 times with 200 records each. This is why all trigger code must be written to handle any number of records — the Trigger.size variable tells you how many records are in the current batch.

4
Where in the Salesforce order of execution do after triggers run relative to custom validation rules?
✓ Correct: B

The order is: system validations → before triggers → custom validations → save to DB (not committed) → after triggers → workflow/process builder → commit. After triggers run after the record has been saved to the database session but before the transaction is permanently committed. That's why they have access to record Ids but can still participate in the same transaction rollback.

5
Which pattern detects that only changed records (where StageName actually changed) should be processed in an update trigger?
✓ Correct: B

The standard pattern: iterate Trigger.new and for each record compare the new value against the old value from Trigger.oldMap.get(rec.Id).FieldName. This avoids reprocessing records where the field didn't change, reducing unnecessary work and preventing recursive execution in some edge cases.

for (Opportunity o : Trigger.new) {
    if (o.StageName != Trigger.oldMap.get(o.Id).StageName) {
        // Only process records where stage actually changed
    }
}
6
Why is calling addError() preferred over throwing an exception in a before trigger?
✓ Correct: B

addError() blocks the save and surfaces a clear, localised error message directly on the offending field or record in the UI — and returns a structured error in API responses. Throwing an uncaught exception shows a generic "APEX_ERROR" in the UI which is confusing for users. Both roll back the transaction, but addError() provides far better UX.

7
A developer has a single Account object with three triggers: AccountTrigger1, AccountTrigger2, and AccountTrigger3. What is the problem with this approach?
✓ Correct: B

Multiple triggers on the same object fire in an unpredictable order — Salesforce does not guarantee execution sequence. If trigger 2 depends on something trigger 1 set up, that dependency can silently break when the order changes. The solution: one trigger per object that delegates to a handler class, where the order of logic within the handler is explicit and controllable.

8
A static Boolean flag hasRun = false is used for recursion prevention. After setting it to true in the first execution, when does it reset back to false?
✓ Correct: B

Static variables persist for the entire lifetime of the current transaction (execution context) and are reset at the start of the next transaction. This means the recursion guard correctly blocks re-entry within a single transaction while allowing normal operation in subsequent transactions (e.g., the next user save operation).

9
In the trigger handler framework, what is the benefit of having the trigger file contain only new AccountTriggerHandler().run();?
✓ Correct: B

When all logic is in the handler class, you can instantiate the handler directly in tests and call its methods with mock data — without needing to perform actual DML to fire the trigger. This leads to faster, more isolated unit tests. The trigger file itself is essentially untestable (it can only run in a trigger context), so keeping it as a thin router is the professional standard.

10
A developer creates a Task in an after insert trigger on Opportunity. The Task creation calls insert tasks. Which of the following is true?
✓ Correct: C

DML inside an after trigger runs within the same transaction as the original save. If the Task insert throws an unhandled exception, the entire transaction — including the original Opportunity insert — is rolled back. This all-or-nothing behaviour is why wrapping related DML in try/catch blocks (or using Database.insert(list, false)) and handling errors gracefully is important in after triggers.
