Indexes — How Salesforce Indexes Fields

Salesforce automatically indexes certain fields. Using indexed fields in WHERE dramatically reduces query time on large objects.

Id
Always indexed. The fastest possible WHERE condition.
Name
Indexed on most standard objects. Fast for equality and startsWith.
CreatedDate / LastModifiedDate
System fields, always indexed. Use for time-range filtering.
OwnerId / RecordTypeId
Standard lookup fields, indexed automatically.
External ID fields
Custom fields marked "External ID" in Setup — auto-indexed.
Unique fields
Custom fields marked "Unique" — auto-indexed.
Standard lookup fields
AccountId, ContactId etc. — indexed on child objects.
Regular custom text fields
NOT indexed unless "External ID" or "Unique" is set. Request a custom index from Salesforce for high-volume queries.
Long Text Area / Rich Text
Never indexed. LIKE queries on these always cause TABLE_SCAN.
Custom Indexes: For high-volume orgs, Salesforce Support can create custom indexes on non-indexed fields (requires a case). Alternatively, mark the field as External ID or Unique to auto-index it if your data allows it.
02

Query Plan Tool

The Query Plan Tool in Developer Console shows how Salesforce will execute a SOQL query before you run it — essential for performance investigation.

Reading Query Plan Output

// Enable: Developer Console → Help → Preferences → Enable Query Plan
// Then click "Query Plan" before "Execute" in the Query Editor

// Example query plan output for a non-optimised query:
// [SELECT Id FROM Account WHERE Description LIKE '%cloud%']
//
// Operation    | Leading Op Type | Cost  | Rows
// --------------------------------------------
// Filter       | TABLE_SCAN      | 0.98  | 45000
//
// Cost >= 1 means full TABLE_SCAN — every row checked
// Cost < 0.1 means good INDEX use

// Same query with an indexed field:
// [SELECT Id FROM Account WHERE Name LIKE 'ACME%']
//
// Operation    | Leading Op Type | Cost  | Rows
// --------------------------------------------
// Filter       | INDEX           | 0.003 | 12

// Key cost thresholds:
// cost < 0.1  : Excellent — uses index effectively
// 0.1 – 0.5  : Good — partial index use
// 0.5 – 0.9  : Concerning — consider rewriting
// cost >= 1.0 : TABLE_SCAN — will slow down at scale
⚠ Leading Wildcard LIKE: WHERE Name LIKE '%cloud%' (leading %) always causes TABLE_SCAN — even on indexed fields — because the index cannot be used when the pattern starts with a wildcard. Use SOSL for full-text search instead.

Selectivity — The Threshold Rule

Salesforce uses selectivity thresholds to decide whether to use an index. Even indexed fields can cause a TABLE_SCAN if too many rows match.

Selectivity Thresholds

// Salesforce threshold rule (approximate):
// Standard objects: index used if query returns < 30% of table
// Custom objects:  index used if query returns < 10% of table

// On a 100,000 row Account object:
// [WHERE Type = 'Customer'] — if 40,000 rows match (40%) → TABLE_SCAN
// [WHERE RecordTypeId = :rtId] — if 5,000 rows match (5%)  → INDEX

// Negative operators ALWAYS force TABLE_SCAN regardless of count:
// != (not equal)
// NOT IN
// EXCLUDES
// NOT LIKE
// Example:
// [SELECT Id FROM Account WHERE Type != 'Customer']
// — Always TABLE_SCAN even if only 5% of rows match

// NULL checks may use an index depending on data distribution:
// [WHERE Email = null]   — uses "null index" if few nulls
// [WHERE Email != null]  — TABLE_SCAN (too many rows)

// Best practice: combine highly selective conditions
// Each individual condition may be borderline, but AND reduces
// total rows until threshold is met
[SELECT Id FROM Opportunity
 WHERE StageName = 'Prospecting'  // 30% rows
   AND OwnerId = :userId           // 5% rows → combined 1.5% ✅
   AND CloseDate >= :startDate];   // further reduces

Pagination Strategies

❌

OFFSET Pagination — Avoid

LIMIT/OFFSET is simple but scales terribly on large data sets.

  • Max OFFSET value is 2,000
  • Each page requires scanning all previous rows
  • Page 100 scans 10,000 rows just to skip them
  • Performance degrades as page number grows
  • Only suitable for small, stable data sets
  • Avoid in production with large volumes
// OFFSET pagination — works but scales badly
// Each page SCANS all previous pages first
Integer pageSize = 50;
Integer pageNum  = 1;  // 0-indexed

List<Account> page1 = [SELECT Id, Name FROM Account
    ORDER BY Name LIMIT :pageSize OFFSET 0];

List<Account> page2 = [SELECT Id, Name FROM Account
    ORDER BY Name LIMIT :pageSize OFFSET :pageSize];

// Getting page 100 requires scanning 5,000 rows
// Getting page 1000 requires scanning 50,000 rows
// OFFSET max = 2,000 rows — you literally can't get past page 40

// Also: if records are inserted/deleted between pages,
// you may see duplicates or skip records
✅

Keyset Pagination — Recommended

Use the last seen Id (or sortable field) as a cursor. O(1) per page regardless of depth.

  • No OFFSET — uses WHERE Id > :lastId
  • O(1) cost per page — scales to millions
  • Must ORDER BY the cursor field
  • Stable — new inserts don't cause duplicates
  • Works perfectly with indexed Id field
  • Used by Salesforce's own bulk APIs
// Keyset pagination — O(1) per page, scales to millions
// Works because Id is sorted and indexed

public class AccountPaginator {
    private Id lastSeenId = null;
    private Integer pageSize = 200;
    private Boolean hasMore = true;

    public List<Account> nextPage() {
        if (!hasMore) return new List<Account>();

        List<Account> page;
        if (lastSeenId == null) {
            // First page — no cursor
            page = [SELECT Id, Name, Industry
                    FROM Account
                    ORDER BY Id ASC
                    LIMIT :pageSize];
        } else {
            // Subsequent pages — use cursor
            page = [SELECT Id, Name, Industry
                    FROM Account
                    WHERE Id > :lastSeenId  // uses Id index!
                    ORDER BY Id ASC
                    LIMIT :pageSize];
        }

        if (!page.isEmpty()) {
            lastSeenId = page[page.size() - 1].Id;
        }
        hasMore = (page.size() == pageSize);
        return page;
    }
}

// Usage
AccountPaginator pager = new AccountPaginator();
while (pager.hasMore) {
    List<Account> page = pager.nextPage();
    processPage(page);
}

// Keyset on other fields — sort by LastModifiedDate + Id
// (Id breaks ties to ensure stable ordering)
Id lastId;
DateTime lastModified;
List<Account> next = [
    SELECT Id, Name, LastModifiedDate FROM Account
    WHERE (LastModifiedDate = :lastModified AND Id > :lastId)
       OR  LastModifiedDate > :lastModified
    ORDER BY LastModifiedDate ASC, Id ASC
    LIMIT 200
];

QueryLocator for Batch Apex

The most scalable option — process up to 50 million records in chunks without memory concerns.

  • Returns a cursor, not data
  • Supports up to 50 million rows
  • Heap-safe — data delivered in chunks
  • Only available in Batch Apex start()
  • Cannot use in triggers or controllers
  • Chunk size: 1 to 2,000 records
// QueryLocator — the only way to process 50M records
global with sharing class LeadCleanupBatch
    implements Database.Batchable<SObject> {

    // start() returns a cursor — no records loaded into heap
    global Database.QueryLocator start(
            Database.BatchableContext bc) {
        // This query can return up to 50 MILLION records
        return Database.getQueryLocator(
            'SELECT Id, Email, Status FROM Lead ' +
            'WHERE IsConverted = false ' +
            'AND CreatedDate < LAST_N_YEARS:2'
        );
    }

    // execute() receives 200 records at a time (default)
    global void execute(Database.BatchableContext bc,
            List<SObject> scope) {
        List<Lead> leads = (List<Lead>) scope;
        List<Lead> toUpdate = new List<Lead>();

        for (Lead l : leads) {
            if (String.isBlank(l.Email)) {
                l.Status = 'Unqualified';
                toUpdate.add(l);
            }
        }
        if (!toUpdate.isEmpty()) update toUpdate;
    }

    global void finish(Database.BatchableContext bc) {
        System.debug('Batch complete');
    }
}

// Launch with chunk size 500
Database.executeBatch(new LeadCleanupBatch(), 500);
🔁

SOQL For-Loop — Heap Safe

The SOQL for-loop delivers records in 200-row batches to avoid loading the full result set into heap.

  • Heap stays constant regardless of total rows
  • Previous batch garbage-collected on next chunk
  • Still counts as 1 SOQL query
  • Governor limits measured per 200-row chunk
  • DML inside still counts toward 150 limit
  • Best for in-transaction processing of large sets
// SOQL for-loop — heap-safe iteration
// Salesforce delivers 200 records per internal batch
// Previous batch is eligible for GC before next arrives

// vs. List query:
// List<Lead> all = [SELECT Id FROM Lead]; // ALL rows in heap at once
// for (Lead l : all) { ... }

// SOQL for-loop alternative — constant heap usage
for (Lead lead : [SELECT Id, Email, Status FROM Lead
                   WHERE IsConverted = false]) {
    // Process one Lead at a time
    // Heap contains ~200 leads max at any time
    if (String.isBlank(lead.Email)) {
        // Don't do DML here — collect first!
    }
}

// Pattern: collect then bulk DML (still need to avoid DML in loop)
List<Lead> toUpdate = new List<Lead>();
for (Lead lead : [SELECT Id, Status FROM Lead
                   WHERE IsConverted = false]) {
    if (lead.Status == 'New') {
        lead.Status = 'Working';
        toUpdate.add(lead);
        // Bulk DML every 200 to avoid DML limit
        if (toUpdate.size() == 200) {
            update toUpdate;
            toUpdate.clear();
        }
    }
}
if (!toUpdate.isEmpty()) update toUpdate;

Best Practices

Filter on Indexed Fields First

Put the most selective, indexed WHERE condition first. Salesforce evaluates conditions left-to-right — start with Id, RecordTypeId, or External ID.

❌ WHERE Description LIKE '%cloud%' AND RecordTypeId = :rtId
✅ WHERE RecordTypeId = :rtId AND Description LIKE '%cloud%'

Use SOSL for Contains Searches

SOQL LIKE '%term%' always causes TABLE_SCAN. SOSL uses the Salesforce search index — much faster for partial-text matching.

❌ WHERE Name LIKE '%cloud%' // TABLE_SCAN every time
✅ [FIND :term IN NAME FIELDS RETURNING Account]

Keyset Over OFFSET for Pagination

OFFSET scans all previous rows on every page. Keyset uses an index — O(1) regardless of which page you're on.

❌ LIMIT 200 OFFSET 10000 // scans 10k rows to skip them
✅ WHERE Id > :lastId ORDER BY Id LIMIT 200

Use QueryLocator for Millions of Records

For Batch Apex processing millions of records, always return a QueryLocator from start() — not a List. QueryLocator supports up to 50M rows.

❌ return [SELECT Id FROM Lead]; // max 50k, heap heavy
✅ return Database.getQueryLocator('SELECT Id FROM Lead');

Run Query Plan Before Deploying

Use the Developer Console Query Plan tool on every new query that touches large objects (>100k rows). Cost > 0.5 warrants a rewrite.

❌ Write query → deploy → discover timeout in production
✅ Query Plan cost < 0.1 before deploying

Combine Conditions to Improve Selectivity

Each AND condition narrows the result set. Combine two 20%-selective conditions to get 4% selectivity — well below the index threshold.

❌ WHERE Type = 'Customer' // 30% → TABLE_SCAN
✅ WHERE Type = 'Customer' AND CreatedDate = THIS_YEAR // 3% → INDEX
