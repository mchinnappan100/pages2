Debug Logs & Logging Levels

Debug logs are the primary tool for Apex debugging. Understanding log levels and the log format unlocks fast root-cause analysis.

Logging Levels

// LoggingLevel enum — controls which messages appear
System.debug(LoggingLevel.ERROR,  'Critical failure: ' + e);
System.debug(LoggingLevel.WARN,   'Approaching limit: ' + Limits.getQueries());
System.debug(LoggingLevel.INFO,   'Processing ' + records.size() + ' records');
System.debug(LoggingLevel.DEBUG,  'Account: ' + acc);        // default level
System.debug(LoggingLevel.FINE,   'Loop iteration ' + i);
System.debug(LoggingLevel.FINER,  'Detailed trace');
System.debug(LoggingLevel.FINEST, 'Very verbose');

// Set log levels in Setup → Debug Logs → Log Filters:
// Apex Code: DEBUG  ← shows DEBUG and above
// Database:  INFO   ← shows SOQL timing
// Workflow:  NONE   ← suppress workflow noise

// Log format in the log viewer:
// timestamp | event type | message
// 12:34:56.123 (1234)|USER_DEBUG|[42]|DEBUG|Processing 50 records

// Tips for reading logs:
// - Search for USER_DEBUG to find your debug statements
// - Search for SOQL_EXECUTE_BEGIN to find queries
// - Search for DML_BEGIN to find DML operations
// - Search for LIMIT_USAGE_FOR_NS to see governor usage
🔵

Structured Logging Pattern

Consistent log formatting makes searching and parsing logs far easier.

  • Use a helper class for consistent format
  • Include class + method context
  • Log at entry and exit of key methods
  • Include record counts and Ids
  • Use ERROR for exceptions, INFO for flow
  • Remove FINEST logs before production
// Logger utility — consistent format
public class Logger {
    private static final String FORMAT = '[{0}] {1}: {2}';

    public static void info(String cls, String msg) {
        System.debug(LoggingLevel.INFO,
            String.format(FORMAT, new List<Object>{cls,'INFO',msg}));
    }
    public static void error(String cls, String msg, Exception e) {
        System.debug(LoggingLevel.ERROR,
            String.format(FORMAT,
                new List<Object>{cls,'ERROR',
                    msg + ' | ' + e.getMessage()
                    + '\n' + e.getStackTraceString()}));
    }
    public static void limits(String cls) {
        System.debug(LoggingLevel.DEBUG,
            String.format(FORMAT, new List<Object>{
                cls, 'LIMITS',
                'SOQL:' + Limits.getQueries() + '/' + Limits.getLimitQueries() +
                ' DML:' + Limits.getDmlStatements() + '/' + Limits.getLimitDmlStatements() +
                ' CPU:' + Limits.getCpuTime() + 'ms' +
                ' Heap:' + Limits.getHeapSize() + 'b'
            }));
    }
}

// Usage
public with sharing class OrderService {
    private static final String CLS = 'OrderService';

    public static void process(List<Order__c> orders) {
        Logger.info(CLS, 'Processing ' + orders.size() + ' orders');
        Logger.limits(CLS);
        try {
            // ... logic ...
        } catch (Exception e) {
            Logger.error(CLS, 'Failed to process orders', e);
            throw e;
        }
        Logger.info(CLS, 'Done');
        Logger.limits(CLS);
    }
}

Developer Console vs SFDX Logs

Two tools for reading debug logs — each suited to different scenarios.

  • Developer Console: visual, filterable log view
  • Execute Anonymous: quick code testing
  • sf apex run — run anonymous Apex via CLI
  • sf apex log tail — stream logs in real-time
  • sf apex log get — fetch logs
  • VS Code: integrated log viewer in extension
# Run anonymous Apex and see output
sf apex run --file scripts/apex/test.apex --target-org my-sandbox

# Stream debug logs in real time
sf apex log tail --target-org my-sandbox --color

# List available debug logs
sf apex log list --target-org my-sandbox

# Get a specific log
sf apex log get --log-id 07L... --target-org my-sandbox

# Run tests and see debug output
sf apex run test \
  --class-names AccountServiceTest \
  --result-format human \
  --output-dir test-results \
  --target-org my-sandbox

The Limits Class — Defensive Monitoring

Real-time Governor Limit Monitoring

// Check limits proactively — don't wait for LimitException
public with sharing class LimitGuard {

    // Warn if > 80% of any key limit is consumed
    public static void checkSafe() {
        checkLimit('SOQL Queries',
            Limits.getQueries(),
            Limits.getLimitQueries(), 80);
        checkLimit('DML Statements',
            Limits.getDmlStatements(),
            Limits.getLimitDmlStatements(), 80);
        checkLimit('CPU Time (ms)',
            Limits.getCpuTime(),
            Limits.getLimitCpuTime(), 75);
        checkLimit('Heap (bytes)',
            Limits.getHeapSize(),
            Limits.getLimitHeapSize(), 80);
    }

    private static void checkLimit(
            String name, Integer used,
            Integer limit, Integer warnPct) {
        Integer pct = (used * 100) / limit;
        if (pct >= warnPct) {
            System.debug(LoggingLevel.WARN,
                name + ': ' + used + '/' + limit
                + ' (' + pct + '%) — approaching limit!');
        }
    }

    // Guard pattern — stop processing if too close to limit
    public static Boolean canContinue() {
        return Limits.getQueries()        < Limits.getLimitQueries()        - 5
            && Limits.getDmlStatements()  < Limits.getLimitDmlStatements()  - 10
            && Limits.getCpuTime()        < Limits.getLimitCpuTime()        - 1000
            && Limits.getHeapSize()       < Limits.getLimitHeapSize()       - 500000;
    }
}

// Batch execute() — check limits per chunk
global void execute(Database.BatchableContext bc,
        List<SObject> scope) {
    LimitGuard.checkSafe();
    for (SObject rec : scope) {
        if (!LimitGuard.canContinue()) {
            System.debug(LoggingLevel.WARN,
                'Stopping early — approaching limits');
            break;
        }
        processRecord(rec);
    }
}

CPU Time Optimisation

The 10,000ms CPU limit is the hardest to diagnose. These patterns eliminate the most common CPU hogs in Apex code.

❌ Nested Loops (O(n²))
Two nested loops over large lists. 1,000 records × 1,000 records = 1,000,000 iterations. CPU killer.
✅ Map for O(1) Lookup
Replace inner loop with Map.get(). 1,000 records × O(1) = 1,000 iterations total.
❌ String Concatenation in Loops
Each s = s + item creates a new String object. 10,000 iterations = 10,000 allocations.
✅ List + String.join()
Collect parts in a List, then String.join(list, ',') — one allocation, much faster.
❌ JSON.serialize in Loops
JSON serialisation is CPU-expensive. Serialising inside a loop multiplies the cost.
✅ Bulk Serialise Once
Collect all objects first, then call JSON.serialize(list) once outside the loop.

CPU Profiling with Timestamps

// Manual CPU profiling using Limits.getCpuTime()
public with sharing class ProfiledService {

    public static void process(List<Account> accounts) {
        Long startTotal = System.currentTimeMillis();
        Integer cpuStart = Limits.getCpuTime();

        // Phase 1: Query
        Long t1 = System.currentTimeMillis();
        Map<Id, List<Contact>> contactMap = buildContactMap(accounts);
        System.debug('Phase 1 (query): '
            + (System.currentTimeMillis() - t1) + 'ms');

        // Phase 2: Process
        Long t2 = System.currentTimeMillis();
        List<Account> toUpdate = applyLogic(accounts, contactMap);
        System.debug('Phase 2 (logic): '
            + (System.currentTimeMillis() - t2) + 'ms');

        // Phase 3: DML
        Long t3 = System.currentTimeMillis();
        if (!toUpdate.isEmpty()) update toUpdate;
        System.debug('Phase 3 (DML): '
            + (System.currentTimeMillis() - t3) + 'ms');

        System.debug('Total wall time: '
            + (System.currentTimeMillis() - startTotal) + 'ms');
        System.debug('CPU consumed: '
            + (Limits.getCpuTime() - cpuStart) + 'ms');
    }
}

Heap Memory Management

Reducing Heap Consumption

// Heap management patterns

// 1. SOQL for-loop — processes 200 records at a time
//    Never loads full result set into heap
for (Account acc : [SELECT Id, Name FROM Account
                     WHERE Type = 'Customer']) {
    // acc is available; previous batch is GC'd
    processAccount(acc);
}
// vs. List query which loads ALL 50k rows at once

// 2. Null out large collections when done
List<String> hugeList = buildLargeList();
processData(hugeList);
hugeList = null; // hint GC to reclaim memory

// 3. Query only needed fields
// BAD: SELECT * equivalent loads everything into heap
// List<Account> all = [SELECT FIELDS(ALL) FROM Account LIMIT 200];

// GOOD: Only what you need
List<Account> lean = [SELECT Id, Name FROM Account LIMIT 200];

// 4. Stream processing — don't accumulate all results
public static void processLargeDataset() {
    List<Account> batch = new List<Account>();
    Integer batchSize = 200;

    for (Account acc : [SELECT Id, Name FROM Account]) {
        batch.add(acc);
        if (batch.size() == batchSize) {
            processBatch(batch);
            batch.clear(); // release memory
        }
    }
    if (!batch.isEmpty()) processBatch(batch);
}

// 5. Monitor heap usage
System.debug('Heap used: ' + Limits.getHeapSize()
    + ' / ' + Limits.getLimitHeapSize() + ' bytes');

Query Plans & Index Optimisation

Using the Query Plan Tool

// In Developer Console: Help → Preferences → Enable Query Plan
// Then click "Query Plan" button before running SOQL

// Understand query plan output:
// Cardinality: number of rows to scan
// Cost: relative query cost (lower is better, < 1 uses index)
// Fields: which fields are indexed
// Leading operation type: INDEX or TABLE_SCAN

// Common performance pitfalls:

// 1. Querying non-indexed fields in WHERE
// BAD: Description is a long text — no index
// [SELECT Id FROM Account WHERE Description LIKE '%cloud%']

// GOOD: Use indexed fields in WHERE
List<Account> accs = [SELECT Id FROM Account
    WHERE Name = 'ACME Corp']; // Name is indexed

// 2. Negative operators bypass index (SOQL injection aside)
// These use TABLE_SCAN instead of INDEX:
// WHERE Status != 'Active'
// WHERE Amount NOT IN :vals
// WHERE Name LIKE '%partial%'  (leading wildcard)

// 3. OR conditions — may force TABLE_SCAN
// Use IN instead of OR when possible
// BAD: WHERE Stage = 'Prospecting' OR Stage = 'Qualification'
// GOOD: WHERE Stage IN ('Prospecting','Qualification')

// 4. Large offsets are slow
// [SELECT Id FROM Account LIMIT 200 OFFSET 50000]
// Use keyset pagination instead:
Id lastId;
List<Account> page = [SELECT Id, Name FROM Account
    WHERE Id > :lastId  // uses index
    ORDER BY Id
    LIMIT 200];
lastId = page.isEmpty() ? null : page[page.size()-1].Id;

Best Practices

Profile Before Optimising

Don't guess — measure. Use Limits.getCpuTime() around suspect code and log the result. Optimise the biggest bottleneck first.

❌ "This loop seems slow" — guessing without data
✅ Integer before = Limits.getCpuTime(); // measure precisely

Never Put SOQL in Loops

Each loop iteration with a SOQL query can hit 100 queries in 100 records. Query once outside, use Map for lookup inside.

❌ for (Opp o : opps) { [SELECT Id FROM Account WHERE Id = :o.AccountId]; }
✅ Map<Id,Account> m = new Map<Id,Account>([SELECT Id FROM Account WHERE Id IN :ids]);

Use SOQL For-Loop for Large Data

Querying millions of rows into a List exhausts heap. SOQL for-loops batch-deliver 200 rows at a time, keeping heap usage constant.

❌ List<Lead> all = [SELECT Id FROM Lead]; // 500k rows in heap
✅ for (Lead l : [SELECT Id FROM Lead]) { ... }

Use String.join() Not Concatenation

String concatenation in loops creates many intermediate String objects, consuming CPU and heap. Collect in List, join once.

❌ String csv = ''; for (s : list) { csv += s + ','; }
✅ String csv = String.join(list, ',');

Query Only Required Fields

Every field in SELECT adds to heap consumption. Query only what your logic actually uses — not SELECT * equivalents.

❌ [SELECT FIELDS(ALL) FROM Account LIMIT 200]
✅ [SELECT Id, Name, Industry FROM Account LIMIT 200]

Use IN Not OR for Multi-Value Filters

WHERE Stage IN ('A','B') uses an index; OR chains often force table scans on large objects.

❌ WHERE Stage = 'A' OR Stage = 'B' OR Stage = 'C'
✅ WHERE Stage IN ('A','B','C')
