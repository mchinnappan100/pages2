What Is Apex?

Apex is a proprietary, strongly-typed, object-oriented programming language developed by Salesforce. It runs natively on the Force.com platform inside a multi-tenant cloud environment, which fundamentally shapes every design decision you will make as an Apex developer.

☁️

Apex & the Multi-tenant Cloud

Multiple customers share the same hardware, so Salesforce enforces limits to protect everyone.

  • Code executes on Salesforce servers — no on-prem runtime needed
  • Each org runs in an isolated execution context
  • Governor limits prevent any single tenant from monopolising resources
  • Transactions are atomic — DML either all succeeds or rolls back

Every Apex transaction lives inside a governor-enforced sandbox:

// A single Apex transaction — Salesforce tracks everything inside it
List<Account> accs = [SELECT Id, Name FROM Account LIMIT 200];
for (Account a : accs) {
    a.Description = 'Processed';
}
update accs; // one DML statement for all 200 records
Key insight: Bulkifying DML like this keeps you well within the 150 DML statement governor limit.
🔑

Key Characteristics

Apex shares surface area with Java but is purpose-built for Salesforce's cloud architecture.

  • Strongly typed — all variables must have declared types
  • Object-oriented — classes, interfaces, inheritance, polymorphism
  • Tightly integrated with Salesforce data (SOQL, SOSL, DML)
  • Compiled and stored as bytecode on Salesforce servers
  • Runs synchronously or asynchronously (Future, Batch, Queueable)
  • Built-in testing framework with code-coverage requirements
⚙️

When to Use Apex

Declarative tools (Flow, Process Builder) are always preferred. Use Apex when declarative tools reach their limits.

  • Complex business logic Flow cannot model
  • Callouts to external REST/SOAP web services
  • Batch processing of millions of records
  • Custom controllers & extensions for Visualforce / LWC
  • Event-driven logic via triggers on sObject events

A simple Apex method called from a Lightning Web Component:

public with sharing class AccountHelper {
    @AuraEnabled(cacheable=true)
    public static List<Account> getTopAccounts(Integer lim) {
        return [SELECT Id, Name, AnnualRevenue
                FROM Account
                ORDER BY AnnualRevenue DESC NULLS LAST
                LIMIT :lim];
    }
}
📜

Apex vs. Java — Key Differences

If you know Java, Apex will feel familiar, but there are critical differences.

  • No file system or network access (use callout APIs)
  • Built-in DML keywords: insert, update, delete, upsert
  • Inline SOQL & SOSL queries replace JDBC
  • No multi-threading — use async Apex instead
  • Case-insensitive (unlike Java)
  • Primitive types differ: Id, sObject, Blob
02

How Apex Fits the Salesforce Architecture

Understanding where Apex lives in the stack removes the mystery behind governor limits, execution contexts, and deployment mechanics.

The Force.com Execution Stack

When a user clicks a button, saves a record, or calls an API endpoint, Salesforce opens an execution context. All Apex code, SOQL queries, and DML statements within that context share a single pool of governor limits. When the context closes, all counters reset.

1

Event triggers the context

A user saves a record, a REST API call arrives, a scheduled job fires, or a Batch Apex start method executes.

2

Order of execution runs

Salesforce processes system validations, before-triggers, after-triggers, workflow rules, processes, and escalation rules in a defined sequence.

3

DML commits or rolls back

If any unhandled exception escapes to the top level, the entire transaction rolls back. Partial success is achievable with the Database class methods.

4

Context closes — limits reset

Governor counters (SOQL rows consumed, DML statements issued, heap usage) all reset when the context ends.

Synchronous vs. Asynchronous Apex

Synchronous Apex runs inline, directly in the user-facing execution context. Asynchronous Apex (Future, Queueable, Batch, Scheduled) dequeues in a separate context with higher or different limits.

  • @future: fire-and-forget method
  • Queueable: chainable, stateful jobs
  • Batch: process millions of records
  • Scheduled: cron-based execution

Where Code Lives

Apex classes and triggers are metadata stored in your org's metadata repository. They are deployed (not published) through:

  • Salesforce CLI / SFDX (sf deploy)
  • Change Sets
  • Ant Migration Tool
  • Developer Console (dev/scratch orgs only)
  • Second-generation packages (2GP)

Apex Syntax Fundamentals

Apex syntax is deliberately close to Java. If you can read Java, you can read Apex. This section covers the building blocks every Apex developer must know cold.

📦

Classes & Methods

The fundamental unit of Apex code organisation.

  • Declared with public, private, global, or protected access modifiers
  • with sharing / without sharing controls record-level security
  • Constructor overloading is supported
  • Static methods don't require class instantiation
public with sharing class DiscountCalculator {

    private Decimal basePrice;

    // Constructor
    public DiscountCalculator(Decimal price) {
        this.basePrice = price;
    }

    // Instance method
    public Decimal applyDiscount(Decimal pct) {
        return basePrice * (1 - pct / 100);
    }

    // Static utility method
    public static String formatCurrency(Decimal amount) {
        return '$' + amount.setScale(2).toPlainString();
    }
}
🔢

Primitive Data Types

Apex's type system is richer than Java's due to Salesforce-specific primitives.

  • Integer, Long, Double, Decimal — numeric types
  • String — Unicode text, immutable
  • Boolean — true / false / null
  • Date, DateTime, Time — temporal types
  • Id — 15- or 18-character Salesforce record ID
  • Blob — binary data (attachments, files)
Integer qty = 10;
Decimal price = 99.95;
String product = 'Cloud Storage';
Boolean isActive = true;
Date closeDate = Date.today().addDays(30);
Id accountId = '001000000000001AAA';

// Decimal is preferred for financial calculations
Decimal total = qty * price;
System.debug('Total: ' + total); // 999.50
📋

Collections

Apex provides three generic collection types essential for bulkified code.

  • List<T> — ordered, allows duplicates, index-accessible
  • Set<T> — unordered, no duplicates, fast membership test
  • Map<K,V> — key/value pairs, O(1) lookup
// List — use for ordered results
List<String> regions = new List<String>{
    'North', 'South', 'East', 'West'
};

// Set — deduplicate Ids before a SOQL query
Set<Id> acctIds = new Set<Id>();
for (Opportunity opp : Trigger.new) {
    acctIds.add(opp.AccountId);
}

// Map — bulk lookup pattern (avoid SOQL in loops!)
Map<Id, Account> acctMap =
    new Map<Id, Account>(
        [SELECT Id, Name FROM Account WHERE Id IN :acctIds]
    );

for (Opportunity opp : Trigger.new) {
    Account parent = acctMap.get(opp.AccountId);
    // use parent without extra query
}
🔁

Control Flow

Standard Java-style control structures with a few Apex-specific nuances.

  • if / else if / else — standard conditional branching
  • for (init; cond; inc) — traditional C-style for loop
  • for (T item : collection) — enhanced for-each
  • for (sObj : [SOQL]) — SOQL for loop (avoids heap overflow)
  • while / do-while — standard loop constructs
  • try / catch / finally — exception handling
// SOQL for loop — processes records in 200-record chunks
// avoids loading millions of rows into heap at once
for (Lead lead : [SELECT Id, Email FROM Lead
                   WHERE IsConverted = false]) {
    if (String.isBlank(lead.Email)) {
        lead.Status = 'Review Needed';
    }
}

// Exception handling
try {
    insert new Account(); // Name is required — will throw
} catch (DmlException e) {
    System.debug('DML failed: ' + e.getMessage());
} finally {
    System.debug('Cleanup always runs');
}
🗄️

sObjects & Inline SOQL

sObjects are first-class types representing Salesforce records. SOQL queries return them directly.

  • Every standard and custom object has a corresponding sObject type
  • Fields accessed via dot notation: acc.Name
  • Inline SOQL wrapped in [ ] returns typed results
  • Bind variables use the : prefix inside SOQL
  • Generic sObject type enables dynamic programming
// Strongly typed sObject — preferred
Account a = new Account(
    Name = 'Acme Corp',
    Industry = 'Technology',
    AnnualRevenue = 5000000
);
insert a;

// SOQL with bind variable
String target = 'Technology';
List<Account> techAccounts =
    [SELECT Id, Name, AnnualRevenue
     FROM Account
     WHERE Industry = :target
     ORDER BY AnnualRevenue DESC
     LIMIT 50];

System.debug('Found: ' + techAccounts.size());
🚨

Exception Handling

Robust exception handling is mandatory for production-quality Apex.

  • DmlException — thrown when DML fails
  • QueryException — SOQL returns wrong number of rows
  • NullPointerException — null dereference
  • LimitException — governor limit exceeded (uncatchable)
  • Custom exceptions extend Exception
// Custom exception class
public class ValidationException extends Exception {}

public with sharing class OrderService {
    public static void placeOrder(Order__c ord) {
        if (ord.Quantity__c <= 0) {
            throw new ValidationException(
                'Quantity must be greater than zero.'
            );
        }
        try {
            insert ord;
        } catch (DmlException e) {
            // Log and re-throw as a user-friendly error
            System.debug(LoggingLevel.ERROR, e.getMessage());
            throw new ValidationException(
                'Order could not be saved: ' + e.getMessage()
            );
        }
    }
}

Governor Limits — The Heart of Apex Development

Governor limits are Salesforce's mechanism for protecting the multi-tenant environment. Every Apex developer must know the key limits by heart and design code around them from day one.

⚠ Critical: LimitException (e.g., "Too many SOQL queries: 101") is uncatchable. The only remedy is writing bulkified code that never approaches the limit in the first place.
Governor Synchronous Limit Async Limit Design Pattern to Respect It
SOQL queries per transaction 100 200 Query outside loops; use Maps for lookups
SOQL rows returned 50,000 50,000 Use SOQL for-loops for large data sets
DML statements 150 150 Collect records in Lists; one bulk DML call
DML rows per transaction 10,000 10,000 Use Batch Apex for volume > 10k records
Heap size 6 MB 12 MB Null out large collections when done
CPU time 10,000 ms 60,000 ms Move heavy computation to async; avoid nested loops
Callouts per transaction 100 100 Batch callout results; use Platform Events if async is acceptable

Checking Limits Programmatically

Use the Limits class to inspect consumption at runtime. This is invaluable during debugging and for defensive coding in shared utilities.

Apex — Limits class usage
// How many SOQL queries have been consumed? System.debug('SOQL used: ' + Limits.getQueries()); System.debug('SOQL limit: ' + Limits.getLimitQueries()); // How many DML statements? System.debug('DML used: ' + Limits.getDmlStatements()); System.debug('DML limit: ' + Limits.getLimitDmlStatements()); // Current heap System.debug('Heap used: ' + Limits.getHeapSize() + ' bytes'); System.debug('CPU used: ' + Limits.getCpuTime() + ' ms');

Best Practices Every Apex Developer Must Know

These patterns separate professional, production-ready Apex from code that will hit limits, fail in bulk, or open security vulnerabilities in your org.

Bulkify Everything

Apex code must handle 1 record and 200 records identically. Never write code that only works for a single record.

❌ // SOQL inside a for-loop
for (Opp o : Trigger.new) {
  Account a = [SELECT Id FROM Account WHERE Id = :o.AccountId];
}
✅ // Query once outside loop
Map<Id,Account> map = new Map<Id,Account>([SELECT Id FROM Account WHERE Id IN :ids]);

Use with sharing

Always declare with sharing unless you have an explicit business reason to bypass record-level security. This ensures the running user's visibility rules are enforced.

❌ public class MyClass { }
✅ public with sharing class MyClass { }

One Trigger Per Object

Multiple triggers on the same object fire in an unpredictable order. Use a single trigger that delegates to a handler class for each object.

❌ AccountTrigger1.trigger, AccountTrigger2.trigger
✅ AccountTrigger.trigger → AccountTriggerHandler.cls

Never Hard-code Ids

Record Ids differ between sandbox and production. Querying by name, Custom Metadata Type, or Custom Setting is always safer than embedding an 18-character Id in code.

❌ Id pricebook = '01s000000001AAAAY';
✅ Id pricebook = [SELECT Id FROM Pricebook2 WHERE IsStandard = true LIMIT 1].Id;

Test with Real Data Shapes

Apex tests must maintain ≥75% code coverage for deployment, but coverage is a floor — not a goal. Write assertions that verify behaviour, not just execution.

❌ // No System.assert — coverage only
✅ System.assertEquals(expected, actual, 'Discount should be 10%');

Use Database Methods for Partial Success

The standard insert DML statement rolls back all rows on any failure. Database.insert(records, false) lets successful rows commit while collecting errors for the failures.

❌ insert records; // all-or-nothing
✅ Database.SaveResult[] results = Database.insert(records, false);
