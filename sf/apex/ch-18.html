01

What Is SOSL?

SOSL (Salesforce Object Search Language) is Salesforce's full-text search language. It searches the Salesforce Search Index — a separate, Lucene-based index that enables fast text matching across multiple objects simultaneously.

SOSL vs SOQL — The Key Distinction

SOQL is a structured query language for exact or condition-based field matching — like SQL. It queries the database directly.

SOSL is a full-text search language that searches an inverted index of indexed text fields. It finds records where the search term appears anywhere in indexed fields across multiple objects in one shot.

🔍

The Search Index

SOSL searches a separate Salesforce Search Index, not the database directly.

  • Lucene-based inverted index
  • Updated asynchronously (slight lag)
  • Tokenises words for matching
  • Supports stemming (run = runs = running)
  • Supports wildcards (* and ?)
  • Case-insensitive by default
🌐

Which Fields Are Indexed?

Not all fields are searchable. Only fields that are part of the Search Index can be found by SOSL.

  • Text, Phone, Email fields
  • Name fields (always indexed)
  • Long Text Area, Rich Text Area
  • Lookup/relationship Name fields
  • Number fields: NOT indexed
  • Date fields: NOT indexed
⚡

When SOSL Beats SOQL

SOSL is the right tool for "search box" scenarios where users type free text.

  • Search across multiple objects at once
  • Partial-word / contains matching
  • User-typed search terms
  • No known object type in advance
  • Avoid table scans on text fields
  • Stemming & synonym support
⚠️

SOSL Limitations

Know these constraints before choosing SOSL over SOQL.

  • Index lag (seconds to minutes)
  • Returns max 2,000 rows per object
  • Up to 20 objects per FIND
  • Cannot aggregate or GROUP BY
  • Counts as 1 SOQL governor query
  • Minimum 2 characters to search

Core SOSL Syntax

A SOSL query has one required clause (FIND) and several optional clauses that refine what is searched and returned.

Complete SOSL Syntax Reference

// Full SOSL syntax:
// FIND {searchTerm}
// [IN searchGroup]
// [RETURNING objectList]
// [WITH filterClause]
// [LIMIT n]
// [OFFSET n]
// [UPDATE trackingType]

// Minimal SOSL — searches ALL indexed fields on ALL searchable objects
List<List<SObject>> results = [FIND 'Acme' IN ALL FIELDS
    RETURNING Account, Contact, Lead];

// The result is always List<List<SObject>>
// Each inner list corresponds to one RETURNING object, in order
List<Account> accounts = (List<Account>) results[0];
List<Contact> contacts = (List<Contact>) results[1];
List<Lead>    leads    = (List<Lead>)    results[2];

System.debug('Found ' + accounts.size() + ' accounts');
System.debug('Found ' + contacts.size() + ' contacts');
03

Search Groups — IN Clause

The IN clause controls which types of fields are searched. Narrowing the search group improves performance and reduces noise.

🌍

IN ALL FIELDS

Searches all indexed fields — Name, Phone, Email, Text, Long Text. The broadest search group.

  • Default if IN is omitted
  • Most comprehensive results
  • Slower than narrower groups
  • Good for global search boxes
// Search ALL indexed fields
String term = 'cloud software';
List<List<SObject>> results =
    [FIND :term IN ALL FIELDS
     RETURNING
         Account(Id, Name, Industry),
         Contact(Id, FirstName, LastName, Email),
         Lead(Id, FirstName, LastName, Company)
     LIMIT 10];

// Always cast each inner list to the correct type
List<Account> accts = (List<Account>) results[0];
List<Contact> cons  = (List<Contact>) results[1];
List<Lead>    leads = (List<Lead>)    results[2];
✏️

IN NAME FIELDS

Searches only Name fields — fastest and most precise for name lookups.

  • Account.Name, Contact.Name etc.
  • Fastest execution
  • Use for autocomplete / type-ahead
  • Misses matches in other fields
// Name-only search — great for autocomplete
String searchTerm = 'acme*'; // trailing wildcard
List<List<SObject>> nameResults =
    [FIND :searchTerm IN NAME FIELDS
     RETURNING
         Account(Id, Name ORDER BY Name LIMIT 5),
         Contact(Id, FirstName, LastName ORDER BY LastName LIMIT 5)
    ];

List<Account> matchingAccounts = (List<Account>) nameResults[0];
List<Contact> matchingContacts = (List<Contact>) nameResults[1];
📧

IN EMAIL FIELDS

Searches only Email-type fields across all returned objects.

  • Searches Email field type only
  • Good for user lookup by email
  • Supports partial email matching
  • Use with trailing wildcard for domain
// Find contacts and leads by email domain
String domain = '*@example.com';
List<List<SObject>> emailResults =
    [FIND :domain IN EMAIL FIELDS
     RETURNING
         Contact(Id, FirstName, LastName, Email),
         Lead(Id, FirstName, LastName, Email)
    ];

List<Contact> contacts = (List<Contact>) emailResults[0];
List<Lead>    leads    = (List<Lead>)    emailResults[1];

for (Contact c : contacts) {
    System.debug('Contact: ' + c.Email);
}
for (Lead l : leads) {
    System.debug('Lead: ' + l.Email);
}
📞

IN PHONE FIELDS & SIDEBAR FIELDS

Targeted search groups for specific field types.

  • IN PHONE FIELDS — Phone type fields only
  • IN SIDEBAR FIELDS — legacy, same as ALL
  • Phone numbers normalised before indexing
  • Useful for duplicate detection
  • Strip formatting before searching
// Find duplicate phone numbers
String phoneNumber = '415-555-1234';
// Strip non-digits for better matching
String normalised = phoneNumber.replaceAll('[^0-9]', '');

List<List<SObject>> phoneResults =
    [FIND :normalised IN PHONE FIELDS
     RETURNING
         Account(Id, Name, Phone),
         Contact(Id, Name, Phone, MobilePhone),
         Lead(Id, Name, Phone)
    ];

List<Account> accounts = (List<Account>) phoneResults[0];
List<Contact> contacts = (List<Contact>) phoneResults[1];

// Flag potential duplicates
if (!contacts.isEmpty()) {
    System.debug('Possible duplicate contacts: '
        + contacts.size());
}

The RETURNING Clause

RETURNING controls which objects are searched and what fields are returned. Each object can have its own field list, WHERE filter, ORDER BY, and LIMIT.

Per-Object Filters, Ordering, and Limits

// Each object in RETURNING gets its own sub-clauses
List<List<SObject>> results = [
    FIND 'cloud'
    IN ALL FIELDS
    RETURNING
        // Account: filter by type, order by revenue, top 10
        Account(
            Id, Name, Industry, AnnualRevenue
            WHERE Type = 'Customer'
            ORDER BY AnnualRevenue DESC NULLS LAST
            LIMIT 10
        ),
        // Contact: filter active only, order by name
        Contact(
            Id, FirstName, LastName, Email, AccountId
            WHERE DoNotCall = false
            ORDER BY LastName ASC
            LIMIT 20
        ),
        // Lead: open leads only
        Lead(
            Id, FirstName, LastName, Company, Status
            WHERE IsConverted = false AND Status != 'Dead'
            LIMIT 10
        ),
        // Knowledge — search articles
        Knowledge__kav(
            Id, Title, Summary
            WHERE PublishStatus = 'Online' AND Language = 'en_US'
            LIMIT 5
        )
    WITH NETWORK = ALL NETWORKS  // optional: search all communities
    LIMIT 50   // overall limit across all objects combined
];

// Unpack results — index matches RETURNING order
List<Account>       accounts  = (List<Account>)       results[0];
List<Contact>       contacts  = (List<Contact>)       results[1];
List<Lead>          leads     = (List<Lead>)          results[2];
List<Knowledge__kav> articles = (List<Knowledge__kav>) results[3];
Index ordering matters: The index into results[] must match the order of objects in your RETURNING clause. If you add or reorder objects, update all your array index references accordingly.

RETURNING with Relationship Traversal

// RETURNING can include relationship fields (child-to-parent)
List<List<SObject>> enriched = [
    FIND 'Acme'
    IN NAME FIELDS
    RETURNING
        Contact(
            Id, FirstName, LastName,
            Account.Name,       // parent Account name
            Account.Industry    // parent Account industry
            WHERE Account.Type = 'Customer'
        )
];

List<Contact> contacts = (List<Contact>) enriched[0];
for (Contact c : contacts) {
    System.debug(c.FirstName + ' at '
        + c.Account.Name + ' (' + c.Account.Industry + ')');
}

SOSL in Apex — Patterns & Bind Variables

🔗

Bind Variables in SOSL

SOSL supports bind variables with the : prefix — just like SOQL.

  • Prevents SOSL injection
  • Auto-escapes special characters
  • Works for the search term and RETURNING WHERE values
  • Cannot bind field names or object names
  • Use wildcards in the bound variable itself
// Bind variable — always prefer this over string concat
String userSearch = 'cloud'; // from user input
List<List<SObject>> results =
    [FIND :userSearch IN ALL FIELDS
     RETURNING Account(Id, Name), Contact(Id, Name)];

// Append wildcard BEFORE binding for prefix matching
String prefix = userSearch + '*'; // 'cloud*' matches 'cloudforce', etc.
List<List<SObject>> prefixResults =
    [FIND :prefix IN NAME FIELDS
     RETURNING Account(Id, Name LIMIT 10)];

// Bind variable with RETURNING WHERE
String targetType = 'Customer';
List<List<SObject>> filtered =
    [FIND :userSearch IN ALL FIELDS
     RETURNING Account(Id, Name WHERE Type = :targetType)];

// WRONG — don't concatenate user input
// [FIND :userSearch + '*' IN ALL FIELDS...]
// CORRECT — build the string first, then bind
String wildcardSearch = userSearch.escapeHtml4() + '*';
List<List<SObject>> safe =
    [FIND :wildcardSearch IN NAME FIELDS
     RETURNING Account(Id, Name LIMIT 5)];
🔄

Dynamic SOSL

Use Search.query() for runtime-built SOSL strings.

  • Search.query(soslString)
  • Returns List<List<SObject>>
  • Escape search terms with String.escapeSingleQuotes()
  • Whitelist object and field names
  • More flexible than inline SOSL
// Dynamic SOSL using Search.query()
public with sharing class SearchService {

    public static Map<String, List<SObject>> search(
            String term, List<String> objectNames) {

        // Escape the search term
        String safe = String.escapeSingleQuotes(
            term.trim()) + '*';

        // Whitelist-validated RETURNING clause
        List<String> allowed = new List<String>{
            'Account','Contact','Lead','Opportunity'};
        List<String> returning = new List<String>();
        for (String obj : objectNames) {
            if (allowed.contains(obj)) {
                returning.add(obj + '(Id, Name LIMIT 10)');
            }
        }

        if (returning.isEmpty()) return new Map<String, List<SObject>>();

        String sosl = 'FIND \'' + safe + '\''
            + ' IN NAME FIELDS'
            + ' RETURNING ' + String.join(returning, ', ');

        List<List<SObject>> raw = Search.query(sosl);

        Map<String, List<SObject>> result =
            new Map<String, List<SObject>>();
        for (Integer i = 0; i < objectNames.size(); i++) {
            if (i < raw.size()) {
                result.put(objectNames[i], raw[i]);
            }
        }
        return result;
    }
}

Testing SOSL in Apex Tests

SOSL searches don't find data inserted during tests unless you register it with Test.setFixedSearchResults().

  • Index not updated during tests
  • Use Test.setFixedSearchResults(ids)
  • Call it before the SOSL-executing code
  • The fixed list is returned regardless of search term
  • Test both empty and populated results
@IsTest
private class SearchServiceTest {

    @IsTest
    static void testSearch_returnsResults() {
        // Create test data
        Account acc = new Account(Name = 'ACME Cloud Corp');
        insert acc;
        Contact con = new Contact(
            FirstName = 'Jane', LastName = 'Cloud',
            AccountId = acc.Id);
        insert con;

        // Register fixed SOSL results — the search index
        // is NOT updated during tests, so we tell Apex
        // which records should be "found"
        Test.setFixedSearchResults(
            new List<Id>{ acc.Id, con.Id });

        Test.startTest();
        Map<String, List<SObject>> results =
            SearchService.search('cloud',
                new List<String>{'Account','Contact'});
        Test.stopTest();

        System.assertEquals(1, results.get('Account').size(),
            'Should find 1 account');
        System.assertEquals(1, results.get('Contact').size(),
            'Should find 1 contact');
    }

    @IsTest
    static void testSearch_noResults() {
        // Register EMPTY fixed results
        Test.setFixedSearchResults(new List<Id>());

        Test.startTest();
        Map<String, List<SObject>> results =
            SearchService.search('xyz123',
                new List<String>{'Account'});
        Test.stopTest();

        System.assert(results.get('Account') == null
            || results.get('Account').isEmpty(),
            'Should return no results');
    }
}

Search.find() — Structured Alternative

The Search class provides a structured API for building SOSL queries programmatically.

  • Search.SearchQuery object
  • Type-safe, no string building
  • Supports all SOSL clauses
  • Returns List<Search.SearchResult>
  • Good for complex runtime queries
// Search.find() — programmatic SOSL without string building
Search.SearchQuery query = new Search.SearchQuery(
    'cloud software'  // search term
);

// Configure what to return
Search.SearchGroup grp = new Search.SearchGroup(
    Schema.SObjectType.Account.getSObjectType(),
    new List<String>{'Id','Name','Industry'}
);
grp.setLimit(10);
grp.setOrderBy('Name');

query.addReturningSpec(grp);
query.setSearchGroup(Search.SearchGroup.ALL_FIELDS);

// Execute
List<Search.SearchResult> results =
    Search.find(query).getRecords();

for (Search.SearchResult sr : results) {
    SObject record = sr.getSObject();
    System.debug('Found: ' + record.get('Name'));
}

Best Practices

Use SOSL for Text Search, SOQL for Exact Lookups

SOSL is for user-typed "search box" queries. SOQL is for known field values. Never use SOQL LIKE '%term%' (TABLE_SCAN) when SOSL would serve the need.

❌ [SELECT Id FROM Account WHERE Name LIKE '%cloud%']
✅ [FIND 'cloud' IN NAME FIELDS RETURNING Account(Id,Name)]

Always Use Bind Variables for User Input

Binding the search term prevents SOSL injection and automatically escapes special characters. Never concatenate user input directly into the FIND clause.

❌ 'FIND \'' + userTerm + '\' IN ALL FIELDS'
✅ [FIND :userTerm IN ALL FIELDS ...]

Narrow the Search Group for Performance

IN NAME FIELDS is fastest. IN ALL FIELDS searches everything. Always use the narrowest group that satisfies your use case.

❌ IN ALL FIELDS // searches everything unnecessarily
✅ IN NAME FIELDS // for autocomplete/name search

Use Test.setFixedSearchResults() in Tests

The search index is not updated during unit tests. Without fixed results, SOSL always returns empty in tests — masking bugs.

❌ Test inserts record; SOSL returns empty; test "passes" for wrong reasons
✅ Test.setFixedSearchResults(new List<Id>{acc.Id});

Add LIMIT to Each RETURNING Object

Each object can return up to 2,000 rows. Without a LIMIT, a popular search term could return 2,000 rows per object, consuming heap rapidly.

❌ RETURNING Account(Id, Name) // up to 2000 rows
✅ RETURNING Account(Id, Name LIMIT 20)

Remember Index Lag

The search index updates asynchronously. Records created seconds ago may not appear in SOSL results. Don't use SOSL for guaranteed up-to-the-second accuracy — use SOQL for that.

❌ SOSL immediately after DML insert expecting the new record
✅ SOQL for immediate post-insert lookups; SOSL for user search
