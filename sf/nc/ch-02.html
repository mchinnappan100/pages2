OAuth 2.0 Overview

OAuth 2.0 is the industry-standard protocol for API authorization. Named Credentials support multiple OAuth 2.0 flows — each suited to different integration scenarios.

🤝

Client Credentials Flow

Machine-to-machine. App uses its own credentials — no user involved. Best for server-side integrations.

  • System-to-system auth
  • App authenticates as itself
  • No user interaction needed
  • Most common for Apex callouts
  • Token auto-refreshed by Salesforce
  • Requires client_id + client_secret
// Setup → External Credentials → New
// Protocol: OAuth 2.0
// Flow Type: Client Credentials
// Token URL: https://auth.example.com/oauth/token
// Client ID: your-app-client-id
// Client Secret: your-app-client-secret
// Scope: api read write

// Apex usage — no special code needed
// Salesforce handles token fetch and refresh automatically
HttpRequest req = new HttpRequest();
req.setEndpoint('callout:My_OAuth_API/data/accounts');
req.setMethod('GET');
HttpResponse res = new Http().send(req);
// Authorization: Bearer {access_token} is added automatically!
🔐

JWT Bearer Flow

App uses a private key to sign a JWT assertion — no client secret required. More secure than Client Credentials.

  • Uses RSA private key signing
  • No client_secret needed
  • Harder to credential-stuff
  • Cert stored in Salesforce Certificate & Key Manager
  • Common with Salesforce-to-Salesforce
  • Ideal for high-security integrations
// Step 1: Generate/upload cert in Setup → Certificate and Key Management
// Step 2: Create External Credential
//   Flow Type: JWT Bearer Token
//   Token URL: https://login.salesforce.com/services/oauth2/token
//   Issuer: your-connected-app-client-id
//   Per User Subject: {!$User.UserName}  (for org-wide: use a fixed value)
//   Signing Certificate: (select the cert from step 1)

// Step 3: Named Credential uses the External Credential
// Apex code — same pattern as always:
req.setEndpoint('callout:Target_Org_API/services/data/v61.0/sobjects/Account');
// Salesforce signs the JWT, sends it to get an access token,
// then adds Authorization: Bearer {token} to your callout
👤

Authorization Code (Per-User)

Each Salesforce user authenticates individually with the target system. Their tokens are stored against their Salesforce identity.

  • User-level consent
  • User clicks "Allow Access" once
  • Tokens stored per-user in Salesforce
  • Uses Named Principal in External Credential
  • User's callouts use their token
  • Ideal for social/CRM integrations
// Setup path:
// 1. External Credential → Protocol: OAuth 2.0
//    Flow: Authorization Code and Credentials
//    Auth URL: https://accounts.google.com/o/oauth2/auth
//    Token URL: https://oauth2.googleapis.com/token
//    Client ID / Secret: from Google Cloud Console

// 2. Add "Named Principal" for per-user auth
//    → Each user has their own token, stored by Salesforce

// 3. Assign via Permission Set:
//    Permission Set → External Credential Principal Access
//    → Grant access to the Named Principal

// 4. User authenticates:
//    Setup → Authentication Settings for External Systems
//    → User clicks "Allow" → Google OAuth consent screen
//    → Token stored for that user

// 5. Apex — Salesforce uses calling user's token automatically
req.setEndpoint('callout:Google_API/gmail/v1/users/me/messages');
// Authorization: Bearer {user-specific-token} injected automatically
📋

Token Refresh

Named Credentials automatically handle OAuth token expiry and refresh — no code needed.

  • Access tokens expire (usually 1 hour)
  • Salesforce stores the refresh token
  • Auto-refreshes before expiry
  • Transparent to Apex code
  • Retry on 401 is handled automatically
  • Refresh token rotation supported

External Credentials — Modern Architecture

External Credential + Named Credential Structure

// Architecture:
//
// External Credential (auth config):
//   - Protocol: OAuth 2.0
//   - Flow: Client Credentials
//   - Token URL, Client ID, Client Secret, Scope
//
// Named Credential (URL + path config):
//   - URL: https://api.example.com
//   - External Credential: (select the EC above)
//   - Generate Auth Header: true
//   - Allow Merge Fields: true
//
// Permission Set (access control):
//   - External Credential Principal Access: (EC + Principal)
//   - Users/profiles need this to make callouts
//
// Result in Apex:
req.setEndpoint('callout:My_Named_Cred/v1/accounts');
// Salesforce:
// 1. Looks up the Named Credential
// 2. Finds the External Credential
// 3. Gets/refreshes the OAuth token
// 4. Adds Authorization: Bearer {token}
// 5. Makes the callout

Connected Apps for OAuth

When You're the OAuth Provider (Salesforce as target)

// When another system calls Salesforce's APIs via OAuth,
// you need a Connected App in the TARGET org:

// Setup → App Manager → New Connected App:
// - Enable OAuth Settings: true
// - Callback URL: https://login.salesforce.com/services/oauth2/callback
// - Selected OAuth Scopes:
//     api (full access)
//     refresh_token (for token refresh)
// - Enable Client Credentials Flow: true (for machine-to-machine)
// - Manage Consumer Details → get Consumer Key (client_id) and Secret

// Then in the CALLING org's Named Credential:
// Token URL: https://login.salesforce.com/services/oauth2/token
// (or https://test.salesforce.com for sandbox)
// Client ID: (Connected App Consumer Key)
// Client Secret: (Connected App Consumer Secret)

// For JWT Bearer to Salesforce:
// Upload your public cert to the Connected App
// Setup → App Manager → (your app) → Manage → Upload a Certificate
04

Best Practices

Prefer Client Credentials for Server-to-Server

For machine-to-machine integrations where no user is involved, Client Credentials flow is the most common and simplest to set up with Named Credentials.

✅ Flow: Client Credentials → Salesforce manages tokens automatically

Use JWT Bearer for Maximum Security

JWT Bearer eliminates the client_secret entirely — the integration authenticates with an asymmetric key pair. No secret to rotate or leak.

✅ RSA key in Salesforce Certificate Manager → no shared secret

Assign External Credential Access via Permission Sets

External Credential access is controlled by Permission Sets. Only assign to users/profiles that actually need to make the callout.

✅ Permission Set → External Credential Principal Access → assign to integration users only

Test in Sandbox First with Sandbox Endpoints

Configure sandbox Named Credentials to point at sandbox/staging endpoints of external systems. Never test integrations against production external APIs.

✅ Sandbox NC: Token URL = https://test.salesforce.com; Production NC = https://login.salesforce.com
