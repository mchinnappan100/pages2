External Credentials Architecture

Introduced in API 53, External Credentials separate the authentication configuration from the endpoint URL, enabling much more flexible auth management — including per-user OAuth tokens.

Three-Layer Architecture

// Layer 1: External Credential (auth config)
// ─────────────────────────────────────────
// Stores: Protocol (OAuth/Basic/Custom), Token URL,
//         Client ID, Client Secret, Scope, Flow type
// One External Credential can serve many Named Credentials

// Layer 2: Named Credential (endpoint URL)
// ─────────────────────────────────────────
// Stores: Base URL (https://api.example.com)
// Links to: External Credential
// Sets: Generate Auth Header = true / false
// Used in: req.setEndpoint('callout:NC_Name/path')

// Layer 3: Permission Set (access control)
// ─────────────────────────────────────────
// Controls: Which users/profiles can use the credential
// Contains: External Credential Principal Access
// Without this: users cannot make callouts using the NC

// Flow:
// User makes callout → Salesforce checks PS → looks up EC
// → gets/refreshes token → injects Authorization header → makes request

Named Principals — Per-User Auth

Setting Up Per-User OAuth (Authorization Code Flow)

// GOAL: Each Salesforce user authenticates with the external system
// using THEIR OWN OAuth token, not a shared org-wide token.

// Step 1: Create External Credential
// Protocol: OAuth 2.0
// Flow: Authorization Code and Credentials
// Auth URL: https://accounts.google.com/o/oauth2/auth
// Token URL: https://oauth2.googleapis.com/token
// Client ID / Secret: from Google Cloud Console
// Scope: https://www.googleapis.com/auth/gmail.readonly

// Step 2: Add a "Named Principal" to the External Credential
// Named Principal Name: User_Gmail   (any name)
// Identity Type: Named Principal (per user — NOT Per User!)

// Step 3: Create a Permission Set
// External Credential Principal Access:
//   External Credential: Google_Gmail_EC
//   Principal Name: User_Gmail
// Assign this PS to users who need Gmail access

// Step 4: Users authenticate
// When user's code first hits the NC, Salesforce redirects to Google OAuth
// User logs in to Google, grants permission
// Token stored against user's Salesforce identity
// Subsequent calls use stored token (auto-refreshed)

// Alternatively, admin can trigger auth:
// Setup → Authentication Settings for External Systems
// → Shows connected credentials per user

// Step 5: Apex code — no change needed!
// req.setEndpoint('callout:Google_Gmail_NC/gmail/v1/users/me/messages');
// Salesforce automatically uses the CALLING USER's token

Custom Headers & Custom Auth

API Key Auth via Custom Headers

// Many APIs use API keys in custom headers (not OAuth)
// Setup → External Credentials → New
// Protocol: Custom
// Then add Custom Headers under the External Credential:
//   Header Name: X-API-Key
//   Value: your-api-key-value  (stored encrypted)

// Named Credential links to this External Credential
// Result: every callout using this NC automatically gets
// the X-API-Key header injected

// In Apex — no header code needed:
HttpRequest req = new HttpRequest();
req.setEndpoint('callout:OpenAI_NC/v1/chat/completions');
req.setMethod('POST');
req.setHeader('Content-Type', 'application/json');
req.setBody(JSON.serialize(new Map<String,Object>{
    'model' => 'gpt-4',
    'messages' => new List<Object>{
        new Map<String,String>{ 'role' => 'user', 'content' => 'Hello!' }
    }
}));
HttpResponse res = new Http().send(req);
// X-API-Key: your-api-key automatically added by Salesforce!

// Multiple custom headers — add multiple rows in EC definition
// e.g., X-API-Key + X-API-Version + X-Client-ID all injected automatically

Merge Fields in Named Credentials

Dynamic Credential Injection

// Named Credentials support merge fields in:
// - URL: use {!$Credential.NC_Name.URL_Parameter}
// - Headers: use {!$Credential.ExternalCredential_Name.Field_Name}
// - Body: use merge fields if "Allow Merge Fields in HTTP Body" is enabled

// Example: Inject username into a header from the NC
// In NC custom header definition:
//   Header Name: X-Username
//   Value: {!$Credential.UserName}      (for basic auth username)
// Or for external credential custom field:
//   Value: {!$Credential.MyEC.custom_field}

// Common merge field tokens:
// {!$Credential.UserName}       — username from credential
// {!$Credential.Password}       — password (never logged)
// {!$Credential.OAuthToken}     — current access token
// {!$User.Id}                   — running user's Salesforce Id
// {!$User.Email}                — running user's email
// {!$User.UserName}             — running user's login username
// {!$Organization.Id}           — org 15-char Id
// {!$Organization.Name}         — org name

// Useful pattern: inject org ID for multi-tenant API identification
// In NC header: X-Org-Id = {!$Organization.Id}
// API knows which Salesforce org is calling without extra code

Deploying Named Credentials via SFDX

Metadata Structure & Deployment

// Named Credential metadata files are in:
// force-app/main/default/namedCredentials/
//   My_API.namedCredential-meta.xml

// namedCredential-meta.xml (legacy):
// <?xml version="1.0" encoding="UTF-8"?>
// <NamedCredential xmlns="...">
//   <label>My API</label>
//   <endpoint>https://api.example.com</endpoint>
//   <protocol>OAuth</protocol>
//   <generateAuthorizationHeader>true</generateAuthorizationHeader>
//   <allowMergeFieldsInBody>false</allowMergeFieldsInBody>
//   <allowMergeFieldsInHeader>true</allowMergeFieldsInHeader>
// </NamedCredential>

// External Credential files:
// force-app/main/default/externalCredentials/
//   My_EC.externalCredential-meta.xml

// IMPORTANT: Credentials (passwords, client secrets) are NOT
// stored in the metadata XML. The XML stores the structure only.
// Secrets are entered manually in each org after deployment.

// Deploy the structure:
// sf project deploy start --source-dir force-app/main/default/namedCredentials

// After deploy, admin must enter the secret values in Setup
// This is intentional security design — secrets never in source control

Best Practices

Use External Credentials for All New Integrations

The External Credential + Named Credential split is more maintainable. Multiple NCs can share one EC, and per-user auth is only available via this model.

✅ EC (auth) + NC (URL) = reusable, auditable, permission-controlled

Control Access with Permission Sets, Not Profiles

Assign External Credential Principal Access via Permission Sets — not profiles. This allows fine-grained, just-in-time access control.

✅ Permission Set: "Integration_Access" → assign only to users who need it

Never Put Secrets in Metadata XML

Credential values (passwords, client secrets, API keys) must never appear in metadata XML files that get committed to source control. Enter them manually in Setup after deployment.

❌ <password>mySecret123</password> in XML committed to git
✅ Blank/placeholder in XML; admin enters real value in Setup

Use Custom Headers for API Key Authentication

For APIs that use API keys in headers (X-API-Key, Authorization: ApiKey), use External Credential custom headers. Keys stored encrypted in Salesforce, injected automatically.

✅ EC Custom Header: X-API-Key = {stored value} → injected on every callout
