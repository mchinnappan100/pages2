Chapter 03 · Testing & Debugging

AI for Testing, Debugging & Log Analysis

Use AI to generate complete Apex test classes, close coverage gaps, diagnose debug log failures in minutes, interpret PMD violations, and fix test failures — transforming the most time-consuming quality assurance tasks into automated, accelerated workflows.

Reading time: ~30 min
Multiplier: 4–8×
Key tools: Claude · apex-test-class-failure-helper · sf-log-viewer

Testing is the Salesforce development task most developers dread — and most frequently shortcut under time pressure. Apex requires 75% code coverage for deployment, but test classes that simply inflate coverage numbers without testing business logic provide false confidence and a maintenance burden. AI changes this equation: generating test classes with genuine assertions, multiple scenarios, and proper test data setup in minutes rather than hours.

This chapter covers the full testing and debugging lifecycle: generating test classes from production code, identifying and closing coverage gaps, using AI as a pair debugger for complex failures, and interpreting Apex debug logs that would otherwise require hours of manual parsing.

Test Class Generation

Generating Full Test Classes from Production Code

The most powerful testing application: paste a complete Apex class and ask AI to generate the corresponding test class. AI analyzes the logic paths, identifies the scenarios that need testing, and generates test methods with proper data setup, assertions, and edge case coverage.

Prompt Template — Full Test Class Generation
Generate a complete Apex test class for the following production Apex class.

Requirements for the test class:
- Use @isTest annotation and @TestSetup for shared test data
- Create realistic test data — do not use hardcoded Ids
- Cover the following scenarios for EACH public method:
  * Happy path (valid inputs, expected output)
  * Null/empty input handling
  * Bulk scenario (200 records) to verify governor limit safety
  * Error/exception paths (if the method throws custom exceptions)
- Use System.assert(), System.assertEquals(), and System.assertNotEquals() with descriptive messages
- Do NOT use System.assert(true) or assertions without messages
- Aim for >95% code coverage, not just 75%
- If the class interacts with external services, use Test.setMock() appropriately

[PASTE YOUR PRODUCTION APEX CLASS HERE]

Before AI: Writing a full test class for a 150-line Apex service class with 5 methods takes 3–4 hours: understanding each method's logic, setting up test data, writing assertions, and handling the bulk scenario.

After AI: 10–15 minutes — 3 minutes to generate, 10 minutes to review and adjust test data field names for your specific org schema.

Test Data Factory Generation

Test data factories — classes that create realistic SObject hierarchies for testing — are essential for maintainable test suites but tedious to write. AI generates complete data factory classes from a description of your object model.

Prompt Template — Test Data Factory
Generate a Salesforce Apex TestDataFactory class for the following object model:

Objects and required fields:
- Account: Name (required), Type, AnnualRevenue, BillingCountry
- Contact: LastName (required), AccountId (required), Email, Phone, Title
- Opportunity: Name (required), AccountId (required), StageName, CloseDate (required), Amount
- Case: Subject (required), AccountId, ContactId, Status, Priority, Origin

Requirements:
- Each object has a static create[Object]() method that accepts a Map<String,Object>
  of field overrides — merge with sensible defaults
- Each object also has a static create[Object]List(Integer count) method for bulk creation
- Do NOT insert records — return SObject instances for the caller to insert
- Include a createFullHierarchy() method that creates and inserts
  Account > Contact + Opportunity + Case in one call (useful for integration tests)
Productivity Gain

A TestDataFactory covering 5 objects with override support and bulk creation methods takes 4–5 hours to write correctly. AI generates it in 4 minutes. The developer spends 15 minutes adjusting field names and required fields to match the org's actual schema. This is a one-time investment that accelerates every subsequent test class in the project.

Coverage Gap Analysis and Fix

Identifying Untested Code Paths

When a class has insufficient coverage, AI can analyze both the production class and the existing test class to identify exactly which branches are not tested and generate the missing test methods.

Prompt Template — Coverage Gap Analysis
I have an Apex class with insufficient test coverage. Analyze both files and tell me:
1. Which specific branches and code paths are NOT covered by the existing tests
2. What test scenarios are missing
3. Generate the additional test methods needed to achieve >90% coverage

Production class:
[PASTE PRODUCTION CLASS]

Existing test class:
[PASTE EXISTING TEST CLASS]

For each missing test method you generate, explain WHY this scenario needs testing
(what business logic it validates, not just what line it covers).

Fixing Test Failures from CI/CD Pipelines

When tests fail in a CI/CD pipeline, the error output contains the failure message, stack trace, and context — exactly what AI needs to diagnose the root cause and propose a fix.

Prompt Template — Test Failure Diagnosis
My Apex test is failing in the CI/CD pipeline. Diagnose the root cause and provide a fix.

Test failure output:
[PASTE THE FULL TEST FAILURE MESSAGE AND STACK TRACE]

Production class being tested:
[PASTE PRODUCTION CLASS]

Test class:
[PASTE TEST CLASS]

Possible context: [describe any recent code changes that might be related]

Provide:
1. Root cause analysis (what is actually failing and why)
2. Whether the fix is in the test class or the production class
3. The corrected code for whichever file needs to change
Productivity Gain

Diagnosing a non-obvious test failure — a subtle NullPointerException caused by missing test data, a SOQL ordering dependency, or a mixed DML error — can take 30–90 minutes of careful analysis. AI diagnoses the root cause from the stack trace and code in 60 seconds, often identifying the exact line and the reason. The apex-test-class-failure-helper npm package automates this exact workflow from the CLI.

Debugging Complex Issues with AI

Governor Limit Exceptions

Governor limit exceptions — "Too many SOQL queries: 101", "Apex CPU time limit exceeded" — have complex root causes that are difficult to trace without understanding the full execution path. AI can analyze the stack trace and code to identify the source and propose architectural fixes.

Prompt Template — Governor Limit Root Cause
I am hitting a Salesforce governor limit exception. Help me find the root cause
and the architectural fix.

Exception: System.LimitException: Too many SOQL queries: 101

Stack trace:
[PASTE STACK TRACE]

The trigger/class entry points involved:
[PASTE THE TOP-LEVEL TRIGGER AND ANY RELEVANT CLASSES]

Context: This error started occurring after [describe the recent change or
when it started]. It only happens when [describe the conditions].

Provide:
1. Where in the code the 101st SOQL is most likely being issued
2. Why the limit is being hit (what loop or recursive pattern causes it)
3. The recommended architectural fix (e.g. move query outside loop, use Maps, use Platform Cache)
4. Any other SOQL queries in the code that are at risk of contributing

Mixed DML and Record Type Errors

Prompt Template — Specific Salesforce Error Diagnosis
I am getting the following Salesforce error. Explain what it means, why it occurs
in my specific code, and how to fix it.

Error: [PASTE THE EXACT ERROR MESSAGE]

Code causing the error:
[PASTE THE RELEVANT CODE SECTION]

What I've tried: [describe any fixes you've already attempted]

Please explain:
1. The exact technical reason this error occurs on the Salesforce platform
2. The specific line in my code that triggers it
3. The fix — both a quick workaround and the proper architectural solution
4. How to test that the fix works correctly

Apex Debug Log Analysis

Apex debug logs are dense files that can be tens of megabytes for complex transactions. Finding the relevant information — the failing SOQL, the line that exceeded CPU time, the DML that caused a trigger re-entry — requires pattern recognition that AI performs far faster than manual inspection.

Log Summarization

Prompt Template — Debug Log Summary
Analyze this Apex debug log excerpt and provide a structured summary:

[PASTE 50–200 LINES FROM THE RELEVANT SECTION OF THE DEBUG LOG]

Provide:
1. Total SOQL queries issued and list any that appear inside loops
2. Total DML statements and what objects were affected
3. CPU time consumption — identify the top 3 most expensive operations
4. Any exception messages found
5. The execution entry point and the key class/method call chain
6. Any Salesforce limits that were consumed significantly (Heap, CPU, DML rows)
Productivity Gain

Manually parsing a 10MB Apex debug log to find performance issues takes 1–3 hours for a developer unfamiliar with the specific code path. Feeding a 200-line excerpt from the relevant section to AI produces a structured performance summary in 10 seconds — identifying the specific SOQL queries in loops and CPU-intensive methods immediately. The sf-log-viewer npm package enhances this further with a visual browser-based log parser.

Performance Profiling from Logs

Prompt Template — Performance Profile
Profile the performance of this Apex execution from the debug log.
I am trying to understand why this transaction is slow (>10 seconds CPU time).

[PASTE THE EXECUTION UNITS / CUMULATIVE LIMIT USAGE SECTION OF THE LOG]

Tell me:
1. Which methods consumed the most CPU time, in descending order
2. Which SOQL queries are the most expensive (by row count and selectivity)
3. Whether there are any redundant queries (same query issued multiple times)
4. Your top 3 specific recommendations for reducing CPU time
5. Estimate the CPU time reduction achievable from each recommendation

PMD Violation Diagnosis and Fixing

Salesforce Code Scanner (PMD) produces violation reports that can be overwhelming — dozens of rules, varying severities, and terse descriptions that don't always explain the correct fix. AI translates PMD violations into plain-English explanations and correct code fixes.

PMD Batch Fix

Prompt Template — PMD Violation Fix
I have Salesforce PMD violations in the following Apex class. For each violation,
explain what the rule means, why it matters, and provide the corrected code.

PMD violations:
[PASTE THE PMD OUTPUT — e.g.:
  Line 23: ApexCRUDViolation — execute a CRUD check before this SOQL statement
  Line 45: AvoidDeeplyNestedIfStmts — deeply nested if statements
  Line 67: NullAssignment — assigning an object to null is unnecessary
]

Apex class:
[PASTE THE CLASS]

After explaining all violations, provide:
1. The complete corrected Apex class with all violations resolved
2. A brief note for each fix explaining what changed and why
Productivity Gain

A class with 15 PMD violations takes 2–3 hours to fix correctly — understanding each rule, applying the right pattern, and avoiding introducing new violations. AI fixes all 15 violations in one pass in under 5 minutes, with explanations for each change. This is especially valuable for ApexCRUDViolation fixes, which require careful insertion of Schema.describeFieldResult checks that are easy to get wrong.

Suppressing False Positives with Justification

Not all PMD violations warrant a code change — some are false positives in test utility classes or legitimate architectural decisions. AI can help evaluate whether a violation is a genuine risk or a false positive, and generate the @SuppressWarnings annotation with appropriate justification text.

Prompt Template — PMD Suppression Justification
Evaluate whether this PMD violation is a genuine risk or a false positive
that should be suppressed with @SuppressWarnings.

Violation: [PMD rule name and message]
Code in question:
[PASTE THE SPECIFIC CODE SECTION]

Context: [explain the purpose of this class / method]

If it IS a genuine risk: explain the fix.
If it IS a false positive: explain WHY it is safe to suppress in this context,
and generate the @SuppressWarnings('PMD.[RuleName]') annotation with a comment
justifying the suppression for future maintainers.

Summary

Key Takeaways — Chapter 3
  • AI test class generation from production code is one of the highest-multiplier applications — 3–4 hour tasks become 15-minute tasks
  • Always ask for genuine assertions with messages, not coverage-inflating boilerplate — include this requirement explicitly in every test generation prompt
  • Coverage gap analysis (paste both production and test class) is far faster than manually tracing branches in complex logic
  • For governor limit exceptions, provide the full stack trace AND the relevant production code — AI cannot diagnose from stack traces alone
  • Debug log summarization is most effective with focused excerpts (50–200 lines) rather than pasting entire multi-MB logs
  • PMD batch fixing through AI is a force multiplier for legacy codebase cleanup — the pmd-annotations npm package provides the visual dashboard to track suppression decisions across a large codebase
