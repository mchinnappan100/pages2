Chapter 05 · Data, Migration & Integration

AI for Data, Migration & Integration

Use AI to optimize complex SOQL queries, design data migration load plans, map fields between systems, write integration transformation logic, validate data quality rules, and design API contracts — compressing weeks of data architecture work into days.

Reading time: ~35 min
Multiplier: 3–6×
Key tools: Claude · sf-load-plan-generator · datagen-cli · sf-data-util

Data migration and integration work is among the most technically complex and risk-laden work in Salesforce implementations. A migration executed incorrectly can corrupt production data that took years to build. An integration designed without careful attention to governor limits, error handling, and retry logic will fail intermittently in ways that are difficult to diagnose.

AI cannot replace the deep data analysis and stakeholder validation that migration and integration work requires. But it can dramatically accelerate the analytical and design phases: generating load plans, mapping fields between schemas, writing transformation code, building data validation rules, and designing retry logic — all tasks where AI's pattern recognition and code generation capabilities add significant value.

SOQL Query Optimization

Query Performance Analysis

SOQL queries that work in a developer org with 1,000 records fail catastrophically in production orgs with millions of records. AI can analyze a query for selectivity, missing indexes, and governor limit risks — providing optimization recommendations before deployment.

Prompt Template — SOQL Performance Analysis
Analyze this SOQL query for performance issues in a large Salesforce org
(assume 2M Account records, 5M Contact records, 1M Opportunity records).

Query:
[PASTE YOUR SOQL QUERY]

Analyze:
1. Selectivity: which WHERE clause fields are selective? Which are not?
   (Selective = indexed field, fewer than 10% of records match)
2. Indexes: which fields in this query have standard or custom indexes?
   List fields that SHOULD be indexed but are not
3. Governor limit risk: at stated volumes, will this query hit the 50,000 SOQL
   row limit or the 10-second CPU timeout?
4. Relationship traversal cost: if the query traverses relationships, how many
   rows might be retrieved at each level?
5. Optimized version: rewrite the query to be more selective, and recommend
   any custom indexes to request from Salesforce support

Aggregate Query Design

Prompt Template — Aggregate SOQL
Write an optimized SOQL aggregate query for the following reporting requirement.

Business requirement: [describe what you need to measure]
Example: "Show total Opportunity Amount and count by Stage, grouped by Account Industry,
for Opportunities closing in the current fiscal year, only for Accounts with AnnualRevenue > 1M"

Requirements:
- Use AggregateResult appropriately
- Group by the correct fields
- Apply HAVING clauses where needed instead of post-query filtering
- Ensure the query is selective on at least one indexed field
- Return as an Apex method that takes fiscal year as a parameter
  and returns a List<Map<String,Object>> suitable for LWC consumption
Productivity Gain

Designing a complex aggregate query, getting the AggregateResult handling right, and adding the Apex wrapper for LWC consumption takes 90–120 minutes. AI produces a correct implementation in 2 minutes. The developer spends 10 minutes verifying field names, adjusting the fiscal year logic for the org's fiscal year settings, and testing in a sandbox.

Data Migration Planning

Load Plan Generation from Object Relationships

Data migration load plans specify the order in which objects must be loaded to satisfy parent-child foreign key dependencies. Getting the order wrong causes lookup field failures. AI generates correct load plans from an object relationship description.

Prompt Template — Load Plan Generation
Generate a data migration load plan for the following Salesforce implementation.

Objects to migrate (with relationships):
- Account (no parents — load first)
- Contact (parent: Account via AccountId)
- Opportunity (parent: Account via AccountId)
- OpportunityLineItem (parents: Opportunity via OpportunityId, Product2 via Product2Id)
- Product2 (no parents — load with Account)
- Case (parents: Account via AccountId, Contact via ContactId)
- CaseComment (parent: Case via ParentId)
- Attachment / ContentVersion (parent: any object via LinkedEntityId)
- Custom object: ProjectMilestone__c (parent: Opportunity via Opportunity__c)

Additional constraints:
- External ID field on each object: Legacy_Id__c (must be populated for all lookups)
- Self-referencing: Account has a ParentId (account hierarchy — load flat accounts first)
- Many-to-many: Opportunity has related OpportunityContactRole (junction object)

Generate:
1. The correct load order (numbered sequence)
2. For each object: which fields need external ID resolution and from which parent
3. A JSON load-plan.json format compatible with the Salesforce Data Loader
4. Rollback sequence (reverse order for deletion if migration fails)
5. Any circular dependency risks and how to resolve them
Productivity Gain

Manually designing a load plan for 10+ objects with complex relationships takes a migration consultant 4–8 hours — carefully mapping every FK dependency, identifying circular references, and writing the JSON. AI generates a complete, correct load plan in 3 minutes. The consultant spends 30 minutes verifying the field names against the actual org schema and adding any org-specific configuration. The sf-load-plan-generator npm package then validates the load plan against the live org.

Migration Risk Assessment

Prompt Template — Migration Risk Assessment
Perform a risk assessment for the following Salesforce data migration.

Source system: [legacy CRM / spreadsheets / SAP / etc.]
Target: Salesforce [edition]
Record volumes:
- Account: [n] records
- Contact: [n] records
- [other objects and volumes]

Data characteristics:
- Data quality issues observed in source: [describe known issues]
- Relationships: [any complex or unclear relationship mappings]
- Historical data: [are you migrating all history or a cutoff date]
- Attachments/files: [volume and type of file attachments]

Identify:
1. Top 5 migration risks with likelihood (High/Medium/Low) and impact
2. Data quality checks to run BEFORE migration begins
3. Go/no-go criteria — what conditions must be true before migrating production
4. Recommended testing sequence (Dev → UAT → Prod)
5. Estimated migration duration at stated volumes using Bulk API 2.0
6. Rollback plan if migration fails midway

Field Mapping and Data Transformation

Field Mapping Document Generation

Field mapping between source and target systems is one of the most labor-intensive parts of any migration. AI can generate an initial mapping from a description of the source schema and Salesforce target, identifying type mismatches, required transformations, and fields that need new custom field creation.

Prompt Template — Field Mapping
Generate a field mapping document for migrating from the following source schema
to Salesforce.

Source system: [e.g. Microsoft Dynamics 365]
Source object: [e.g. Account / Customer]
Source fields (paste CSV or list):
[PASTE SOURCE FIELDS WITH DATA TYPES]
e.g.:
  customer_id        | INT (primary key)
  company_name       | VARCHAR(255)
  annual_revenue_usd | DECIMAL(15,2)
  created_on         | DATETIME
  account_status     | ENUM('Active','Inactive','Prospect')
  primary_contact    | VARCHAR(100) (free text, "FirstName LastName")

Target Salesforce object: Account

Generate a mapping table with columns:
| Source Field | Source Type | SF Field API Name | SF Field Type | Transform Required | Notes |

For each field:
- Map to the most appropriate standard Salesforce field where one exists
- Flag fields requiring a new custom field (with recommended API name and type)
- Describe any transformation needed (type conversion, splitting, lookup resolution)
- Flag fields where data quality validation is recommended before migration

Transformation Logic Code Generation

Prompt Template — ETL Transformation Code
Write a Node.js data transformation function for the following migration mapping.

Source: CSV export from legacy system
Target: Salesforce Bulk API 2.0 CSV format for Account object

Transformations required:
1. customer_id → Legacy_Id__c (direct copy, used as External ID)
2. company_name → Name (trim whitespace, capitalize first letter of each word)
3. annual_revenue_usd → AnnualRevenue (parse to number, default 0 if null/empty)
4. created_on → [not migrated — Salesforce CreatedDate cannot be set via API]
5. account_status → Type mapping:
   'Active' → 'Customer'
   'Inactive' → 'Other'
   'Prospect' → 'Prospect'
   null/unknown → 'Other'
6. primary_contact → [split on first space: first word = first name, rest = last name]
   [create separate Contact records — output to a contacts.csv alongside accounts.csv]

Write a complete Node.js script that:
- Reads input.csv
- Applies all transformations
- Writes accounts.csv (for Account Bulk API load)
- Writes contacts.csv (for Contact Bulk API load, with Legacy_Id__c on both for relationship)
- Logs a summary: total input rows, successfully transformed, skipped (with reason)
- Handles CSV files with 500k+ rows efficiently (streaming, not loading all into memory)
Productivity Gain

Writing a streaming CSV transformation script with correct handling of nulls, type conversions, enum mapping, and dual-output for related objects takes 4–6 hours for a developer. AI generates a complete, streaming-safe Node.js implementation in 3 minutes. The developer spends 20 minutes testing with a sample file and adjusting edge cases. For a migration with 10 objects, this saves 40–60 hours of transformation code development.

Integration Development

REST API Integration with Error Handling

Prompt Template — Integration Apex Class
Write an Apex class that integrates Salesforce with an external REST API.

Integration name: ERP Order Creation
External endpoint: POST https://erp.example.com/api/v2/orders
Authentication: OAuth 2.0 client credentials (credentials in Named Credential: ERP_API)

Request payload (JSON):
{
  "salesforceOpportunityId": "[Opportunity.Id]",
  "customerExternalId": "[Account.ERP_Customer_Id__c]",
  "orderLines": [
    { "productCode": "[OpportunityLineItem.Product2.ProductCode]",
      "quantity": "[OpportunityLineItem.Quantity]",
      "unitPrice": "[OpportunityLineItem.UnitPrice]" }
  ],
  "requestedDeliveryDate": "[Opportunity.CloseDate in ISO-8601]"
}

Response handling:
- Success (201): extract "orderId" from response body, store in Opportunity.ERP_Order_Id__c
- 400 Bad Request: log error, create a Task on Opportunity for rep to review
- 500 Server Error: throw custom exception for retry by calling code
- Timeout (>10 seconds): treat as 500

Requirements:
- @future(callout=true) method for async execution
- Use HttpRequest, HttpResponse — no third-party libraries
- Proper JSON serialization/deserialization
- Respect Salesforce callout governor limits (10 seconds timeout, handle 10 callout limit)
- Include unit test stubs using HttpCalloutMock

Platform Event Integration Pattern

Prompt Template — Platform Event Architecture
Design and implement a Platform Event-based integration pattern for the following requirement.

Use case: When a Salesforce Case is resolved (Status changes to 'Closed'), notify an
external customer portal in near real-time.

Design requirements:
- Decouple Salesforce from the external system
- Handle the external system being temporarily unavailable (retry logic)
- Guarantee at-least-once delivery
- Do not block the Salesforce transaction that closes the Case

Generate:
1. Platform Event definition: CaseResolved__e with required fields
2. Apex trigger on Case that publishes the event on Status →'Closed'
3. Apex trigger on CaseResolved__e that calls the external API
4. Retry logic: if the callout fails, re-publish the event with a retry counter field
   (stop retrying after 3 attempts, create a monitoring record instead)
5. A simple monitoring custom object ResolutionNotificationLog__c to track
   successful and failed notifications with timestamps

Include governor limit considerations for high-volume Case close scenarios.

Data Quality and Validation

Data Quality Rule Generation

Before a data migration goes live, a suite of data quality validation rules must be run against the source data to identify issues that will cause load failures or data integrity problems in Salesforce. AI generates comprehensive validation rule sets from a description of the target schema requirements.

Prompt Template — Data Quality Validation Rules
Generate a comprehensive data quality validation script for a Salesforce data migration.

Target object: Contact
Salesforce field requirements:
- LastName: Required, max 80 chars
- Email: Optional but must be valid format if present; must be unique across migration set
- Phone: Optional but if present must match E.164 format or US format (###-###-####)
- AccountId: Required — must resolve to an existing Account Legacy_Id__c
- Birthdate: Optional, must be a valid date, must be before today, person must be < 120 years old
- LeadSource: Must be one of: 'Web', 'Phone Inquiry', 'Partner Referral', 'Trade Show', 'Other'

Write a Node.js validation script that:
1. Reads contacts.csv (up to 500k rows, streaming)
2. Runs all the above validations on each row
3. Outputs:
   - contacts_valid.csv (rows that passed all validations)
   - contacts_errors.csv (rows that failed, with an additional column listing each failed rule)
4. Prints a summary report:
   - Total rows processed
   - Pass rate
   - Failure breakdown by rule (which rule failed most often)
   - Top 10 most common error values for each failing rule
5. Exit code 1 if error rate > 5%, else exit code 0 (for CI/CD integration)
Productivity Gain

Building a comprehensive, streaming data validation script with rule-by-rule error reporting, a pass/fail summary, and CI/CD integration takes a developer 6–8 hours. AI generates a complete, production-ready implementation in 4 minutes. For migrations with 8–10 objects each needing validation scripts, this represents 50–80 hours of script development reduced to a few hours of review and testing. The datagen-cli npm package complements this by generating realistic test data to validate the validation scripts themselves before running on real source data.

Post-Migration Reconciliation Queries

Prompt Template — Migration Reconciliation
Generate post-migration reconciliation SOQL queries to verify a Salesforce data migration.

Migration details:
- Migrated objects: Account, Contact, Opportunity, Case
- Expected record counts (from source system):
  Account: 45,230
  Contact: 112,450
  Opportunity: 38,900
  Case: 67,200
- External ID field on all objects: Legacy_Id__c

Generate SOQL queries that verify:
1. Record count matches for each object (compare against expected counts above)
2. All Legacy_Id__c values are populated (no nulls — would indicate a load failure)
3. All AccountId lookups on Contact are resolved (no Contact with null AccountId where source had a value)
4. All Opportunity.AccountId lookups resolved
5. All Case.AccountId and Case.ContactId lookups resolved
6. Sample spot-check: 10 random Accounts with their full Contact and Opportunity counts

Also generate the equivalent Apex anonymous script that runs all checks,
prints a pass/fail for each, and throws an exception if any critical check fails —
suitable for running as a post-migration validation step in the deployment runbook.

Summary & Closing Thoughts

Key Takeaways — Chapter 5
  • SOQL performance analysis with AI catches selectivity and governor limit risks before they hit production — a 2-minute prompt prevents a potential P1 incident
  • Load plan generation from object relationship descriptions correctly handles multi-level dependency chains that are easy to get wrong manually
  • Transformation script generation (Node.js, streaming) is the highest-multiplier migration task — 6–8 hours reduced to 30 minutes per object
  • Data quality validation scripts with CI/CD integration (exit code on error threshold) make validation a first-class automated step rather than a manual pre-migration checklist
  • Platform Event-based integrations with retry logic follow a well-known pattern that AI implements correctly and completely — including the monitoring object that manual implementations often skip under time pressure
Closing Thoughts — The AI-Augmented Salesforce Team

Across five chapters and thirty-plus concrete use cases, a consistent pattern emerges: AI's value is highest for tasks that are patterned, voluminous, or tedious — boilerplate code, documentation, data transformation scripts, validation rules, test classes. For these tasks, AI is not a marginal improvement. It is a qualitative shift: from hours to minutes, from days to hours.

The Salesforce developers who will thrive in the next five years are not those who resist AI — it is those who learn to direct it precisely. They will know which tasks to delegate entirely to AI's first draft, which to use as a design conversation partner, and which require their own judgment and org-specific expertise. That combination — AI speed, human judgment — is what the next generation of Salesforce development looks like.
