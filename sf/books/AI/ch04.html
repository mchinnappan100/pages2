Chapter 04 · Documentation & Architecture

AI for Documentation & Architecture

Use AI to generate ApexDoc comments, technical design documents, architecture decision records, Mermaid diagrams, and release notes — eliminating the documentation debt that accumulates on every Salesforce project under delivery pressure.

Reading time: ~30 min
Multiplier: 8–15×
Key tools: Claude · mc-apex-doc · mermaid-viewer-cli · sf-doc-generator-cli

Documentation is the development task most consistently sacrificed under sprint pressure. Salesforce projects accumulate documentation debt silently — undocumented Apex classes, design decisions recorded nowhere, integration patterns understood only by the developer who built them. When that developer moves on, the knowledge goes with them.

AI has the highest productivity multiplier for documentation tasks because documentation is pure writing given existing artifacts — and writing is AI's primary strength. For documentation tasks, the multiplier is not 5× but 8–15×. A task that takes a developer a full day to write from scratch takes AI 10 minutes to generate a complete first draft.

ApexDoc and Inline Documentation Generation

Batch ApexDoc for Entire Classes

The most common documentation debt on Salesforce projects: Apex classes with no class-level or method-level documentation. AI adds complete ApexDoc comments — class descriptions, method descriptions, @param tags, @return tags, and @throws tags — by reading the existing code and inferring intent from variable names, method names, and logic.

Prompt Template — Full ApexDoc Generation
Add complete ApexDoc documentation to the following Apex class.

Requirements:
- Class-level comment: describe the class's purpose, responsibilities, and any important
  usage notes or constraints (e.g. must be called in a with-sharing context)
- Method-level comments for EVERY public and global method:
  * @description: what the method does (2-3 sentences max, plain English)
  * @param: one tag per parameter with type and purpose
  * @return: what the method returns and what null means
  * @throws: any custom exceptions this method explicitly throws
- For private helper methods: add a single-line comment explaining the WHY
  (not just what it does, but why the approach was chosen)
- Do NOT add comments that simply restate the method name

[PASTE YOUR APEX CLASS HERE]

Return the complete class with all documentation added inline.
Productivity Gain

Documenting a 200-line Apex class with 8 public methods takes a developer 1.5–2 hours to do thoughtfully. AI generates complete ApexDoc for the same class in 90 seconds. For a project with 80 undocumented Apex classes, the manual documentation effort is 120–160 hours. AI reduces that to 80 × 5 minutes of review = 7 hours. The mc-apex-doc npm package automates this workflow from the CLI for batch processing entire codebases.

README Generation for Salesforce Projects

Prompt Template — Project README
Generate a comprehensive README.md for a Salesforce DX project.

Project overview: [describe the project in 2-3 sentences]
Salesforce org type: [Production / Sandbox / Scratch Org]
Key custom objects: [list main objects]
Key Apex classes: [list main classes and their purpose]
Integrations: [list any external system integrations]
DevOps: [describe your CI/CD setup]

The README should include:
1. Project description and business context
2. Architecture overview (what the key components do)
3. Prerequisites (Salesforce CLI version, Node.js, etc.)
4. Setup instructions (clone, authenticate, push to scratch org)
5. Key configuration (Custom Metadata, Named Credentials that need setup)
6. Running tests locally
7. Deployment guide
8. Troubleshooting section covering the 3 most common setup issues

Use Markdown with headers, code blocks for commands, and a clear table of contents.

Technical Design Documents

Integration Technical Design Document

Technical design documents (TDDs) are required for most enterprise Salesforce implementations but take senior architects 2–3 days to write from scratch. AI generates the full TDD structure — architecture overview, data flow, error handling design, security model, and deployment plan — from a set of requirements bullet points.

Prompt Template — Integration TDD
Generate a Technical Design Document for the following Salesforce integration.

Integration summary: [describe the integration in 3-4 sentences]
Source system: [e.g. SAP S/4HANA — Order Management module]
Target system: Salesforce (CRM)
Direction: Bidirectional / One-way
Trigger: Real-time event / Scheduled batch / On-demand

Data objects involved:
- Source: [list source system objects/tables]
- Salesforce: [list Salesforce objects]
- Field mapping summary: [list key field mappings]

Requirements:
- Volume: [expected record volume per day]
- Latency: [real-time / near-real-time / batch]
- Error handling: [retry policy, dead letter queue, alerting]

Generate a TDD with these sections:
1. Executive Summary
2. Architecture Diagram (describe as a Mermaid sequence diagram)
3. Data Flow (step-by-step numbered flow)
4. Field Mapping Table
5. Error Handling and Retry Design
6. Security Model (authentication, authorization, data masking)
7. Governor Limit Analysis (SOQL, DML, CPU projections at stated volume)
8. Deployment and Testing Plan
9. Open Questions and Risks
Productivity Gain

A senior architect writing a thorough integration TDD from scratch takes 2–3 days. AI generates a complete first draft — all 9 sections — in 5 minutes. The architect spends 4–6 hours reviewing, filling in org-specific details, and refining the governor limit analysis. Total effort: 1 day instead of 3. The sf-doc-generator-cli npm package automates this from requirements documents.

Data Model Design Document

Prompt Template — Data Model Design Doc
Generate a Data Model Design Document for the following Salesforce implementation.

Business domain: [e.g. Field Service Management]
Custom objects to design: [list each object with its purpose]
Key relationships: [describe how objects relate to each other and to standard objects]
Key business rules: [list 5-10 business rules that the data model must support]

The document should include:
1. Entity Relationship description (describe relationships in text — I will render as ERD)
2. Object-by-object table: Object Name | Purpose | Key Fields | Relationships | Record Volume
3. Field design decisions: for any non-obvious field choices, explain the rationale
4. Sharing model recommendations: OWD setting per object with justification
5. Roll-up summary fields and formula field dependencies
6. Indexing recommendations for SOQL performance
7. Potential governor limit risks at stated volumes

Architecture Decision Records

Architecture Decision Records (ADRs) capture the context, options considered, and rationale behind significant technical decisions. They are invaluable for future maintainers who need to understand why a system was built a certain way — but are rarely written because they feel like overhead. AI makes writing them trivial.

Prompt Template — ADR Generation
Write an Architecture Decision Record (ADR) for the following decision.

Decision: [one sentence — e.g. "Use Platform Events instead of Outbound Messages for real-time integration"]

Context:
- What problem were we solving? [describe]
- What constraints existed? [e.g. volume requirements, security, existing infrastructure]
- When was this decided and by whom? [date and team]

Options that were considered:
1. [Option A]: [brief description]
2. [Option B]: [brief description]
3. [Option C — the chosen option]: [brief description]

Reasons the chosen option was selected: [list key reasons]
Known trade-offs accepted: [list downsides of the chosen option]
Consequences: [what this decision affects going forward]

Format as a standard ADR with sections:
Title, Status, Context, Decision, Consequences, Alternatives Considered, Date
Productivity Gain

Writing a thorough ADR from bullet point notes takes 30–45 minutes to structure and phrase properly. AI produces a publication-ready ADR from the same bullet points in 60 seconds. For teams that make 10–15 significant architectural decisions per project, this saves 5–10 hours of documentation writing per engagement and produces more consistent, complete ADRs than the time-pressured manual alternative.

Architecture Diagram Generation (Mermaid)

Mermaid is a text-based diagramming language that renders as professional diagrams. AI generates Mermaid diagram source from natural language descriptions — making it possible to produce sequence diagrams, ERDs, flowcharts, and architecture diagrams from a description in seconds.

Integration Sequence Diagrams

Prompt Template — Sequence Diagram
Generate a Mermaid sequence diagram for the following integration flow.

Participants: Salesforce, External ERP System, MuleSoft Integration Layer, Email Service

Flow:
1. Sales rep closes an Opportunity as 'Closed Won' in Salesforce
2. Salesforce fires a Platform Event (OpportunityWon__e)
3. MuleSoft subscribes to the Platform Event and receives it
4. MuleSoft queries Salesforce REST API for full Opportunity and Account details
5. MuleSoft transforms the data and creates an Order in ERP via REST API
6. ERP returns Order number and confirmation
7. MuleSoft updates Salesforce Opportunity with ERP Order Number via REST API patch
8. MuleSoft triggers an email notification via Email Service with order confirmation
9. Salesforce updates the Opportunity Stage to 'Order Placed'

Show error paths: ERP creation failure (MuleSoft logs error and creates Salesforce Task for rep)

Return ONLY the Mermaid code block, no explanation needed.

Data Model ERD

Prompt Template — Entity Relationship Diagram
Generate a Mermaid erDiagram for the following Salesforce data model.

Objects and key fields:
- Account: Id, Name, Type, AnnualRevenue, OwnerId
- Contact: Id, LastName, Email, AccountId (FK to Account)
- Opportunity: Id, Name, AccountId (FK), Amount, StageName, CloseDate
- OpportunityLineItem: Id, OpportunityId (FK), Product2Id (FK), Quantity, UnitPrice
- Product2: Id, Name, ProductCode, IsActive
- Case: Id, Subject, AccountId (FK), ContactId (FK), Status, Priority

Relationships:
- Account has many Contacts (1:M)
- Account has many Opportunities (1:M)
- Opportunity has many OpportunityLineItems (1:M)
- OpportunityLineItem references Product2 (M:1)
- Account has many Cases (1:M)
- Contact has many Cases (1:M)

Return ONLY the Mermaid erDiagram code, ready to render.
Productivity Gain

Drawing a complex sequence diagram in draw.io or Lucidchart takes 45–90 minutes for a 10-step flow with error paths. AI generates the Mermaid source in 30 seconds. The mermaid-viewer-cli npm package renders and exports it to PNG in one command, producing a presentation-ready diagram from description to image in under 3 minutes total.

Release Notes and Runbooks

Release Notes from Commit History

Prompt Template — Release Notes
Generate professional release notes from the following list of changes in this sprint.

Release version: [e.g. Winter '25 — Sprint 14]
Release date: [date]
Target audience: [Business stakeholders / Technical team / Both]

Changes deployed:
[PASTE YOUR COMMIT MESSAGES OR JIRA STORY TITLES HERE]
e.g.:
- feat: Add custom SLA escalation flow for Priority 1 Cases
- fix: Correct duplicate Contact merging logic in AccountMergeService
- feat: New LWC dashboard for pipeline health metrics
- refactor: Migrate 3 Process Builder automations to Flow
- fix: Governor limit fix in OrderSyncBatch for orgs with >500k Orders

Format the release notes with:
1. Summary (2-3 sentence overview of this release)
2. New Features (user-facing, in plain business language)
3. Bug Fixes (brief description of what was broken and is now fixed)
4. Technical Changes (for developers/admins — refactors, migrations, deprecations)
5. Known Issues / Limitations
6. Rollback instructions if the release needs to be reverted

Operational Runbook Generation

Prompt Template — Runbook
Generate an operational runbook for the following Salesforce batch process.

Process: [name and purpose of the batch job]
Schedule: [when it runs]
Normal behavior: [what it does when working correctly — expected log output, duration]

Write a runbook covering:
1. How to verify the job ran successfully (what to check in Apex Jobs, logs)
2. How to manually trigger the job if the scheduler failed
3. Common failure scenarios with diagnostic steps:
   a) Job shows 'Failed' status: how to investigate and re-run
   b) Job ran but processed 0 records: likely causes and fixes
   c) Job hit governor limits: how to diagnose and remediate
4. How to pause/resume the scheduled job without losing data
5. Escalation path: who to contact if you cannot resolve in 30 minutes
6. Related monitoring dashboards and log locations

Format as a step-by-step numbered runbook that an on-call admin can follow
without deep developer knowledge.
Productivity Gain

Writing a thorough operational runbook for a complex batch process takes a developer 3–4 hours — thinking through failure scenarios, writing clear steps for non-developer operators, and reviewing for completeness. AI generates a complete, structured runbook in 3 minutes that covers scenarios the developer might not have thought to document. Total effort: 20 minutes of review and customization. Runbooks that previously existed only in the original developer's head now exist as searchable documents.

Summary

Key Takeaways — Chapter 4
  • Documentation has the highest AI productivity multiplier (8–15×) because it is pure writing — AI's primary strength
  • ApexDoc generation for entire classes takes 90 seconds — apply it to every class before it goes to code review to establish a documentation baseline
  • Technical Design Documents generated from bullet-point requirements reduce architect writing time from 3 days to 1 day
  • ADRs written with AI assistance are more complete and consistent than time-pressured manual ADRs — invest 5 minutes per major decision to avoid months of future confusion
  • Mermaid diagrams from AI + mermaid-viewer-cli produce presentation-ready architecture diagrams from a description in under 3 minutes
  • Runbooks generated by AI and stored alongside the code they describe transform ops knowledge from tribal to institutional
