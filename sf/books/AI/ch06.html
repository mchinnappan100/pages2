Chapter 06 · PMD Code Quality

AI-Augmented PMD Code Scanning

How AI transforms PMD static analysis from an overwhelming violation list into an actionable quality pipeline — covering violation triage, bulk fixing, custom rule authoring, CI/CD integration, and the @SuppressWarnings strategy that keeps false positives from drowning real issues.

Reading time: ~35 min
Multiplier: 4–8×
Key tools: pmd-annotations · sf-code-scanner · Claude
PMD Contributor Perspective

Mohan Chinnappan is a contributor to PMD — the open-source static analysis tool that underpins Salesforce Code Scanner (sf scanner). The pmd-annotations npm package was built specifically to give Salesforce teams a visual, manageable interface for the @SuppressWarnings annotations that PMD-heavy codebases accumulate. This chapter reflects both the contributor's inside view of how PMD rules work and the practitioner's experience of applying AI to make PMD scanning dramatically more productive.

PMD is the backbone of Salesforce static analysis — it is the engine that powers sf scanner run and catches security vulnerabilities, performance anti-patterns, and maintainability issues before code reaches production. But raw PMD output is overwhelming: a large Apex codebase can produce hundreds or thousands of violations across dozens of rules, with terse messages that don't explain what to do. Most teams either ignore PMD entirely or suppress violations in bulk with broad @SuppressWarnings annotations — both of which defeat the purpose of static analysis.

AI changes this. With AI assistance, every PMD violation becomes understandable, every fix becomes explicit, and the suppression decision becomes documented and defensible. This chapter shows how to build a quality pipeline where PMD and AI work together to enforce Salesforce code quality at scale.

PMD for Apex — A Practitioner's Primer

How PMD Works on Apex Code

PMD analyzes Apex source code by parsing it into an Abstract Syntax Tree (AST) — a structured representation of the code's syntax. Each PMD rule is a visitor that traverses the AST looking for specific node patterns that match anti-patterns or vulnerabilities. When a rule's pattern matches, it emits a violation at the corresponding source line.

Understanding this AST-based model is important for two reasons: it explains why PMD catches what it catches (syntactic patterns) and why it misses what it misses (runtime behavior, complex data flow). PMD cannot know whether a DML operation will actually execute in a loop at runtime — it only knows whether the syntax places a DML statement inside a loop construct in the source code.

PMD Rule Categories for Apex

Running PMD via Salesforce Code Scanner

# Install Salesforce Code Scanner plugin
sf plugins install @salesforce/sfdx-scanner

# Run PMD on a specific directory, output as CSV for analysis
sf scanner run --target force-app/main/default/classes \
               --engine pmd \
               --format csv \
               --outfile pmd-results.csv

# Run only security category rules
sf scanner run --target force-app/main/default/classes \
               --category "Security" \
               --format json \
               --outfile security-violations.json

# Run with a custom ruleset XML
sf scanner run --target force-app/main/default/classes \
               --pmdconfig custom-ruleset.xml \
               --format sarif \
               --outfile results.sarif
Use pmd-annotations for Visual Analysis

After running the scanner, npx pmd-annotations ./force-app provides a visual dashboard of all @SuppressWarnings PMD annotations in your codebase — showing which rules are suppressed, where, by whom, and whether each suppression has a justification comment. This is essential for orgs that have accumulated suppression annotations over years without governance.

AI-Assisted PMD Violation Triage

The Triage Problem

A first PMD scan of a mature Salesforce codebase typically produces 200–2,000 violations. Not all violations are equal: some are critical security gaps, some are genuine performance anti-patterns, some are style preferences, and some are false positives in specific contexts. Without triage, developers either fix everything (weeks of work) or fix nothing (violations as noise). AI enables systematic triage in an afternoon.

Prompt Template — PMD Violation Triage Report
I have a PMD scan report for a Salesforce Apex codebase. Triage the violations
and produce an actionable prioritization.

PMD CSV output (or paste the violation list):
[PASTE YOUR pmd-results.csv CONTENT OR VIOLATION SUMMARY]

Triage criteria:
- P1 (Fix immediately): Security violations (CRUD, sharing, injection)
- P2 (Fix this sprint): Performance violations in DML/SOQL (loops)
- P3 (Fix next sprint): Best practice violations with high business risk
- P4 (Schedule): Design/complexity violations — refactor debt
- REVIEW (Possible false positive): Violations that may be context-appropriate

For each category:
1. Count and percentage of total violations
2. Top 3 most common rules in that category
3. A one-line fix strategy for each common rule
4. Estimated dev hours to fix each category completely
5. Recommended fix order (what gives the best quality/effort ratio)

Analyze PMD violations for a single Apex class and provide fixes.

PMD violations for this class:

  Line 56: AvoidDmlStatementsInLoops (Performance) — DML inside a for loop

  Line 92: AvoidHardcodingId (BestPractices) — Hardcoded Salesforce record Id

1. Explain what the PMD rule detects and why it matters on the Salesforce platform
2. Determine: is this a genuine risk or a false positive in this specific context?
3. If genuine: provide the corrected code for that section
4. If false positive: explain why and provide the @SuppressWarnings annotation
   with a justification comment (as recommended by the pmd-annotations governance tool)

Provide the complete corrected class at the end.
Productivity Gain

Manually triaging and fixing 20 PMD violations across a 300-line Apex class takes 2–4 hours — understanding each rule, deciding genuine vs. false positive, applying the right fix pattern for each. AI completes the same triage and fix in 3 minutes with explanations for every decision. For a codebase with 50 classes needing remediation, this compresses a 3-week cleanup sprint into 3 days of focused review work.

Key PMD Rules Deep-Dive with AI Fixes

The following rules appear most frequently in Salesforce Apex codebases and have the highest security or performance impact. For each, AI can explain the risk and generate the correct fix pattern.

ApexCRUDViolation Security · Critical

What it detects: SOQL queries or DML operations executed without first checking whether the running user has the required object-level (CRUD) permission.

Why it matters: In Apex code running without sharing, or called from a context where the user lacks object access, unguarded DML can create, read, update, or delete records the user is not authorized to touch. This violates Salesforce's security model and can fail Salesforce Security Review for ISV packages.

AI Fix Prompt
The following Apex method has an ApexCRUDViolation for a SOQL query on Contact.
Add the correct Schema.sObjectType.Contact.isQueryable() CRUD check.
Show where to add it, how to handle the permission failure gracefully
(throw a custom exception vs. return empty list), and explain which CRUD
methods to use for each DML operation type (insert=isCreateable, update=isUpdateable, etc.)

[PASTE THE METHOD]

AvoidSoqlInLoops Performance · Critical

What it detects: A SOQL query inside a for loop, while loop, or do-while loop body.

Why it matters: Each iteration issues a separate SOQL query. With a 100 SOQL query per-transaction governor limit, this fails as soon as the loop processes more than 100 iterations. In a Batch Apex context with scope size 200, a single SOQL-in-loop pattern guarantees failure on every batch execution.

AI Fix Prompt
This Apex method has a SOQL query inside a for loop (AvoidSoqlInLoops violation).
Refactor it to:
1. Collect all required query keys in a Set before the loop
2. Issue a single bulk SOQL query outside the loop using the Set
3. Build a Map from the query results keyed by the lookup field
4. Replace the in-loop SOQL with a Map.get() lookup inside the loop

[PASTE THE METHOD WITH THE SOQL-IN-LOOP PATTERN]

Preserve all existing logic and variable names. Show the before/after clearly.

ApexSOQLInjection Security · Critical

What it detects: Dynamic SOQL strings built by concatenating user-controlled input without using bind variables or String.escapeSingleQuotes().

Why it matters: An attacker can inject SOQL operators into the dynamic query to bypass WHERE clause filters, access all records regardless of sharing rules, or probe the org's data structure.

AI Fix Prompt
This dynamic SOQL has an ApexSOQLInjection vulnerability. Provide two fixes:
1. Using bind variables (preferred — immune to injection)
2. Using String.escapeSingleQuotes() (fallback when bind variables cannot be used)
Explain when each approach applies and the limitations of each.

[PASTE THE DYNAMIC SOQL CODE]

ApexUnitTestClassShouldHaveAsserts Best Practice · High

What it detects: An Apex test class or test method that contains no assertion statements (System.assert, System.assertEquals, System.assertNotEquals).

Why it matters: A test without assertions verifies only that code executes without throwing an exception — it does not verify correctness. Such tests provide false confidence, inflate coverage percentages, and fail to catch regressions. This is the most common test quality anti-pattern in Salesforce codebases.

AI Fix Prompt
This Apex test method has no assertions (ApexUnitTestClassShouldHaveAsserts).
Analyze what the production code being tested does and add meaningful assertions that:
1. Verify the expected return value or output
2. Verify that the expected DML operations occurred (query for the created/updated record)
3. Verify that the expected field values were set correctly
Do NOT add trivial System.assert(true) assertions. Each assertion must test a real behavior.

Production class under test: [PASTE PRODUCTION CLASS]
Test method to fix: [PASTE TEST METHOD]

AvoidHardcodingId Best Practice · Medium

What it detects: A hardcoded 15- or 18-character Salesforce record ID or prefix in Apex code.

Why it matters: Record IDs are org-specific. A hardcoded ID from a sandbox is invalid in production, causing runtime failures. Hardcoded object type prefixes break if the object is replaced or if the code is deployed to a different org type. IDs should come from Custom Labels, Custom Metadata, or a SOQL query.

AI Fix Prompt
This Apex class has hardcoded Salesforce IDs (AvoidHardcodingId violation).
For each hardcoded ID:
1. Identify what the ID refers to (record type, user, custom setting, etc.)
2. Recommend the correct approach to look it up dynamically:
   - Custom Label (for user-configurable values)
   - Custom Metadata (for deployment-time configuration)
   - SOQL query at runtime (for record IDs that must be current)
   - Schema.SObjectType prefix (for object type prefixes)
3. Provide the refactored code using the recommended approach.

[PASTE THE CLASS WITH HARDCODED IDs]

Writing Custom PMD Rules with AI Assistance

PMD's true power for mature Salesforce teams is the ability to write custom rules that enforce org-specific standards — naming conventions, required patterns, prohibited API usage, or project-specific architectural constraints. Custom rules are written in XPath or Java and added to a custom ruleset XML. AI makes authoring them dramatically more accessible.

XPath-Based Custom Rules

XPath rules are the most accessible custom PMD rule type — they match patterns directly on the Apex AST without writing Java. AI can generate the XPath expression from a plain-English description of the pattern to detect.

Prompt Template — Custom XPath PMD Rule
Write a custom PMD rule for Salesforce Apex using XPath that enforces the following standard.

Rule: All Apex classes that contain DML operations must use 'with sharing' or
      'inherited sharing' keyword. Classes using 'without sharing' must have an explicit
      @SuppressWarnings('PMD.ApexSharingViolations') annotation to confirm the decision.

In PMD XPath rule format:
1. Write the XPath expression that matches classes with DML but without 'with sharing'/'inherited sharing'
   and without the SuppressWarnings annotation
2. Write the complete rule XML block (name, message, description, priority, example)
3. Explain how to add this to a custom-ruleset.xml file
4. Provide an example Apex class that WOULD trigger this rule
5. Provide an example Apex class that would NOT trigger this rule

Custom Ruleset XML Generation

Prompt Template — Custom Ruleset
Generate a custom PMD ruleset XML file for a Salesforce enterprise project.

Include the following rule selections and customizations:

From the standard Apex rulesets, include ONLY:
- All Security rules (category/apex/security.xml)
- Performance rules: AvoidSoqlInLoops, AvoidDmlStatementsInLoops, AvoidSoslInLoops
- Best Practices: ApexUnitTestClassShouldHaveAsserts, AvoidHardcodingId,
  ApexUnitTestShouldNotUseSeeAllDataTrue, DebugsShouldUseLoggingLevel

Customized thresholds:
- CyclomaticComplexity: raise threshold to 20 (default is 10 — too strict for our handlers)
- ExcessiveClassLength: raise to 500 lines (default 1000 is fine)

Custom rules to add (write as XPath rules):
1. Enforce: all classes must have an @author tag in their class-level comment
2. Prohibit: System.debug() calls in production classes (allow only in classes ending with 'Test')

Output: a complete custom-ruleset.xml file ready to pass to sf scanner via --pmdconfig
Productivity Gain

Writing a PMD XPath rule from scratch requires reading PMD's AST documentation, understanding the Apex grammar's node types, and iteratively testing the XPath against sample code. This takes 2–4 hours per rule for a developer new to PMD's AST model. AI generates a correct XPath expression and the complete rule XML in 2 minutes, with a working example. For teams that need 5–10 custom rules to enforce project standards, this saves a full sprint's worth of tooling work. Mohan's PMD contributor experience is reflected in the pmd-annotations package, which surfaces rule metadata alongside suppression decisions.

PMD in CI/CD Pipelines with AI-Generated Configuration

GitHub Actions Integration

Prompt Template — CI/CD PMD Pipeline
Generate a complete GitHub Actions workflow that runs PMD via Salesforce Code Scanner
on every pull request and blocks merges when violations are found.

Requirements:
- Trigger: pull_request to main and develop branches
- Run sf scanner on the changed files only (not the full codebase on every PR)
- Use a custom ruleset: .sfdx/pmd-ruleset.xml
- Fail the workflow if any P1 or P2 violations are found (Security or Performance)
- Allow P3/P4 violations (Best Practice, Design) to pass with a warning
- Post a comment on the PR with a formatted violation summary table
- Cache the Salesforce CLI and scanner plugin between runs
- Output results as both SARIF (for GitHub Code Scanning dashboard) and CSV (for the comment)

Also generate:
1. The .sfdx/pmd-ruleset.xml referenced in the workflow (Security + Performance rules only)
2. A script get-changed-apex.sh that outputs only the Apex files changed in the PR
3. The PR comment template showing violation table format

PMD Baseline Strategy

Introducing PMD into a codebase with existing violations requires a baseline strategy — otherwise the CI pipeline immediately blocks all PRs with pre-existing violations that the current PR author did not introduce. AI can design the baseline approach.

Prompt Template — PMD Baseline Strategy
Design a PMD baseline strategy for introducing static analysis into an existing
Salesforce codebase that already has 800 violations.

Goals:
- Don't block PRs with pre-existing violations the current author didn't introduce
- Ensure new code added after the baseline date is violation-free
- Gradually reduce the existing violation count over time

Design:
1. How to generate and store the baseline violation report
2. How to configure the CI workflow to diff new violations against the baseline
3. How to assign ownership of pre-existing violations for remediation sprints
4. KPI metrics to track (violation count by category over time)
5. A policy for when a class's violation count is allowed to stay unchanged vs.
   must be reduced before a PR touching that class can merge

Generate the Node.js script that diffs a new PMD report against the baseline
and outputs only the NET NEW violations introduced in the current PR.

@SuppressWarnings Strategy and Governance

@SuppressWarnings('PMD.RuleName') is a necessary safety valve — some violations are legitimate false positives in specific contexts, and suppressing them keeps the violation report focused on real issues. But unsupervised suppression becomes its own problem: annotations accumulate without justification, teams stop trusting the scan report, and genuine violations hide behind broad suppressions.

The Three-Part Suppression Standard

A well-governed @SuppressWarnings annotation always has three components: the specific rule name (never a blanket PMD suppress), a justification comment, and a reviewer who approved the suppression decision. AI generates annotations that comply with this standard.

Prompt Template — Governed Suppression
I need to suppress a PMD violation that is a false positive in this context.
Generate a compliant @SuppressWarnings annotation following the three-part standard.

Violation: ApexCRUDViolation on a SOQL query
Context: This class is a test utility class — it always runs in test context
         where sharing and CRUD checks are not applicable and intentionally bypassed.
         The class is only callable from @isTest methods.

Generate:
1. The precise @SuppressWarnings annotation (specific rule name only, not 'PMD')
2. A multi-line comment above it that explains:
   a) Why this is a false positive (not a genuine risk)
   b) What safeguard ensures this code cannot be called outside the intended context
   c) The date and reviewer who approved the suppression
3. A code snippet showing where to place the annotation (class-level vs. method-level)
4. Confirm: would the pmd-annotations npm package detect and surface this annotation
   for governance reporting?

Auditing Existing Suppressions

Prompt Template — Suppression Audit
Audit the following @SuppressWarnings annotations in this Apex codebase.
For each suppression, evaluate:
1. Is the suppression specific (rule name) or broad ('PMD' — suppresses everything)?
2. Is there a justification comment? Is the justification convincing?
3. Given the surrounding code context, is this genuinely a false positive
   or does it appear to be suppressing a real violation?
4. Recommendation: Keep with existing justification / Update justification /
   Remove suppression and fix the violation

pmd-annotations + AI — The Governance Workflow

The complete PMD governance workflow combining Mohan's npm tool with AI: (1) Run npx pmd-annotations ./force-app to get a visual dashboard of all suppressions in the codebase. (2) Export the suppression list. (3) Feed it to the AI audit prompt above to identify unjustified or suspicious suppressions. (4) Fix genuine violations, update justification comments for confirmed false positives. This audit takes 1–2 days for a large codebase — without AI it would take a week.

Summary

Key Takeaways — Chapter 6
  • PMD's AST-based analysis catches syntactic anti-patterns reliably — but raw violation output requires AI-assisted triage to be actionable for a team under delivery pressure
  • The three critical rule categories to fix immediately are Security (CRUD, sharing, injection), Performance (SOQL/DML in loops), and test quality (missing assertions) — these have the lowest false-positive rate and highest risk
  • AI generates correct, explanatory fixes for common PMD patterns in minutes — the class-level fix prompt (paste violations + class, get back corrected class) is the highest-leverage workflow for cleanup sprints
  • Custom XPath PMD rules authored with AI assistance enforce project-specific standards that standard rulesets do not cover — governance rules for naming, required patterns, and prohibited API usage
  • The CI/CD PMD baseline strategy prevents the "800 violations on day one" problem that kills static analysis adoption in mature codebases
  • @SuppressWarnings requires governance: specific rule names, written justifications, and the pmd-annotations dashboard to surface the full annotation inventory for audit
  • PMD is open-source — contributing custom Apex rules back to the PMD project (as Mohan has done) benefits the entire Salesforce developer community
